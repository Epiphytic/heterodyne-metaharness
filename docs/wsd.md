# wsd: the workstream daemon (queue and state)

`wsd` picks up beads for each configured workstream, one coder bead at a time, and keeps a journal so that a crash never loses or repeats a claim, a launch, a park or a resume (ADR 0001 §3.3, §4.3, §5.2, §9). This page covers plan 3 (the queue, the journal, pickup, parking and recovery) and plan 4's agent runtime (§5). Approvals (plan 5) and Marmot (plan 6) plug into the seams listed at the end.

**`wsd run` launches agents only when `[platform] sandbox = "openshell"`, which only an operator's edit sets (§5).** With what setup records (`bubblewrap` on Linux), `none`, or `seatbelt`, it holds every workstream (`runtime_unavailable`) and claims nothing.

## 1. Configuration

All of it is host config (`config.toml`); a workstream file can't set `[wsd]` or `[integrations]`.

| Key | Meaning |
|---|---|
| `wsd.backstop_seconds` | How often pickup runs without a trigger. Default 60. |
| `wsd.reconcile_seconds` | How often state is rebuilt from beads and the runtime, then pickup runs. Default 300. |
| `wsd.launch_failures_before_human` | Failed launches of one bead before it is `stuck` with `needs-human`. 1 to 100, default 2. It also bounds consecutive deaths of a bead's session, counted before each launch: at the bound the bead is `stuck` (`crash_loop`) instead of launched again. The count resets on a live lifetime stop, a release, or a new claim (§5). |
| `wsd.park_attempts_before_human` | Failed park attempts (session not confirmed stopped, git failure) before `stuck`. Default 3. Beads being unreachable never counts. |
| `wsd.inbox_attempts_before_human` | Failed attempts to apply one inbound event before it needs a human. Default 3. |
| `wsd.coder_role` | The role (from a workstream's `[roles]`) that runs beads. Default `coder`. Renaming it never frees the role: every session the runtime lists for the workstream holds it, whatever role it was launched as, and a bead already picked up keeps the role recorded for it. |
| `integrations.beads.btq` | Required. The btq checkout; wsd loads its `bin/btq` and uses its `Queue` as agent `wsd`. In code this is `WsdSettings.btq_checkout`. |
| `integrations.beads.config_dir`, `repo`, `dolt_host`, `dolt_port`, `dolt_database`, `tls_cert` | Optional btq locations, passed to `Queue` unchanged. Unset ones fall back to btq's own `BTQ_*` environment and defaults. |
| `integrations.beads.credentials` | Optional. Must be `{ file = "<path>" }`: btq's credentials file. Inline secrets are refused. |

**`BTQ_REPO` is not the btq checkout.** btq itself reads `BTQ_REPO` as the beads database repository (the same thing as `integrations.beads.repo`). The plan and btq's contract test use `$BTQ_REPO` for the btq checkout, which here is `integrations.beads.btq`. Don't conflate them: if `repo` is unset and wsd's environment has a `BTQ_REPO` pointing at the btq checkout, btq will take that checkout as its beads repository. Set `repo` explicitly, or keep `BTQ_REPO` out of wsd's unit environment.

A workstream is `workstreams/<name>.toml`, where `<name>` is a slug (lowercase letters, digits, `.`, `_`, `-`). wsd needs:

- `[repos]`: repository name to absolute path (or `~/...`). One must be called `default`. A bead's `metadata.repo` picks another one; an unknown name makes that bead `stuck` with `config_invalid`.
- `[roles]`: `coder` (or your `wsd.coder_role`) must name a profile from `[profiles]`.

The journal, locks and control socket live in `<state>/wsd/` (0700): `wsd.db`, `wsd.lock`, `claims/<ws>.claim` and `ctl.sock`.

## 2. Commands

| Command | Does |
|---|---|
| `wsd run` | Runs the daemon. Exit 78 means a configuration problem, a journal that failed its check, or something other than a socket at the control socket's path (wsd never removes it); the unit should not restart on it. Exit 1 means another wsd holds the state directory, or another process has the journal locked; retrying is safe and nothing was changed. A timer (backstop or reconcile) that dies ends `wsd run` with an error rather than leaving a daemon that never picks up again; the unit restarts it. On SIGTERM (even mid-startup) wsd stops taking requests and cancels every job that has not started, on every workstream at once (no queued job starts after it), then waits up to 120 s for jobs already running, closes the journal and only then releases its instance lock; the control socket and timers never start after a stop, and the timers never start after a stop that arrives while the socket is opening. If jobs are still running after the 120 s, it exits 1 at once (`os._exit`, even if it can't write its message): to the journal that is a crash, which the next start's recovery replays. The unit's stop timeout must exceed the 120 s. |
| `wsd unit [--python P] [--config-dir D] [--state-dir D] [--release C]` | Prints the systemd user unit, `heterodyne-wsd.service` (below). Exit 78, with nothing on stdout, when a value can't go in a unit. |
| `wsd tick pickup [--ws WS]` | Asks the running wsd to run pickup now. Timers may call it. Each workstream runs its jobs one at a time on its own worker, with at most one pickup and one reconcile waiting: a tick that finds one waiting joins it and gets its outcome. Each workstream also has its own backstop and reconcile timers. A busy workstream never delays another, its timers, or status. A pickup or reconcile that raises replies `failed`, is recorded as `tick_failed`, and the workstream is recovered again before its next pickup. |
| `wsd tick reconcile [--ws WS]` | Asks for a reconcile (recovery, then pickup). |
| `wsctl pause WS` | Asks wsd to stop new claims for `WS`. Returns only once no claim can start. Needs a running wsd. |
| `wsctl resume WS` | Asks wsd to allow claims again; wsd then runs a pickup. Pauses and resumes waiting together behind a busy workstream apply the one asked last, once. A request a later one overtook is refused, with the state wsd published. |
| `wsctl status [WS] [--all]` | Each workstream's state, holds, beads with their state and reason, open journal steps and the last event number. Closed and dropped beads are only counted (`finished=`) unless `--all` lists them too. A `stuck` workstream also shows `attention=not idle; a human must act`. A reply is at most 1 MiB; one that would be longer fails with `reply too large` (ask about one workstream, or leave out `--all`) and is never cut short. |
| `wsctl unlanded WS` | Shows the workstream's sessions whose commits were not landed (§5). |
| `wsctl resolve WS SESSION --generation N (--land --tip SHA \| --keep --tip SHA \| --discard [--tip SHA])` | Lands, keeps or discards one unlanded session's commits, then removes its directory (§5). It runs on the workstream's lane; a repeat goes on from where a failed one stopped. |

**The unit.** `deploy/install.sh` writes `~/.config/systemd/user/heterodyne-wsd.service` from its release with `wsd unit`, and starts it after admind ([deploy/store-helper/README.md](../deploy/store-helper/README.md)). The unit is generated, never committed. It runs `<release>/.venv/bin/python3 -m heterodyne.wsd run` with `Type=simple`, `Restart=always`, `RestartSec=5`, `RestartPreventExitStatus=78` (a configuration problem doesn't restart-loop), `TimeoutStopSec=150` (more than the 120 s drain), `KillMode=control-group` (the tmux server is in its own scope, so it outlives a stop or restart), `UMask=0077`, and `WantedBy=default.target`. Its environment block sets `PATH`, `HETERODYNE_CONFIG_DIR` and `HETERODYNE_STATE_DIR` to what the installer checked, and unsets `BTQ_REPO` and the `XDG_*` overrides, so wsd never sees `BTQ_REPO` (§1). Run by hand, `wsd unit` resolves the two locations from its environment and writes them explicitly. The installer counts wsd ready when `wsctl status` answers, and refuses to install while a wsd runs outside its unit.

Pause is btq's own pause flag for the workstream's session worker, which wsd sets under the workstream's claim lock. A direct `btq pause` on that worker sets the same flag without the lock: wsd honours it from its next claim check, so at most one claim already under way can still complete. With wsd stopped nothing claims, so `wsctl` refuses rather than acknowledge anything. Pause stops **new claims only**. A running bead carries on, and a parked bead whose blockers closed still resumes. wsd never unclaims a bead.

## 3. States

Each bead wsd holds has one state and, when it is waiting or stuck, a reason:

- `claiming`, `starting`, `running`, `resuming`: being started, working, or coming back from a park.
- `parking`, then `parked` (`blocked_on_bead`), `waiting_input` (`waiting_on_operator`: it waits on an approval, question or confirm bead) or `held` (`held_by_operator`: `/stop`).
- `stuck`: needs a human. The reason says why (`launch_failed`, `crash_loop`, `launch_unrecorded`, `park_failed`, `config_invalid`, `claim_lost`, `routing_changed`, `worktree_failed`, `journal_lost`, `stop_unconfirmed`, `needs_human`, `unexpected_state`) and the bead gets the `needs-human` label.
- `stuck` with `unclaimable` is different: a ready bead wsd has **not** claimed, because btq's claim can never take it (a `session:` pin on the workstream session, or wsd's park labels left on an unclaimed bead). It gets no `needs-human` label and no release applies to it. A human repairs the bead (removes the pin or the labels) and the next pickup claims it; a bead that stops being ready is forgotten.
- Owned `held` and `stuck` beads move on only through the operator's release (plan 6). Removing `v2:held` or `needs-human` by hand changes nothing in wsd.
- `closed`, `dropped` (no longer ours).

A workstream is `running`, `idle`, `all_blocked`, `paused`, `held` or `stuck`. `stuck` is never idle: status, tick and resume replies all carry `attention: not idle; a human must act` for it. What the human does depends on the reason: release an owned stuck bead, or repair an `unclaimable` one. `held` lists its holds: `beads_unreachable`, `runtime_unavailable`, `claim_uncertain`, `launch_uncertain` (a launch whose outcome the runtime could not report), `actions_unreconciled` (a plan 5 action in any state but `pending`, `succeeded` or `failed`, closed beads included). A hold is retried on every pickup and cleared once its cause is gone. Holds never escalate a bead: an outage is not the bead's fault.

Every state change is also a progress event in the journal, carrying the reason, its detail (for a parked bead, the blocker IDs) and the message or event that caused it when there is one.

## 4. Recovery

On start, before the control socket opens, wsd runs for each workstream:

1. the journal integrity check (a failed check stops wsd with exit 78 and leaves the file in place; move it aside to start from beads alone);
2. read every bead the workstream's per-bead workers hold, found by assignee whatever its labels say, and every session the runtime may still be running;
3. hold the workstream while any action is unsettled, closed beads included;
4. replay every open park, release and escalation, and read back any claim a pickup left uncertain;
5. the sweep: stop the sessions of beads no longer ours, give a running bead whose session is gone a resume operation, and hold as `stuck` anything beads and the journal disagree on;
6. then a startup pickup, and only then events.

Recovery never launches: every launch goes through pickup's launch guard, which checks the runtime, the holds, the coder role, `needs-human`, btq's own post-claim checks, the launched-session record on the bead, whether the bead is still runnable, and its worktree, in that order. A workstream whose recovery failed stays `held` and is recovered again before its next pickup; so does one whose pickup, tick or recovery raised. A job that fails on a timer is recorded as a `tick_failed` event (skipped if the journal itself is locked) and the timer keeps running. Nothing is inferred from missing evidence. An unreadable claim, session list, session record or pause flag holds rather than proceeds. A bead the journal has no row for (a lost journal) is held as `journal_lost` until the operator releases it.

The journal is backed up with `Journal.backup(dest)`, a consistent online copy (SQLite's backup API). Scheduling it next to the beads backups is plan 8's job.

## 5. Runtime

**Enabling it.** `heterodyne setup` records `bubblewrap` on Linux, which builds no runtime: wsd prints a one-line notice and holds every workstream. To enable the runtime, set `sandbox = "openshell"` under `[platform]` in the host `config.toml`, prepare the host as `packaging/sandbox/README.md` describes, and restart wsd.

With `[platform] sandbox = "openshell"`, wsd runs each session's agent CLI in its own OpenShell sandbox, in a pane of wsd's own tmux server (socket `heterodyne-wsd`; on systemd it runs in a transient `heterodyne-wsd-tmux-*` scope, so it outlives a wsd restart). Setup and the image are in `packaging/sandbox/README.md`; the `[sandbox]` keys are in [configuration.md](configuration.md).

**The session directory.** Each session has a directory under `<state>/sessions/<short id>/`: its record `session.json`, the agent's `home`, the `bridge`, its private git directory `git`, and one `r<generation>` folder per launch (the hook socket, its token and the self-test files). Only `home`, `bridge`, `git` and the generation's folder are bound into the sandbox. The record is written before every step, so a dead wsd's half-done launch is found and cleaned up. Its phases are `creating`, `testing`, `starting`, `running`, `stopping` and `ended`. It also records whether the private git directory was seeded, whether the sandbox was created, whether a generation ever ran, the agent's native session ID, the lifetime deadline, and whether a WIP commit or a landing is still owed.

**The launch.** A launch checks the adapter, the pinned CLI version, the repository and worktree, and the login's freshness: a login that expires within the maximum lifetime plus the stop margin refuses the launch, since plan 4 never refreshes one. It then seeds the session's home and private git directory, sets the deadline, and starts the deadline watcher (the `wsd-<short id>-r<generation>` pane, which deletes the sandbox at the deadline even if wsd is down). The record says a create may be submitted before the watcher starts, and only then does wsd create the sandbox. A watcher stays while the record shows a create that never returned and a session not yet ended, so a wsd that dies mid-create can't leave a sandbox unwatched. Before the agent does any work, the §7 self-test runs in two parts. On the exec path it checks the outer fence (the workload container's `NetworkMode=none`), then runs the probes: the real home and other accounts' logins are unreadable, only allowlisted hosts and the model host are reachable, direct network and control operations are refused, wsd's socket is absent, the host environment is not inherited, and the probe can't be tampered with. On the agent path the same probes run from the agent's own prompt, and the workload's namespaces and podman cgroup are checked; the cgroup is frozen while its members are read. Every launch fails closed, before the sandbox is created, unless `kernel.yama.ptrace_scope` is exactly 1. A failed check ends the sandbox and refuses the launch, naming the check (`launch self-test failed: <check>`). Nothing that can't be listed, read or confirmed is assumed absent: it is `RuntimeUnavailable` or an uncertain launch.

**Resume (D9).** A relaunch resumes the agent's own session when the session's home holds its state. It starts fresh only when the record shows that no generation ever ran. A session that ran but whose state can't be found is `RuntimeUnavailable`: missing state is never evidence that none existed. The agent must report the native session ID it was started with; a different one fails the launch.

**The lifetime stop (D13).** A session lives at most `max_lifetime_minutes` from the moment its login can be reached, and never past the login's expiry less `stop_margin_minutes`. Within the margin of its deadline it is stopped at the next turn boundary, and at the deadline it is interrupted. Every end lands the session's private commits on the bead branch first; a lifetime end then makes a WIP commit. Both are recorded before anything is stopped, so a crash at any point replays them exactly once. A WIP commit that keeps failing stays owed: the next launch refuses (`the last generation's lifetime WIP commit is still owed`) and counts against the bead's launch-failure budget, so a persistent failure escalates the bead like any other failed launch rather than holding the workstream. wsd can't promise to stop a healthy session before its deadline (a long job or a stale clock can carry pickup past it), so the watcher records what it saw: at its first pass at the deadline, before it kills anything, it writes `reaped-r<generation>.json` beside the record if the record shows that generation running, the backend lists its sandbox and its pane lives. That generation's end is then a lifetime end. A session found dead after its deadline, with no such marker, is a death that still owes its lifetime WIP.

**How a session ended (btq-g08sd).** The record's `end_cause`, written once in the first `stopping` write and never changed, is `stopped` or `lifetime` only when wsd confirmed the generation live as it began the stop, or the watcher's marker says it was live at the deadline. A refused launch is `refused`, and everything else, including absence found late, is `died`. `AgentRuntime.ended(key)` reports it. Before each launch of a bead, wsd's launch guard accounts every launched generation once: a death adds one to the bead's count, a live lifetime end resets it, and an intentional stop (park, defer, release, an operator stop) does neither. When the count reaches `wsd.launch_failures_before_human`, the bead is `stuck` with `crash_loop` and `needs-human`, and the launch that would follow never happens; a release clears it. A reboot or a backend outage that kills a running session counts as a death. The counts live in the journal's `meta` table, so they survive restarts. A resolve keeps the end (`crash_end:` in `meta`).

**Unlanded commits.** When a session's private commits can't be landed on the bead branch, the session still ends, but its record is marked unlanded and its private git directory is kept. From then on `sessions()` and `stop()` for that workstream raise `RuntimeUnavailable`, so the whole workstream is held (`runtime_unavailable`), across restarts, until a human resolves it. No pickup, relaunch, park, defer or lifetime WIP commit runs, because a WIP on the host branch would diverge from those commits. A park or defer that was under way stays open at its stop step (`stop_unconfirmed`) and finishes once the hold clears. The hold detail in `wsctl status` names the session and the command that shows it, for example ``session hz0123456789ab generation 1: its commits were not landed; see `wsctl unlanded alpha` (docs/wsd.md §5)``. No message names a path.

To resolve it, with wsd running:

1. `wsctl unlanded <ws>` shows each of the workstream's unlanded sessions: its short ID, generation, bead and branch; the landed tip and the session's tip as full SHAs (or `tip: unreadable (<reason>)`); how far the session is ahead and behind, and whether a fast-forward is possible; and up to 20 commit subjects. The subjects are the agent's and untrusted: each is shown as printable ASCII only (anything else is `?`), cut to 72 characters. A session that may still run (its pane, a reaper of any generation, or a sandbox of any generation is still there) shows `running` and nothing else. A failure on one session is shown on it, and the others are still listed.
2. `wsctl resolve <ws> <short id> --generation <n>` with one action:
   - `--land --tip <sha>` fast-forwards `btq/<bead>` to the tip. If the branch moved and can't be fast-forwarded, it refuses and changes nothing.
   - `--keep --tip <sha>` creates `refs/heads/unlanded/<bead>/<short id>-g<n>` at the tip and leaves the bead branch alone. A ref already there at the tip counts as done; one at another SHA, or an existing `unlanded` or `unlanded/<bead>` ref, refuses with `the keep ref can't be created`. The `unlanded/` branch namespace is reserved for this: don't create branches under it.
   - `--discard [--tip <sha>]` imports nothing. `--tip` may be left out only when the tip is unreadable, so nothing readable is discarded unseen.

   `--tip` is the confirmation: it must equal the tip wsd reads at resolve time, as `wsctl unlanded` showed it. wsd reads the session's directory as untrusted: it copies only its object files (plain files, no links) into a store of its own, checks them with git's strict checks there, and imports from that store, never running git in the session's directory. Then the session's directory is removed, its conversation with it, so the next launch of that session starts the agent afresh.
3. The resolve runs on the workstream's lane, like a pickup, and records each step in an intent (`<state>/resolutions/`) before the next. The workstream stays held from the intent's first write until it is gone, which is only once the `unlanded_resolved` event is journaled. If a resolve fails or wsd stops midway, the reply says why: run the same `wsctl resolve` again. It goes on from the last step, and journals the event once. A repeat that names another workstream, action, tip or generation is refused while the intent is there.

   Two refusals point here. `the resolve's state is inconsistent` means the session's directory and its trash (`<state>/resolutions/<short id>-g<n>.trash`) are not where the intent's step says, or are not the directory it confirmed: something other than wsd changed them. wsd changes nothing then; compare them with the intent by hand. `the session has no record` means a session directory without a record and without an intent: this command never removes one, since it may be a launch's leftover rather than an unlanded session.
4. Run `wsd tick pickup --ws <ws>` (or wait for the next pickup). The hold clears once the runtime lists sessions again.

A resolve drops a lifetime WIP mark the session still owed, with its record; it makes no WIP commit itself. The worktree's uncommitted changes stay there, and the next park or lifetime stop commits them as usual, as after manual step 4.

A resolve carries the generation's end from its record into the journal before the hold clears, so the next launch's guard accounts it as it would have from the record (btq-wpyv5). A live stop isn't counted, a live lifetime end resets the count, and a death counts.

When wsd is not running, the manual steps are the fallback:

1. Check that nothing is running: `tmux -L heterodyne-wsd ls` lists no `wsd-<short id>` pane, and the record `sessions/<short id>/session.json` says `"phase": "ended"`.
2. Treat the directory as untrusted: the agent could write to it. From the bead's repository, fetch its bead branch (never run git inside it): `git fetch --no-tags <state>/sessions/<short id>/git btq/<bead>`. Review `git log btq/<bead>..FETCH_HEAD` and the diff.
3. If you want the work, land it as a fast-forward only. Confirm `git merge-base --is-ancestor btq/<bead> FETCH_HEAD`, then run `git update-ref refs/heads/btq/<bead> FETCH_HEAD btq/<bead>`. If you don't want it, skip this step.
4. Remove the whole session directory, `<state>/sessions/<short id>`, not only its record: a private git directory without a record refuses the next launch. The agent's conversation goes with it, so the next launch of that session starts the agent afresh. Uncommitted changes in the worktree are kept, and the next park or lifetime stop commits them as usual. The next launch has no ended record to read, so it counts one death (unless a release reset the count first). If wsd can be started, do this step with `wsctl resolve` instead: after step 3, `--land --tip <the landed tip>` imports nothing, and otherwise use `--discard --tip <tip>`. Either keeps how the session ended. Removing the directory by hand counts one death.
5. Start wsd. If `<state>/resolutions/` holds an intent for the session, finish it with `wsctl resolve` instead: the hold stays while it is there.

**One session per bead branch.** A bead's branch `btq/<bead>` holds one session at a time, so a launch is refused (`another session of this bead still holds its branch`) while another session's record of that bead, in the same repository, is not ended, is unlanded, or still owes its lifetime WIP commit. A launch never ends that other session to make room: the hold clears through its own workstream's pickup (which ends a dead session) or its `stop`, and an unlanded one through the steps above.

**What `RuntimeUnavailable` holds.** wsd holds the workstream (`runtime_unavailable`, with the runtime's reason as its detail) when the backend can't list its sandboxes, a session's commits were not landed (above), a sandbox has no session record, a session's pane or record can't be read, a session's end can't be confirmed, or a session ran but its state can't be found. Every listed session counts as the coder's, and a session whose end is unconfirmed stays listed as `unknown`. The hold is retried on every pickup.

**The brief, steer and session events (plan 5i part 1).** wsd pastes each session's brief once the self-test's probe turn has ended (within 60 seconds). The launch counts only once the agent's next `UserPromptSubmit` confirms it took the brief; otherwise the launch fails (`the agent's first turn did not end`, `the agent did not take its brief`). The paste is bracketed, so a multi-line brief arrives as one prompt. A first brief gives the bead's ID, title, description and acceptance criteria, then how to work: commit locally on `btq/<bead>`, never push, never run btq or bd, and one how-to line for each op the workstream handles (`question`, `ask`, `close`, and what a turn that ends without a request means), so a session is never told to make a request that would be refused. A resume brief says where the session is, repeats the rules, and carries its notes. A handoff to another account starts fresh, so it gets the first brief, with the notes.

The bead's text and the notes are untrusted. Before they are pasted, CR and CRLF become newlines, every other terminal control (C0 but tab and newline, DEL and C1) is shown as `\xNN`, a lone surrogate as `\udNNN`, and a literal backslash as `\\`, so an ESC can't end the paste early, a CR can't submit the rest as prompts of their own, and a `\xNN` in the brief always stands for an escaped control. The title is kept to one line and cut at `TITLE_MAX` (512 UTF-8 bytes), and the description and the criteria at 12,288 bytes each; each cut says `[cut: N more bytes]`. The runtime refuses a brief that still holds a control, isn't valid UTF-8, or is over `BRIEF_MAX`.

Resume notes (ADR §5.6: part 2's answers and decisions, part 3's review findings) ride on the resume brief. `brief.fit` takes whole notes, oldest first, while they fit 16,384 bytes (each with its `--- i ---` line), and stops at the first that doesn't. The first note is always taken, so every brief makes progress; it is cut only past 65,536 bytes, which is a writer's bug. Once the launch's receipt says `started`, only the notes the brief carried are marked delivered (`notes_delivered(ws, bead, upto)`), so a crash before then delivers them again: delivery is at least once. The rest stay pending, named by count in the brief, for part 2's steer or the next brief (`test_fit_takes_whole_notes_and_acks_only_those_it_took`, `test_an_overflowing_brief_leaves_the_rest_pending_across_a_restart`).

**Steer (D4).** `steer(session_key, generation, text)` pastes into the session's pane only for the generation asked for, and only at a turn boundary this wsd process's socket has seen. After a wsd restart or a rebind the socket's turn state starts empty, so a steer is refused (`the session is mid-turn`) until the next turn end. The socket spends the boundary before the paste and holds back turn events until the paste returns (`SessionServer.at_boundary`), so no turn can start between the idle check and the paste, and two steers never share a boundary. A paste that failed before reaching the pane gives the boundary back and is `SteerRefused`; one that may have landed keeps it spent and is `SteerUncertain`. The text must be valid UTF-8 of at most 16,384 bytes with no terminal control but tab and newline: a steer with one is refused, never escaped. Every refusal has fixed wording. Text an operator types into the pane is outside the gate.

**The session event log.** Each Stop after the brief (never a `StopFailure`, and never the probe's turn) and each `ws-request` the runtime accepts is one JSON line of `sessions/<short id>/r<generation>-session-events.jsonl`, outside every bind, written whole and fsync'd, with its directory entry, before the agent is answered. So `accepted` means durable, never decided: the reply tells the agent to end its turn, and the decision comes later (D1). Lines are numbered `e1, e2, ...` in file order under the log's lock, and the event ID is `<key>:g<generation>:e<n>`. A Stop's turn is read back from the log, so it survives a restart. A request's `rid` (one per shim invocation) gets the first reply when it is resent, and is never logged or delivered twice. A request for an op the workstream doesn't handle is `unsupported`, and one without a valid `rid` is `malformed`.

A torn last line was never answered, so nothing it held was accepted: readers ignore it, and opening the log to append (a launch or a rebind) first cuts it and fsyncs the cut (`DIAG_EVENT_LOG_TORN`). A write that fails is cut back, so the next append starts a fresh line, and the log goes on. An fsync that fails stops the log, since its outcome is unknown, and later requests get `unavailable`. A complete line that won't decode, or whose number isn't above the line before it, is a `damaged` event at the next number. A run of numbers missing from the file is one `damaged` event at the run's last number, standing for every number after the event before it. The lines that survived keep their numbers, so a cursor still finds them, and the next append takes the number after the highest. Damage is logged (`DIAG_EVENT_LOG_DAMAGED`) and the log goes on. A `damaged` event has no payload: what it asked for is unknown.

`session_events(ws, since, limit)` returns, per session key, the events after the key's cursor `(generation, n)`, at most `limit`, from the cursor's generation up to the record's, so no generation is skipped however many started since. A cursor inside a missing run gets that run's marker. The running generation is read from memory and the others from disk, complete lines only. A generation is final, in `EventBatch.ends` with its highest number, once a later one exists or the record has ended and its log is no longer live; `more` says a page was full. Ops are enabled per workstream: `subscribe(wake, ops)` takes `ops` keyed by workstream, and a disabled op is `unsupported`. The runtime calls `wake(ws)` once a new event is logged. A wake is only a hint: a resent request wakes nothing, and a wake that fails is ignored, since the next pickup reads the log anyway.

A Stop whose hook never arrives is lost; the session's lifetime still ends it. Each generation's log is capped at 4 MiB: past that, requests get `full` and Stops are dropped. A request is one line of at most 64 KiB, so close evidence is at most 32,768 bytes; a Stop keeps the first 16,000 characters of its last message. A request still in flight when its generation is torn down is refused as `unavailable` when it tries to commit, and is never logged.

**Attaching.** An operator can watch a session with `tmux -L heterodyne-wsd attach -t wsd-<short id>`. By convention this is read-only: the pane is the agent's own terminal, so anything typed there is input to the agent.

## 6. Seams for later plans

- **Plan 4, `AgentRuntime`** (`heterodyne.wsd.runtime`): `available()`, `sessions(ws) -> [Session]` (every session that may be running, until its end is confirmed; never a partial list), `launch(LaunchSpec)` (raises `LaunchFailed` when nothing started, `RuntimeUnavailable` when nothing was attempted, anything else is treated as uncertain) and `stop(session_key)` (returns only once the session has ended). `unknown` liveness is never treated as dead. The launched-session record (`metadata.wsd_session`: role, profile, session key, repository, worktree) is written to the bead before every first launch; plan 4 may add fields. wsd never rewrites an existing record: the same five fields leave it exactly as it is, extra fields included, and different ones are escalated (`unexpected_state`). Crash-loop accounting (btq-g08sd) reads the runtime's `ended(session_key) -> Ended | None` (the latest generation's end cause, whether it reached `running`, and how long it ran) before every launch, so a bead whose session dies on every launch escalates `crash_loop` rather than relaunching without limit. `LaunchSpec.resume` is prepared identity, not launch evidence: a first pickup shelved after writing its record never launched, so the runtime must create the session when it can establish none ever existed, and hold when it can't tell. wsd counts every listed session as the coder's; before a second runtime role (a reviewer, an auxiliary session) is enabled, occupancy must be classified by role, keeping the coder's reservation across a `wsd.coder_role` rename. `heterodyne.wsd.cli` builds the runtime from `[platform] sandbox` (§5); setup does not select it.
- **Plan 5, `ActionReconciler`**: `unresolved(ws) -> [approval bead IDs]`. The default `HoldingReconciler` reports every action not `pending`, `succeeded` or `failed`, closed beads included, so the workstream stays held until plan 5 settles them. Approval beads must carry the `ws:<ws>` label and `metadata.action_state`.
- **Plans 5 and 6, parking**: `Parker.park(bead, blockers, why, hold, ref)` parks a running bead on blocking beads, or for the operator with `hold=True`. It takes the workstream's operation lock, raises `OpConflict` while another operation is open on the bead, and raises `BeadsUnavailable` when beads can't be reached; the caller keeps the request and retries after the next pickup.
- **Plan 6, release**: `Parker.release(bead, ref)` is the only way out of `held` or `stuck`. It raises `NotReleasable` for any other bead.
- **Plan 6, events**: `Journal.inbox_add` (deduplicated by surface and event ID), `inbox_pending(ws=None, surface=None)`, `inbox_failed`, `inbox_finish`; `Journal.events_since(seq)` for progress; `Journal.snapshot(ws)` for status. Triggers enter on the event loop as `await Wsd.pickup(ws, Trigger(kind, ref))` (or a `tick` through `Wsd.handle`), which runs `Wsd.pickup_one` on the workstream's lane; never `Scheduler.pickup` directly, and never a bare thread: `pickup_one` holds the workstream's operation lock while it decides whether to recover first, recovers, picks up and records the result, and leaves the workstream to be recovered again if anything raises. Once shutdown begins, `Wsd.handle` refuses everything. Correlation: triggers waiting on a lane share one pickup only if their refs are equal (or both absent); that pickup runs with the first trigger, and every caller gets its outcome. Different refs queue separate pickups, so admission is bounded per distinct ref, not overall. Before ref-bearing events use lanes, plan 6 must bound how many refs it queues per workstream, or define how joined events' refs are recorded.
- **Plan 5i, session events** (`heterodyne.wsd.session_events`): each pickup, after the lifetime stop and the signals and before the sweep, `ingest`s every event logged past the journal's cursors into the inbox (surface `session`), then `dispatch`es them.
  - **The cursor.** There is one cursor per session key in `meta` (`session_cursor:<ws>:<key>` = `<generation>:<n>`). It is committed in the same transaction as the inbox rows it covers, so ingest is lossless and ordered across crashes and journal failures: a failed page moves nothing, and the next pickup reads it again.
  - **Paging.** Pages hold `PAGE = 1024` events per key, and ingest goes on until nothing moves or no page is full.
  - **Order.** The cursor follows the log's numbers in order, not one at a time: a jump onto a `damaged` marker is taken like the next number. A cursor rolls on to the next generation once the batch marks its generation final at the cursor's number. An event read before its generation's launch has an outcome waits, and so does the rest of its key (P1). An event the journal never launched for that workstream and bead is skipped.
    <!-- TODO(review): taking a jump onto a damaged marker is the pending T6 fix; at 36200c8 `_take` reports `session_event_gap` and stops the key. -->
  - **Dispatch** runs the workstream's pending session rows in order, and a bead's rows never run out of order. A handler that raises `OpConflict` leaves the row, and the bead's later rows, for the next pickup. Any other failure counts against the row; after `wsd.inbox_attempts_before_human` failures the row is `needs_human` (`session_event_needs_human`). `BeadsUnavailable` and `RuntimeUnavailable` propagate. A kind with no handler is `rejected`. Handlers are idempotent by event ID, since a crash between a handler and its row's mark runs it again.
  - **A `damaged` row** becomes `needs_human` with `session_event_damaged` and is consumed, so its bead's later rows run (P3). If a notice client is wired (`Deps.notices`), it first sends one `stuck` notice with ref `damaged:<event_id>` and fixed text.
  - **Resolve.** `Wsd.resolve_one` ingests before the session directory is removed; if it can't, the resolve fails and is run again.
- **Plan 5i, handlers and ops:** `Deps.session_handlers` maps a kind (`stop`, `ask`, `question`, `close`) to a `SessionHandler(parker, event)`, and `Deps.inbox_attempts` comes from `wsd.inbox_attempts_before_human`. A workstream's ops are its handler kinds less `stop`. Only those get a how-to line in the brief and are accepted by the log (D6).
- **Plan 5i, the wake:** the runtime's `wake(ws)`, called from a socket thread, queues one `TURN_ENDED` pickup with no ref, which joins any queued pickup with no ref, so a burst costs at most one queued job. It is only a hint. Since it carries no ref, it satisfies the "Plan 6, events" bullet's requirement to bound how many refs are queued. `Wsd.serve` subscribes each runtime once, before any pickup.

- **Plan 5i, resume notes:** `Deps.notes` is a `ResumeNotes` (`notes_for(ws, bead) -> NoteBatch`, `notes_delivered(ws, bead, upto)`), `NoNotes` until part 2 wires one. `brief.fit(batch) -> Fitted(texts, upto, more)` picks the notes a brief carries. The D1 contract: an accepted request is a receipt, not a decision. A refusal comes later and durably, delivered by `steer` at the session's next turn boundary or, failing that, as a note on the resume brief.
- **Plan 8, backups**: `Journal.backup(dest)`.
