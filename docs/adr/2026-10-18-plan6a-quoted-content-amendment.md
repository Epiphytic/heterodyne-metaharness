# Plan6A structural card-content framing amendment

Author Codex. Proposed change to approved Plan6A D4 (btq-ns85p;05ddf59853c1c2735199897e47df9b0d825565e3), prompted by actual eighth MEDIUM code review. ONE actual HIGH design review then one incorporation and genuine human Marmot approval are required. No implementation or activation is authorized yet. Full critical findings and author response are in docs/reviews/plan6a-code-r8-*.md.

## Change and invariants

Use a fixed generated `│ ` content margin on EVERY physical line containing owner-supplied text in protected approval/question cards, including its first line, every wrapped continuation and every LF-derived line. This supersedes only D4 card layout details where owner literals share unmarked lines with generated labels. Preserve every literal character and logical LF; never silently normalize, delete, abbreviate or replace owner content to make it safe. Existing unsafe/redaction/privacy/typed-exception rules still apply and may withhold a whole protected card. The margin is additional generated framing, not part of the native authority digest or stored owner content. Genuine exact effects still use fenced source-owned syntax; fixed margin remains outside the fenced payload so byte-sensitive effects are not changed by copy/paste.

Generated headings (`Approval`, `Question`, `What`, `Effect`, `Excludes`, `Why`, `Context`, `Recommended`, choice labels, digest, answer policy and operator mention) occupy their own separate non-content physical lines. Their owner fields appear below them only inside the margin. Bead/purpose/recommended choice references use existing validated bounded typed identifiers on their generated metadata line; do not treat arbitrary field text as generated authority. Display a choice as generated `Choice yes:` then margin-prefixed literal description; display recommendations as generated `Recommended choice: yes` only for the validated actual choice. Question/answer text get fixed generated headings and margin-prefixed bodies. No user literal can begin a generated frame line because it always follows a fixed margin. The margin itself appearing inside owner content is harmless; it never removes the outer margin.

For exact-effect fences, generated `Effect:` and dynamically long generated fence delimiters remain outside the margin; each payload physical line is emitted verbatim inside the fence. The opening/closing delimiters are generated and strictly longer than every backtick run in that complete effect; existing atomic/no-wrap effect rules continue. Require a renderer model where a fenced block is literal and non-executable; clients without this admitted property withhold protected cards. An effect payload can contain text resembling labels inside the block but it cannot emit an authoritative card frame outside its generated delimiters. Existing Inline.full_text evidence is now likewise margin-framed on every LF/wrapped line, closing its previously explicit deferral without changing the complete text.

The protected layout code owns the distinction between generated metadata lines, margin-bearing content and fenced atomic effects using typed segments; do not infer it from string prefix or a post-hoc blacklist. The ordinary read surfaces remain unchanged by this amendment. Maintain Span public/syntax/template exception offsets when adding margin, splitting and wrapping; no grant crosses its original literal and generated margin is not a broad content exemption. Validate original entire literals before splitting and validate the final complete protected document again. Never construct a public/syntax exception from a user-supplied prefix.

## Bounds and completeness

Physical lines remain ≤120 codepoints INCLUDING the2-character margin. Wrap owner text at118 while preserving existing typed atomic grants; oversized atomic text withholds whole card. Respect all existing line/character/page limits (36lines, min(policy.max_chars,3200)), counting every added heading/margin/newline; if expanded layout no longer fits, withhold without a partial card. Never drop a heading or margin to fit. A complete protected card and details view retain the same stored context digest and immutable binding identity; rendering does not confer approval. No artifact/reference I/O, dispatch, Queue/Journal/DB constructor, native effect, external network or new admin command is added.
