# Fulfilled questions: release capacity without rewriting decisions (d2)

Design task: `btq-1b5km`. Author: Codex. Proposed, inactive, not implementation or deployment authority. The controller obtained one actual Claude Opus HIGH design review of d1 (`81e307fbbf4250613722119ad511f90e13d90cb8`): changes required, ten findings. This is the author's single incorporation, not a reviewer clearance. Genuine human design approval through Marmot admind remains required; no second design review or validation is requested.

## 1. Problem, evidence and source boundary

At product source `07637745fe75dc614109a0b8ba72d3489f262a97`, `store.ASK_ACTIVE` includes `open`, `answered`, `deciding`, and `uncertain`; `asks.MAX_OPEN` is 20. Both question posting and native approval posting count those rows. Thus an answered question continues consuming capacity after its authorized operation is completed. An answer proves a human response, not performance of an operation.

The controller retained private before/after evidence for two explicitly fulfilled questions. Supported cancellation released their slots, and the exact original authenticated answers survived. This was a bounded historical repair, not a general rule that answered means completed. No raw private card text, operator messages or transcript is republished here. The source map records hashes of the bounded evidence, not its contents. Do not retrospectively relabel those cancellations as a new fulfilled operation.

The isolated task branch starts at old source `2c0c5b5b775ee652d2ce32c192091aa2314e5b32`. Operative research uses immutable product076 objects; no runtime code is being changed or represented as deployed by this design. Implementation must reconcile its actual claimed source against the mapped interfaces before editing. This proposal adds an admind capability; it is not installed today.

## 2. Chosen boundary and invariants

Use an append-only fulfillment overlay owned by admind, not an additional wire status and not mutation of original decision data. A question's stored `status` remains `answered`. Fulfillment means that the exact response-bound requested operation was completed, as attested by a trusted local controller, or explicitly confirmed completed by a currently authenticated operator. It means neither approval revocation nor new consent.

The following bytes remain immutable: original ask fields, card/source identity, creation time, ordered answers (including original operator, source message ID, time, text and choice), native approval pins, completed-operation receipt and original operation history. A fulfillment receipt references these facts. It never sets an answer, rewrites `outcome`/`decided_by`, changes a Bead, reruns an operation, renews an approval, or declares an unknown effect successful.

V1 eligibility is `kind=question` or `kind=merge`, `status=answered`, at least one retained authenticated `kind=answer` row and no prior fulfillment. A completed merge must bind the original PR/head and actual terminal integration evidence; a merge answer alone proves neither merging nor deployment. Native approval asks remain excluded; native `approved` is already terminal. An empty note, delivery receipt, title, local poster string, thumbs-up without its retained authenticated source, or question choice alone cannot establish completion. Unanswered, deciding, uncertain, denied, blocked, stale, superseded and cancelled asks cannot be fulfilled. Historical cancelled-but-answered rows are not silently migrated.

## 3. Authority and operation correlation

Two explicit routes are proposed; neither runs automatically merely on answer arrival.

1. **Trusted controller completion:** one local compare-and-set application supplies a terminal operation receipt and expected ask/answer bindings. There is no persisted prepare step on this route. Extend the existing `platform.peer_pid_checked` SO_PEERCRED seam to expose checked PID/UID/GID, retaining its existing checked-PID wrapper for callers; do not add a second credential reader. Pass server-observed credentials through the protected socket's Peer context. Require UID equal the service UID; missing credentials fail closed for the new operation. Today's `ctl.Peer` exposes only PID for audit. Same-UID controllers are trusted administrators, as with the existing local control boundary: this is neither producer enrollment nor protection against a malicious same-UID process. Labels confer no authority. The receipt is a controller attestation, not independent proof of external effects.
2. **Operator confirmation:** a separate operator-intent schema requires no producer receipt, namespace or terminal-result digest. It binds the stored ask identity, all answers digest, exact consumed-answer references, requested-operation and original-authority digests, a bounded declared completion description and up to eight declared evidence references. These are explicitly declarations for a human to assess, not machine proof. Staging atomically stores the intent and an outbox confirmation notice, outside the capped ask population. The notice states the task/request, consumed response context, claimed completed work, evidence IDs, missing machine proof, and that confirmation releases capacity without authorizing execution. Use the existing redaction/secret-shape refusal rules; no raw secret or unbounded answer dump enters the notice. All decision material must fit 3,500 characters and 40 LF; otherwise refuse staging and require a narrower, truthful declaration, never truncate material facts. It includes the short ask ID, intent ID and digest for audit. The operator replies to that exact delivered notice with fixed `!fulfill`; no copying a terminal digest is needed. Resolve the reply's stored transport message ID to exactly one current intent and verify current group/principal policy. Never accept an unbound command, reaction, title match, pasted operator name or terminal consent. Duplicate replies return the original receipt. A notice is not a new ask or original answer; it cannot itself execute work. Outbox delivery IDs and exact notice digest are retained with the intent; partial/unknown delivery cannot be treated as authenticated confirmation. Marmot unavailability leaves diagnosis and later recovery, never an alternative human-consent channel.

Controller receipts use closed schema `operation-completion-v1`: operation ID (1–128 ASCII `[A-Za-z0-9._:-]`), producer namespace (1–64 same grammar), exact ask identity, consumed-answer digest/references, requested-operation and original-authority digests, `state=completed`, terminal result digest and at most eight immutable evidence references. Separate a shared operation core (namespace/ID, requested operation, authority, terminal result) from each ask-specific binding. One operation may fulfill several genuinely bound asks; its shared core digest must agree across applications. Evidence references are opaque registered artifact IDs (1–128 same grammar) plus SHA256, never a daemon file path, URL fetch, command or database expression. The actual producer adapter validates bounded regular-file bytes beneath its admitted receipt root, rejecting symlinks/traversal, before sending the attestation. Admind performs no arbitrary artifact reads, subprocess or network verification in its transaction. Pin the actual producer's schema and adapter in implementation evidence; no installed receipt API is asserted. Operator-only fulfillment uses a server-created stable intent ID in namespace `operator-confirmation`, not an invented producer receipt.

A producer may have a terminal receipt for a completed denial/no-op decision. Its requested-operation digest must explicitly identify that disposition, not an omitted side effect. A partial operation, operation-issued marker, timeout, transport success, shell exit without required readback, or uncertain outcome is not `completed`. For existing workflows without a machine-correlated receipt, use operator confirmation of an exact staged intent and declared evidence; do not manufacture a receipt adapter or auto-complete. Both routes preserve the distinction between operator response and operation completion.

The caller must identify which exact retained answer(s) its existing policy consumed. Multiple/conflicting answers are not resolved by this endpoint. Its full ordered-answer digest is a concurrency fence; a newly arrived answer invalidates the prepared intent. Existing operation policy remains responsible for whether the consumed answer was authorized. Fulfillment cannot make an invalid operation valid or repair missing historical consent.

## 4. Canonical identities and proposed API

Add a durable random `ask_store_id` to admind metadata exactly once, transactionally, with no invented historical ask identity. Existing database backup/restore must retain it. The logical replay key is stable `{ask_store_id, ask_id}`; enforce `UNIQUE(ask_id)` within this Store. Bind each receipt additionally to `{created_at, ask_sha256}` as checked content, never as an alternative unique key. Encoding upgrades must retain the original encoding/version and validate old receipts with that version; they cannot create another receipt for the same ask. Canonical ask bytes include kind, poster, title, body, PR/head, bead/digest, form/choices/links and original creation time using a versioned deterministic JSON encoding. Exclude mutable status/activity/delivery observations. The separate canonical ordered-answer digest includes all retained answer row fields and sequence; do not normalize original timestamps or text. Digests are SHA256 over canonical UTF-8 bytes with a domain/version prefix. Publish the exact encoding and golden fixtures in implementation; do not hash an unversioned display string.

Proposed commands and wire operations, not current commands:

- `admind ask fulfillment apply --receipt FILE --json`: one trusted-controller compare-and-set request containing the receipt and exact expected ask/all-answers digests, expected fulfillment=null. It neither stages a pending intent nor sends a confirmation notice. An identical retry queries/returns the durable receipt; no successful after-state, operator identity or UID may be supplied by the client.
- `admind ask fulfillment propose --ask ID --declaration FILE --json`: operator route only. It returns exact canonical intent/digest and pending notice state; insertion and outbox enqueue are atomic. Matching pending bytes reuse the existing intent/notice. It changes no capacity until an authenticated reply confirms completion.
- `admind ask fulfillment dispose --ask ID --expect-intent SHA256 --json`: trusted local administrative metadata operation atomically retires exactly that pending intent with fixed reason `operator-withdrawal`, `stale-answers`, or `expired`; it cannot dispose an applied receipt or erase an answer. Audit and notice-message association tombstones survive. `propose --replace-intent SHA256` explicitly retires that exact pending predecessor and creates a fresh intent/notice atomically; it cannot silently reuse an earlier operator reply.
- `admind ask fulfillment get ID --json`: opt-in diagnostic lifecycle view, original bindings, receipt/null, pending state and capacity/conflict projection. Missing state is not completion proof.
- `admind ask fulfillment reconcile --receipts MANIFEST --limit N --plan|--apply --json`: bounded local receipt reconciliation below, never external operation execution.

FILE readers use no-follow service-user-owned regular files, maximum 24KiB; wire requests must independently fit 64KiB after complete encoding, replies 128KiB, within existing 262144-byte/1MiB outer bounds. Oversized encoded requests refuse without truncation. Closed schemas reject duplicate keys, unknown fields, NaN, non-UTF8, recursive/unbounded objects and overlong integers/strings. Limit labels to 512 characters and references to eight. Operator intents bind schema, stable store/ask ID, ask/answers digests, declaration digest, expected fulfillment=null, route and server intent ID; all fields enter the digest. Controller requests bind the analogous receipt fields without requiring a staged intent. There is no arbitrary status setter.

Use a dedicated tagged fulfillment request union and reply namespace inside the existing protected local socket, with strict dispatch and explicit client opt-in. Unknown operations on old servers fail visibly before changing state. Do not append fields to the existing `AskView`, `AskSummary` or `AskReply` without a separate negotiated version: old strict DTO consumers may reject them. The CLI's old post/get/wait/list/cancel output schema remains unchanged.

## 5. Atomic application, audit and idempotency

Use only the existing Store transaction discipline (`RLock`, `BEGIN IMMEDIATE`, no await). Do not acquire daemon `work_lock` or `ask_post_lock`: the worker holds the former across long awaits, while fulfillment only lowers capacity and does not post an ask. Bound SQLite busy waiting to five seconds for this operation; return a fixed unavailable outcome without changing state on lock failure. Validate size, peer credentials and receipt shape before entry, then re-read ask, complete answers, current fulfillment and (operator route only) exact current pending intent/notice association inside the transaction. In `answer_ask`, move the authoritative refusal/status, fulfillment and answer-total checks inside the same transaction as add_answer/set_ask; an earlier check is only advisory. Also make cancel, same-bead supersession and other status writers enforce the overlay inside their Store transaction. Principal policy must be current at operator commit; no await or external I/O is inserted into the transaction. Posting retains its existing serialization and rechecks; a concurrent fulfillment cannot increase the count or make an accepted post exceed the cap.

One transaction inserts the unique immutable fulfillment row, consumes its pending intent if operator-confirmed, inserts an immutable authority/before-after audit record, and queues at most one redacted fulfillment notice via the existing durable outbox. The authoritative audit record lives in the same Store transaction; the existing external audit log is a supplemental mirror. A failure to mirror after commit must not undo or repeat the terminal operation. Store audit records never include raw answer text, raw receipt bodies, secret tokens or arbitrary paths.

Receipt fields: schema, ask identity/digests, original `answered` status and original-answer count/digest, operation identity and controller-receipt digest or operator-declaration digest (a tagged union, never a fabricated receipt), route, server-observed UID/PID or verified operator source-message/principal identity, prior fulfillment=null, resulting lifecycle=`fulfilled`, before/after active-count observations, created UTC, canonical application-request or operator-intent digest, and durable receipt ID. The count observations describe the transaction, not a permanent global count. Completed operation bytes remain with their original owner; admind retains its bounded digest-bound attestation and evidence IDs.

Enforce stable ask uniqueness as above and `(producer namespace, operation ID, ask_id)`, checking the shared operation core digest for reuse across asks. Different ask-specific bindings are allowed only when each independently matches its ask/answers; differing shared operation cores refuse conflict. An exact duplicate returns the same receipt with `already-applied`; a differing receipt for the same ask refuses `conflict`, without another notice. Operator keys use the stable server intent ID and ask ID, with no fabricated machine operation identity. Unknown socket response: query fulfillment by exact ask identity; identical receipt means committed, absence permits retry of the identical controller request (or re-delivery of the identical authenticated confirmation), mismatch holds. Retry only the metadata commit, never the external operation. Crash before commit leaves no fulfilled projection; crash after commit leaves the receipt and outbox intent together. A new answer versus apply race is serialized: if answer commits first, apply refuses stale; if fulfillment commits first, subsequent answer/reaction is refused with “already fulfilled; original answer retained,” not appended or made active again.

## 6. Capacity, listings, repeat and consumer compatibility

Keep the existing ten wire status values and their meanings (four active plus six terminal). Define a separate query `capacity_active`: an original active status without a currently valid fulfillment, OR a retained fulfillment conflict. A valid fulfillment requires original `answered` status and exact stored ask/answer bindings; mere row existence is insufficient. During startup/roll-forward, rebuild a fulfillment-binding validity index before serving posts or lifecycle projections, comparing actual retained asks and ordered answers. Every new-code answer/status mutation atomically maintains or invalidates that index. This permits an indexed anti-join for routine reads without hashing all answers per list. A mismatch is a diagnostic `conflict`, never receipt replacement: it remains capacity-active even if old code cancelled/superseded the ask. Do not fabricate an original status or answer. Resolution preserves both histories and requires investigation plus a genuinely new request where needed; this endpoint cannot overwrite the old receipt to hide new instructions. Both post_ask and approval_post_refusal, their post-await rechecks, list grouping, in-flight counts, reminders, `!asks`, summary generation and scheduling queries must use this projection consistently. No per-row N+1 reads: indexed anti-join/NOT EXISTS on the receipt key. Native `deciding`/`uncertain` busy guards remain unchanged and can never be hidden by an ineligible fulfillment. MAX_OPEN20, MAX_PER_HOUR30 and MAX_IN_FLIGHT2 remain unchanged; fulfillment is not a new ask and does not refund the hourly post budget.

Original `get` returns `status=answered` and byte-identical answer fields after fulfillment; it is a response/authority history API, not a capacity query. Old `list` keeps its exact DTO and returns capacity-active plus20 newest inactive-or-fulfilled entries, with each ask once. A fulfilled entry has original `answered` status; this deliberate limitation is explained in CLI help. The new lifecycle command and human `!asks` line show `fulfilled` explicitly as a lifecycle label separate from wire status. Existing original status selectors used to inspect historical answers must retain raw-status semantics; add a distinct query for capacity rather than silently changing every `asks_with_status` call.

`!details`/explicit history lookup continue showing original card and response, plus a clearly separate fulfillment label/receipt ID in lifecycle-aware rendering. `!asks repeat`, automatic bumps and outstanding reminders exclude fulfilled asks. Explicit resend of an original fulfilled card is diagnostic only, labelled “fulfilled; no new answer or authority”; no active ask, new decision, operation or hourly-post reset is created. Same-bead `commit_approval` supersession must skip valid fulfilled asks inside its transaction, irrespective of kind; no superseded notice is queued for them. A retained conflict is not silently retired by supersession. Current cancel refuses a fulfilled ask with a fixed explanation and receipt reference, preserving the receipt; never erase fulfillment via cancellation. Reopening requires a genuinely new request under ordinary policy, not deletion of the old receipt.

Consumer activation is an implementation acceptance boundary: inventory exact current wake/status parsers, Handoff/manage, supervisor and read consumers before rollout. Existing product clients continue accepting their current statuses without adding `fulfilled` as an unrecognized status. A wake bound to a completed operation must first check its own terminal operation receipt; the new lifecycle reader can suppress redundant wake work only after full identity matching. Legacy clients may still see `answered` and wake; that cannot authorize reexecution because original operation idempotency/readback gates remain mandatory. Where that property is absent, update and review the actual consumer before enabling automatic fulfillment for its producer. An unsupported producer stays manual; do not globally block unrelated eligible producers or infer a new response from lifecycle metadata.

The separate wake design at `59ffe75c32932b60597fd2c43a945a98e383957a` is a design contract, not evidence of an installed consumer. Its nine-row status table omits product `uncertain`; its unknown-status rule already holds observation without inferring resolution. The fulfillment adapter must preserve that fail-closed treatment: `uncertain` remains HOLD and capacity-active, never terminal or fulfilled. No wake design byte, enum or review requirement is changed here. Fulfillment preserves `answered` and all original answer bytes, so lifecycle metadata alone must not become a new answer fingerprint or wake authority. Record exact consumer compatibility in implementation evidence; core manual fulfillment does not depend on deploying the bridge.

## 7. Bounded reconciliation and recovery

No timer scans all answered questions and declares success. Reconciliation is a supported explicit local command using a caller-supplied bounded manifest of terminal operation receipts, default plan mode. N is1–20, manifest at most256KiB, maximum20 distinct asks and one exact application request per ask. It fetches the opt-in exact lifecycle view, validates receipt bindings, and emits one typed result per ask: `eligible`, `already-applied`, `stale`, `unsupported`, `incomplete`, `conflict`, or `unavailable`. A plan is not permission to execute the requested operation. Apply revalidates independently and runs one atomic metadata application at a time. Return partial outcomes and a stable continuation key; no automatic replay after uncertain response. Failure of one entry does not imply success of unprocessed entries. No general claimant impersonation or task status/dep modification is included.

Only the operator route has pending intents: cap40 current intents total, one per stable ask, max24KiB canonical intent each. This also bounds active confirmation notices and avoids a capacity-independent spam lane; identical requests do not enqueue another notice. At full40, trusted controller apply/get/dispose remain available. After24h an intent becomes non-confirmable but its digest/declaration and delivered-message tombstone remain retained; it is not silently erased during an outage. Explicit dispose or replace retires its current slot transactionally. Replacement always sends a new bound notice and leaves old replies stale. Admission/cleanup and expiry checks are transactional. An outage beyond24h requires explicit refresh after checking current answers, not a replay of an old confirmation. Trusted controller apply has no pending-intent dependency, so a full or stale staging population cannot lock routine attested completion. A receipt-less operator proposal is a new independently declared route, not a route field change that would reuse a controller signature.

Trusted local metadata application remains available at the20-active cap and while posting is latched, analogous to local cancellation. Operator confirmation requires current inbound authorization and its actual latch/trust gates; no bypass. Confirmation notices use existing durable outbox handling but do not create a capped ask. If delivery/authentication is unavailable, retain pending/tombstone state and diagnose. No unsolicited new external question is required to finish trusted known work.

If an operation has unknown effects, keep its question active; reconcile the actual operation through its existing supported recovery path. Do not retry the operation to obtain nicer evidence. If a historical receipt is missing, use explicit authenticated operator confirmation of a digest-bound intent after actual investigation, or retain hold. Store corruption/loss freezes metadata application; restore the exact supported backup/catalog and original store identity before interpretation. Missing state is not negative proof, and does not permit ask-ID reuse or bulk completion.

## 8. Storage, migration and rollback

Use admind's existing Store, outbox, authenticated inbound messages and answer rows, not a second daemon or standalone completion database. Proposed additive tables: `ask_fulfillments` (stable unique ask ID, checked versioned bindings, operation/ask key and immutable bounded receipt), `ask_fulfillment_intents` (bounded pending canonical bytes and state), and `ask_fulfillment_audit` (transactional bounded metadata per attempt/disposition). Add store identity/schema capability metadata and indexes. The exact DDL and migration guard must be reviewed with implementation. No backfill of old answered/cancelled rows. Migration must run before serving; failed migration leaves the old state intact and startup fails visibly. Read-only tools must not instantiate the mutating Store constructor to inspect a backup.

Retain fulfillment rows, identities and replay keys as long as their original asks remain retained; no deletion by age. Existing asks are not automatically pruned, so v1 does not claim bounded lifetime disk usage. Cap pending bytes as above; cap supplemental retry-audit entries per intent at8 with exact aggregate count and last fixed failure code thereafter. One authoritative immutable fulfillment record and one application audit always survive. Capacity-exhausted disk/Store errors refuse mutation and preserve evidence; a reviewed archive policy with immutable digest lookup is required before pruning replay keys. Do not silently rotate away authority to meet a storage number.

Deployment is a separate Marmot ask linking the approved design, reviewed source and deviations. Snapshot database coherently with its supported backup mechanism, code/config/schema capability and consumer versions; WAL is not a standalone database backup. Test restoration offline. Rollback stops the new writer, preserves the complete database and receipts, and restores reviewed old code/config: old code sees original answered rows and may again count them toward20. It can append answers, cancel or supersede those rows because it does not understand fulfillment; retain all such genuine later history. Roll-forward must rebuild and check the binding-validity index before serving, marking any changed answer/ask/status as a capacity-active conflict rather than hiding it under an old receipt. This cannot grant new consent or erase the earlier completion. Do not restore an older database over later genuine answers/operations to regain capacity. Continued old operation may require manual hold for capacity; forward repair is safer. No timers, run/session/native task identity or deployment are changed by this design filing.

Use named offline tests with temporary Store/files and fake Marmot/native/executor adapters; no live sender, service or model. Cover:

- Wrong ask/store/creation/body/answers/operation/authority/evidence digest; two answers/conflict; stale answer race; unknown/partial effects; missing/forged receipt; one shared operation completing two independently bound asks; conflicting shared core rejected; receipt-less operator proposal and no invented machine receipt; no arbitrary paths/symlinks or command execution.
- UID verification failure and wrong UID refused before mutation; labels never authenticate; real fake-transport inbound policy checks for operator confirmation, revoked principal, duplicate message and wrong/replaced notice binding. The exact readable confirmation notice must work at20 active asks without terminal digest copying. No terminal path can manufacture human consent.
- Atomic crash points before/after insert/audit/outbox and response loss; exact retry same receipt/no second notice; conflicting duplicate; audit mirror failure after commit; read-only query cannot change state; no external operation replay.

## 10. Human design decision and implementation sequence

The governing relay specification at product076, `docs/superpowers/specs/2026-10-05-admind-marmot-relay-design.md`, currently defines R15 active capacity directly by four statuses and R24 listing by active status. Human approval must explicitly amend those clauses to the separate fulfillment-aware capacity projection while preserving all numeric limits. It must also approve the narrow R13 qualification refusing additional answers after fulfillment, the new local trusted completion route with R16 residual trust disclosure, and the R17 local metadata-recovery exception described above. Native approval semantics R5–R12 and decision-attempt recovery R23/R26 are unchanged. These are proposed amendments in this same design decision, not a claim of existing authority or a redundant later approval layer.


The Marmot design ask must explicitly adopt: the fulfillment overlay instead of an additional wire status; original answers/status retained; routine trusted same-UID completion attestation with honest residual trust; opt-in new lifecycle API and unchanged old DTO; exact operation correlation and no execution inference; optional authenticated capacity-independent operator completion verb; question and merge eligibility with actual completion evidence; bounded manual reconciliation, explicit pending dispose/refresh and retained tombstones; producer-specific compatibility gate; and rollback's possible return of capacity pressure without loss of history. Approval authorizes implementation only, not runtime mutation, receipt migration, automatic scans, deployment or completion of particular historical requests.

Implement one coherent product task for schema/endpoint/CLI/operator verb/projections/tests. A concrete controller producer adapter and affected wake consumer belong in their actual repository task(s), each pinned to this design and exact real source; do not invent native target IDs or bundle unrelated Plan6/7/8 features. Land disabled capability first, review source under current operator code policy, prove offline compatibility, then request separate deployment with exact activated producers. No dependency on future Plan5/6 is required to implement the core manual/attested lifecycle. Existing future delivery/retention designs must reconcile their definition of active/settled before co-activation; this proposal does not silently amend their storage or consent contracts.
