## 1. Scope and sequencing decision

This slice admits a future native ingress adapter and bounded read-query service for wsd: normalize authenticated Marmot messages, verify registration and fresh policy, persist replay and query-response mappings, project authoritative observations into the separately approved Plan6A presentation schema, and answer `/workstreams`, `/status`, `/status <bead>`, `/approvals`, `/queue [ws]`. Reading Beads never claims work or mutates it. Local ingress/cache/response journals are derived communication state, not task or approval authority.

The roadmap's full Plan6 predecessor remains Plan5 plus S4. The proposed **new human sequencing decision** is narrower: after compatible Plan6A is genuinely approved and implemented, permit standalone read-only 6B implementation and offline acceptance before complete Plan5. This exception does not permit starting a consumer, sending a message, deploying a service or claiming Plan6 complete. A later exact deployment approval must separately admit any early read-only live rollout and disclose the incomplete predecessor. If the operator does not approve that explicit exception, implementation waits for the full predecessor. This document does not decide the exception on the operator's behalf.

Excluded: unthreaded task intake, steering, approval/question answers, any Plan5 decision port or writer, task/label/dependency/status changes, claims, release/pause/resume/trust-group handlers, managed-install commands, membership/invite/repost operations, task/approval/question card creation or mirroring, reminder/digest scheduling, timers, consumer startup/cutover, gatekeeper changes, installation, deployment and live acceptance. Existing admind questions/approvals remain exclusively through authenticated Marmot and its native flow. No terminal/chat approval substitute exists.

The existing btq-rd4z5 invite-recovery scope, held btq-qrljq managed-install routing and btq-56v6h wording work remain separate. Plan5/e7knb owns the sole decision-writer/executor protocol; 6A/0bkbo owns pure presentation; later 6C owns full card outbox/mirroring/join visibility/reminders; later mutation integration owns command cutover. These are ownership boundaries, not new task admissions.

## 3. Verified transport and source boundaries

At source 076, `marmot/control.py` implements strict `marmot.agent-control.v2` NDJSON with a 1 MiB frame limit. Subscription ACK precedes serving events. Authenticated inbound message fields include native account/group/sender, self flag, message ID, text, timestamp and reply target. Reactions can lack an event ID; group-state events have none. `group_info` proves the returned group/count, not an identity census. `send_final` returns a list of message IDs. No history replay, unknown-send readback, native deduplication lifetime, group-ID universal fixed length or canonical multipart root is established. These limitations are contractual, not imagined transport features.

Source 076's `Journal` is **not** a read capability: construction creates missing files, its working connection switches WAL, and `snapshot`/`usage_cache` use `BEGIN IMMEDIATE`. `wsd.btq.factory` constructs the general queue. The pinned queue constructor reads write-capable credentials and can mkdir even when a caller wants a read; `make_state=False` alone does not solve credentials or `bd`'s 20-second timeout. `ready --limit 0` is unbounded and hides paused queues. No read component constructs these objects, invokes these helpers, uses their environment, or parses display strings from `Wsd.status`.

The scheduler's `_candidates` first considers resumable/overdue rows, then new ready rows, skipping/gating candidates and honoring pause only for new claims. A native ready list is not the next actual pickup order. Calling the scheduler to discover order would mutate state. This design therefore requires a separate read-only candidate observation described below; it never presents a native ready list as a guaranteed launch prediction.

## 4. Restricted producer and closed read contract

The proposed consumer receives four query capabilities: subscribe to its configured native route; `ReadProjectionPort.read(ReadRequest)`; its own derived journal; and a response-only native send wrapper. It also receives one separate, closed safety capability: SafetyAlertPort may request a single fixed trust/capacity notice through existing admind NoticePost. That capability has no caller-supplied text, route or effect opcode; it accepts only a persisted local safety reason and bounded correlation reference. It does not send through the response wrapper or post general cards. It cannot import executor/Parker/decision writer/managed-install/general queue or general CtlRequest dispatch. These are new proposed interfaces, not installed APIs. Python capabilities assume a trusted service user and do not claim hostile same-user confinement.

The proposed source producer is a bounded read handler in the already running source owner. It opens a **separate owner-controlled SQLite mode=ro connection**, with query_only enabled, for parameterized SELECTs in bounded deferred read transactions. It never uses the shared Journal.db connection or its RLock, Journal.transaction, a new Journal constructor, new runtime indexes, or a scheduler tick. The separate connection observes committed snapshots only; short read transactions and busy/statement deadlines fit the source budget. Ordinary SQLite WAL coordination can touch owner-controlled -shm and empty -wal sidecars; this is explicitly permitted coordination, not authoritative row/schema mutation. It must not switch journal mode, checkpoint or auto-migrate. Real disposable WAL/concurrent-writer fixtures must prove this exact behavior and no scheduler lock contention. It does not start the owner. Its private IPC checks socket owner/mode and peer identity and binds exact configured producer/release/run/boot. Consumer imports must not initialize source state. When the owner is absent the journal-derived source is unavailable; early read implementation remains useful offline and native-only sections may remain available. A standalone live consumer cannot start pickup, reconciliation, timers or action executors to obtain data.

Native reads require a new fixed-operation bounded adapter under this same proposed contract. It must use an explicitly provisioned read-only native account, fixed repository/server binding and a bounded process wrapper; it does not construct Queue or load wsd writer credentials. No caller supplies argv, SQL, credential path or repository. Provisioning of the real read role/transport and its tested operation shapes is a deployment prerequisite, not a claim that the role exists now. Read wrappers cap decoded bytes (256 KiB), item counts (100 per collection), at most four fixed native bulk operations per projection, and elapsed time, kill/join their own process group on timeout, and include cleanup in the five-second aggregate source budget. No unbounded native enumeration or in-process cancellation of an uninterruptible queue call is permitted. Missing supported count/order/limit contracts produce explicit unavailable sections while adapters are completed; adding a fixed nonmutating adapter within these bounds is implementation work, not a new design permission cycle. Native source effects or credential privileges beyond this contract require a reviewed design amendment. If actual source architecture cannot provide this isolation, early live use stays disabled pending that integration design and its genuine approval. A design is not implementation authorization: native design admission and later code review remain mandatory. Ordinary implementation details within an actually approved contract do not require separate approval per function; historical personal Claude rules do not supersede the current operator instructions.

### 4.1 Versioned records and collection accounting

Immutable version 1 records reject extra fields and unknown tags. Before JSON allocation the projection IPC rejects frames over 256 KiB; after bounded decode it enforces field/type/count limits. This differs from native ingress: native text is already decoded inside its 1 MiB frame before the stricter text check (§5). Safe display labels follow compatible 6A rules; internal IDs never render automatically.

`ReadSelector` is Workstreams, Status, BeadStatus(safe bead label), Approvals, Queue or QueueFor(safe workstream label). Request fields are version, selector, locally generated request_id (1–128 ASCII bytes), and owner-supplied scope. Scope fields are surface(workstream/control), route(account/group), registration_epoch(u64), 1–100 WorkstreamBinding(name, routing_agent, queue_identity, repository_identity), and ProducerBinding(name, release_commit (40 hex), run_id, boot_id). Workstream surfaces have exactly one binding; control surfaces list only registered bindings. Safe workstream names are unique within a route and resolve to exactly one full binding; conflicting same-name agent/queue bindings are rejected at registration rather than guessed at query time. routing_agent is an exact configured queue agent. Queue identity resolves to the exact native database/server/repository binding, never a display label alone. Opaque identities are 1–128 ASCII bytes, not paths. Input text cannot set scope or producer. Define ContentScope as surface, route, registration_epoch and sorted WorkstreamBindings only. Its digest **excludes ProducerBinding and every release/run/boot/generation value**. Full request scope additionally carries ProducerBinding for fresh-read authentication; cached historical envelopes retain their original producer binding and are not relabeled as current.

Result is Available(envelope), Unavailable(source-unreachable|source-budget|missing-data|ordering-unproven|producer-restarted), Rejected(invalid-request|scope-mismatch|ambiguous-selector|not-found|invalid-source|generation-regression), Busy, or NeedsDetails(envelope-budget). NeedsDetails has only a fixed narrow-query meaning and no source text. All not-found/out-of-scope responses use identical fixed wording. Errors contain no raw source values. Timeout never becomes an empty result.

Envelope fields: version, request_id, selector, scope, positive generation, capture_started_ns, capture_finished_ns, observed_at UTC, 1–1024 SourceObservation rows, and compatible 6A view. Generation is increasing only inside an exact producer boot/run; capture_finish >= capture_start. Each observation has origin(native-beads|wsd-journal|account-usage-journal|host-config), workstream(nullable only for shared configuration/account facts), **collection**(configuration|state|holds|running|approvals|candidates|recent-events|usage), observed_at, availability(reachable|cached-unreachable|unavailable), completeness(complete|incomplete|unavailable), and shown/total. Identity is `(origin,workstream,collection)`; duplicates reject. A selector has at most eight collections per workstream plus shared observations; the 1024 cap bounds observation metadata for 100 bindings; it does **not** promise that full data for 100 workstreams fits the 256 KiB frame. The producer builds bounded per-workstream summaries first, then deterministically allocates row space in registered workstream order without splitting a required row. It can return honest incomplete per-collection counts only with verified totals, preserving section labels and omitted counts. If even the minimal registered summary cannot fit, return a fixed narrow-query/NeedsDetails outcome, never silently drop bindings or imply a full inventory. `/queue <ws>` and workstream `/status` remain ways to request details; a large control response is not promised a full dump. Counts are independent per collection; scalars/unavailable have null counts, enumerated available collections have actual verified nonnegative totals and shown <= total. Unknown totals cannot become an honest truncated count.

No projection performs a per-row design_approval show loop or reimplements Queue.design_allowed as authoritative eligibility. The native adapter must use a bounded fixed bulk read shape; reuse of a future limited read-only btq command requires its own reviewed implementation and real native effect tests. Candidate rows may carry eligibility unknown, explicitly not runnable; a missing batch approval proof cannot trigger N+1 native calls. No atomic snapshot across stores is promised. Every section preserves its own observation time and provenance. Complete is allowed only if every required section is complete/reachable. Unavailable optional sections are explicit unknowns; they cannot turn into empty lists, zeros or inferred approvals. Projection validation verifies producer/scope binding independently of display labels.

## 5. Registration, trust recovery and authentication

A proposed supported operator configuration schema, `marmot_read` version 1, contains enabled (default false), a private journal identity/path, producer endpoint/binding, finite routes, and bounded policy/cache settings only. Each route binds account (64 hex), group (even hex, 1–256 bytes), kind, 1–100 permitted workstream bindings, positive registration epoch, trusted initial group/count baseline and recovery owner. Reject duplicate/conflicting routes and **any route whose normalized (account, group) pair equals admind's own pair**, before startup. Reusing the same local account for a distinct group is allowed; reusing the admind group with another account is also refused to avoid routing overlap. No second identity or invite is implicitly required. Shared wn-agent transport remains one owner, with subscriptions partitioned by exact account/group pair and local replay namespace; no second MLS-home opener. Account IDs are exactly 32-byte public keys at this pinned protocol, as are sender/message/reaction target IDs; there is no loose account fallback. Group length is a local resource limit, not an assertion of universal native length.

Configuration is installed through a proposed supported `wsd-read-config` operator script: `validate`, `plan`, and `apply --expect-digest=...` publish a canonical private config atomically after exact before/after validation. It manages read configuration only, never task/approval/member state. This is planned implementation under 6B, **not an installed command today**, and personal CLAUDE.md preferences do not authorize terminal file surgery. Genuine approvals and questions remain exclusively Marmot; script execution consumes an already recorded approved deployment/recovery instruction and does not create approval evidence. No group creation, invite or automatic baseline adoption is included.

Trust recovery is a local operator action, not an inbound query effect or Plan5 decision execution. The proposed config script has a separate `recovery-plan` command that durably stores canonical old/new registration, exact old hold digest, request digest and full request bytes before asking anything. It does not clear a hold. The controller posts the exact bounded recovery question through the **existing** private admind AskPost interface; title contains the full 64-hex request digest, form yes-no, recommended yes, and body names the precise effect. It retains exact returned ask ID plus original request and response. If posting is uncertain, existing admind list/get can locate candidates but cannot authenticate a candidate by title alone. Adoption requires the owner-side full-request association proof described below; without it the operation remains held, with no blind repost or fabricated ID. The controller—not the read consumer—operates this question workflow. No new Plan5 writer or generic decision import is introduced.

`recovery-apply --expect-digest=... --ask-id=...` reads existing **AskGet** over the configured private admind socket (owner/mode/peer verified), checks the stored request/id/title binding, summary.kind=question, summary.delivered=true, summary.status=answered, and exactly one answers entry with kind=answer and choice=yes, with no other answer or note. These field names are actual AskSummary/AnswerView fields; asks.summary returns row.title unchanged and asks.map_reply maps yes/y to choice=yes. Reject free text, contradictory/multiple answers and any changed request or title. Current principal authorization needs the additional owner proof described next; an operator name alone is insufficient. AskView omits the original body: therefore an arbitrary user-supplied ask ID is insufficient; only the script's retained exact request/post receipt with matching full digest title is eligible. It records original AskView bytes/hash and before/after registration audit. A generic approval title, free text, native approval display row, digest-only authored file or cached decision cannot authorize recovery. Current admind response integrity relies on its private trusted local service, not an invented signed API. **Remaining explicit compatibility prerequisite:** AskView exposes operator name but not authenticated sender key or a current-principal proof. Existing daemon.sender_current(mid)/authorised(mid) can check retained inbound provenance against fresh policy intersected with confirmed keys, but no current AskGet field invokes/exports that proof. Therefore stock AskPost/Get is necessary yet insufficient for automatic recovery apply after policy/rekey changes. Recovery apply must HOLD unless a separately reviewed, narrowly read-only admind owner adapter binds the exact retained answer to its real sender and verifies that sender is current at apply; it must also verify the retained full post request/body association. Do not invent those as existing response fields or infer them from title alone. The compatible adapter is a deployment prerequisite with named disposable fixtures, not Plan5 writer execution or permission per function. If retained owner provenance has been pruned, HOLD for an actual fresh recovery question; no authored proof file substitutes. Offline fixtures must prove real AskPost/Get shapes, exact affirmative interpretation, bodyless-reply limitations, current-principal adapter denial, and refusal on missing retained post provenance. The script then atomically advances the registration epoch only; the old epoch remains held/history intact. New epoch serving still requires ACK/group_info. This is explicitly proposed supported configuration recovery within the design, not an installed endpoint or automatic Plan5 executor. Deployment requires the implemented mechanism and genuine recovery authority; a normal source edit does not create a new approval need.

Membership/admin/identity change or count mismatch durably holds only the affected route and stops disclosure there. Closed hold reasons are membership-change, admin-change, identity-change, count-mismatch, unknown-group-change and protocol-conflict; arbitrary native change strings map to unknown-group-change and never become storage keys. Repeated events coalesce by route epoch plus this enum. Create a bounded safety-alert record; SafetyAlertPort requests a fixed notice through the **existing admind NoticePost owner**, which owns native delivery to its admin group. Thus the consumer has no unsolicited group-send or general 6C card capability. Notices identify only safe configured labels and the fixed recovery instruction; no inbound text/keys or caller-selected destination. If admind is absent, retain one pending alert per route/reason and expose it through the proposed local `wsd-read-config doctor`; do not retry an uncertain post. This minimum safety notification is an explicit exception to “only query responses,” not general card mirroring. The separate operator workflow uses actual admind to obtain recovery decisions. During an admind outage reads remain safely held until it returns; local doctor diagnoses without pretending local text is consent. A new baseline cannot be adopted from first count, reconnect or matching count alone.

Before reservation, validate current route registration, a fresh uniquely normalized Policy.approvers key, not-self, exact account/group binding and native message provenance. Reservation may enter waiting-auth when subscription/group proof needs refresh. Before disclosure and after every await/before every part, recheck these facts plus current subscription ACK and successful same-generation group_info matching baseline. No stale authority cache. Group observations expire after 30 monotonic seconds. A stale observation creates **waiting-auth**, coalesces a check within a five-second auth lifetime (connect/read/cancel/join included, overriding the native client's 30-second default) and resumes the same query on success; it is not immediately terminally suppressed. Definite revocation/hold/scope change is suppressed terminally; timeout/unreachable becomes auth-unavailable terminally with no reply, allowing a new explicit query later. On an idle route the first valid query can wait for this bounded check rather than always disappearing. Disclosure still requires fresh authorization.

Native frames have already been decoded within 1 MiB before text validation; do not claim otherwise. Text limit is 4096 Unicode code points (therefore at most 16 KiB valid UTF-8), plus compatible 6A control/format refusal. Invalid types/IDs/version reject before grammar handling. Native timestamps are observations, never local freshness authority. No identity census is invented from counts, and unchanged-count swaps by privileged local actors remain the ADR residual risk.

## 6. Grammar and response policy

The compatible 6A classifier parses the entire trimmed single-line, case-sensitive ASCII-space grammar. Workstream groups can read only their one binding. Control groups can read only explicitly registered bindings; `/queue <ws>` resolves no hidden binding. `/workstreams`, `/status`, `/status <bead>`, `/approvals`, `/queue`, `/queue <ws>` map only to their corresponding 6A read views. Threading under any same-group message adds context but no authority. Safe transcript locations are configured labels/links, never file reads or raw session IDs. The producer creates a **scoped DTO before handing it to the renderer**; it never sends a global snapshot for later redaction. Query results never contain another requester's source text. Every adopted row is bound to its configured agent/workstream/queue/repository; neither output order nor redaction can repair a scope failure.

| Query | Workstream surface | Control surface |
| --- | --- | --- |
| `/workstreams` | Its one registered workstream | Registered workstream summaries only |
| `/status` | Own state, holds and optional account/running facts | Registered aggregate, open approvals and needs-human summary, with unknown sections explicit |

Authenticated mutation commands **must** receive a fixed unsupported/no-action notice, subject to bounded admission/rate limits and the same authorization checks; no positive acknowledgement. Malformed/unknown slash forms receive fixed usage; nonexistent/out-of-scope targets identical fixed not-found. Ordinary text and reactions cause no query and no reply. No input reaches an LLM, writer, queue mutation, card answer, membership API or scheduler.

## 7. Separate journal, bounded replay and complete state machine

Create a **separate 6B database**, private owner/mode/path with symlink refusal, schema `marmot_read` version 1. Never add tables, indexes or version markers to wsd's exact-schema runtime journal. Only explicit first-install initialization may create it; a missing previously initialized DB holds ingress/delivery, preserving evidence rather than silently replacing history. Startup opens/validates existing private state, bounds recovery batches and does not start any transport automatically. Proposed tables: metadata/schema/identity; route epochs/holds/alert reservations; query reservations; snapshot cache; response revisions/parts/attempts/receipts; replay epochs/quotas. Typed constraints and named indexes support all bounded recovery/query lookups.

Replay reservation applies to **authenticated read/usage/unsupported messages with a valid native message ID**, key `(account_id, group_id, native_message_id)`; the third value is exactly InboundMessage.message.message_id_hex, with no optional synthetic event ID. It atomically claims that key and exact immutable requester/registration/selector/reply target before projection/send. Same key with changed provenance/payload quarantines, never overwrites. Message IDs cannot dispatch twice under different parse categories. Reactions without IDs and group-state events do not enter this query table: reactions are always effect-free ignored; state events idempotently latch the route hold keyed by current epoch+reason, with no requirement to synthesize a replay identity. Malformed/nonallowlisted/ordinary input creates no per-event row. Record only capped hourly counters by fixed reason/route; do not persist stranger text or identity or reversible public-key hashes. Optional diagnostics use a private rotating keyed HMAC solely within a bounded window, never exported as a durable identity. No correlation is needed for authorization.

Durable query transitions (one transaction per validated transition). Auth waits are at most five seconds, projection/cleanup at most five seconds, and each native send at most five seconds including cancellation/cleanup. A ready revision has an absolute 30-second first-attempt expiry; multipart expires 30 seconds after its first attempt. Waiting or retrying cannot reset these clocks. An admission has a 60-second absolute lifetime from reservation; source refresh/rebuild can occur at most twice before any attempted send, within that lifetime. At expiry, preparing/ready becomes expired with no send; it cannot rebuild forever. Persist UTC deadlines with monotonic checks inside a boot; clock rollback or restart time ambiguity expires the admission rather than extending it. The multipart deadline is the earlier of this admission deadline and 30 seconds after first attempt.

| State | Next / restart recovery |
| --- | --- |
| reserved | waiting-auth or preparing; exact message replay key exists before any reply, including busy |
| waiting-auth | preparing on fresh proof; suppressed for definite denial, auth-unavailable for timeout/read failure; restart repeats only inside original five-second deadline |
| preparing | ready with success or a fixed semantic outcome: unavailable, not-found, usage, unsupported, busy, narrow-query; restart rebuilds within retained lifetime |
| ready | fresh authority/content checks then sending; supersede/rebuild stale **unattempted** revision atomically; a failed bounded refresh can yield fixed unavailable within its lifetime; an expired admission becomes no-send expired |
| sending | persisted part/key/attempt precedes call; one valid receipt becomes part-confirmed; proven no-effect refusal may return ready once within the same deadline, otherwise send-failed; missing result becomes uncertain/partial-uncertain |
| part-confirmed | last part delivered; otherwise next ready under same revision; definite revocation -> partial-suppressed; auth recheck failure -> partial-auth-unavailable; deadline -> partial-expired |
| delivered | terminal with semantic outcome; delivered unavailable/busy is not delivered source data |
| suppressed, auth-unavailable, send-failed, expired | terminal before any confirmed part; retain no-send facts; no automatic restart retry |
| partial-suppressed, partial-auth-unavailable, partial-expired, partial-send-failed | terminal with confirmed receipts intact; remaining parts never restart |
| uncertain, partial-uncertain | terminal with all definite/ambiguous receipts; no automatic resend or remaining parts |

An auth wait between parts retains the confirmed-part prefix. On timeout use partial-auth-unavailable, never ordinary auth-unavailable or delivered. A no-effect refusal after a confirmed prefix exhausts to partial-send-failed. Unknown process crash during sending maps to uncertain/partial-uncertain. No terminal state is resumed automatically.

Quota refusal reserves **the same native message replay key** and a busy semantic outcome atomically before attempting a reply; a dedicated preallocated bounded slot controls reply rate, not replay identity. If no key/storage slot is available, make no reply and do not claim the event was accepted; count a bounded drop and raise capacity status. A later redelivery may then be accepted once, since the earlier event had no reply or dispatch. At most one busy reply per requester/route per 30 seconds; otherwise keep a compact suppressed/rate-limited tombstone if storage allows. At most 64 active queries globally, 8 per requester/route, 4 source workers, one send per group, fair round-robin. Fixed five-second backoff; no background retry timer. Recovery joins bounded owned work.

Responses have <= 20 deterministic parts and a revision digest over snapshot identity, original observation times, rendered-at UTC, bytes and part order. Part 1 replies to query; subsequent parts require **exactly one** well-formed native ID from each successful send and use the unique first-part ID. For a returned list of zero/multiple/duplicate/malformed IDs, retain the exact bounded returned receipt evidence, mark uncertain/partial-uncertain and stop. Do not arbitrarily select a root or resend. Multiple IDs are not silently interpreted as failure-before-effect; a future proven native root contract can be separately reconciled. Persist a send key before the first attempt: `read:v1:<64 lowercase hex SHA256>` over UTF-8 canonical JSON (sorted keys, no insignificant whitespace) containing version=1, account_id, group_id, registration_epoch, native_message_id, response_revision_digest and zero-based part_index. Every permitted retry of that exact part uses the **same stored key**. Changed bytes require an unattempted superseding revision and a new key; attempted unknown effects never supersede/retry. Permit at most one retry only when the wrapper proves the native request was not written/dispatched (for example local queue refusal before socket write); a peer retryable flag or error after write is not no-effect proof. No retry relies on native key retention; uncertain outcomes stop.

Send-time freshness is checked before first attempt: rebuild an unsent old revision rather than reusing a false fresh label. Every rendered response includes absolute observed-as-of and rendered-at timestamps; relative wording is explicitly **at render time**. Multipart uses one snapshot/byte revision, finishes within 30 seconds of first attempt and never substitutes a fresher chunk. Restart may resume a ready revision only before its first attempt and within its freshness bound, otherwise atomically rebuild. Any attempted part without definite result is uncertain on restart. Old rendered bytes never gain new timestamps. Authorization is always fresh independently of content freshness.

Storage is bounded: 16 MiB cache and 64 MiB non-cache logical budget plus filesystem headroom. Query admission reserves its bounded response/evidence budget, including one possible 1 MiB ambiguous native frame; the 64-active-query limit is only a concurrency ceiling, never a promise that every maximum-size query fits. Evidence reservation failure follows the same atomic busy/drop path before dispatch. Admission must leave preallocated capacity for a terminal uncertainty record. At every terminal transition compact rendered bytes, full source DTOs and routine request text out of the active database. Keep a fixed-size replay tombstone with exact normalized route/message key, requester provenance, immutable request/payload digest, registration epoch, terminal outcome, response/receipt digest, confirmed count and up to 20 confirmed receipt IDs; oversized or ambiguous native receipt frames are retained exactly in bounded private forensic segments (at most the native 1 MiB frame per attempted part) with their digest/index in the tombstone. Ambiguous attempts retain these forensic facts, never become retryable. No raw response bytes are required after terminal delivery, because no terminal state resends. Receipt evidence is hashed/archived before deletion of bulky bytes. Tombstones and actual ambiguous receipt evidence are never silently evicted. A terminal compaction test proves large (20-part) responses do not accumulate rendered payload forever.

At 70% non-cache capacity, coalesce one durable capacity alert through admind and expose doctor counts/estimated remaining reservations. At 85%, reject new large reservations but allow compact fixed notices within reserved space; at 95%, refuse new acceptance/replies and retain preallocated diagnosis/recovery slots. The supported operator command `wsd-read-config archive-plan`/`archive-apply --expect-digest=...` moves **terminal** tombstones/evidence to immutable private, digest-indexed closed segments, retains every replay key in a bounded on-disk lookup, verifies exact counts/digests before atomic publication, and reclaims bulky active DB pages. It does not reset a route epoch or delete replay identity. The version 1 archive manifest permits at most 32 closed segments and 1 GiB total archive bytes, with a 1-second aggregate indexed duplicate-lookup deadline and no unbounded directory scan. Active plus archived indexes are checked before accepting a key; an unavailable/corrupt/excess archive or lookup timeout holds acceptance rather than skipping duplicate checks. A finite configured quota within those maxima warns before it fills; an operator can increase that configured quota or add verified segments within these bounds through an audited plan without inventing consent, task state or native replay horizons. Raising the protocol maxima or changing retention is a design change. No native boundary is assumed and no automatic rollover forgets IDs.

Finite storage cannot retain unlimited distinct IDs forever. After compaction and supported archive/capacity expansion are exhausted, the honest safe outcome is a visible capacity hold with a real admind escalation asking for a scoped storage/retention design decision; it is not a permanent unexplained silence or a fabricated approved rollover. Approval is needed only if that decision changes the replay retention/design, not for ordinary supported archive movement or capacity adjustment. Journal loss/corruption preserves files and uses this same existing admind operator escalation; no empty replacement. Unauthenticated traffic cannot allocate replay rows or unbounded alerts. Quota/reserve metadata and at most one alert per closed reason are fixed size.

Schema upgrades are 6B-only transactional copies with exact source/destination versions, old rows/keys/FK/index/trigger checks, fsync+atomic publication and failure rollback; runtime DB untouched. Downgrade stops 6B and retains new DB/receipt; never overwrite newer query/send evidence with backup. No old runtime inbox is automatically imported as trusted 6B provenance. Legacy ambiguous rows, if explicitly migrated in a reviewed fixture, are nonselectable quarantine. Journal corruption/loss holds; operator uses supported doctor/recovery procedure through the authenticated approval flow, never empty replacement.

## 8. Stable cache identities, generations and bounded refresh

Stable cache/refresh identity is `(producer logical identity, projection schema, registration epoch, ContentScope digest, selector)`, **not** generation/boot/run. Each validated entry stores producer release/run/boot, positive generation, capture/observation times and the immutable envelope. Single-flight uses that stable key. Maintain an active producer binding separately: fresh reads must match it; a changed binding starts a new generation domain, invalidates pending adoption and marks retained same-scope entries **historical stale**. A persisted old-run entry is eligible only as explicitly historical display after fresh current authorization and unchanged ContentScope/schema; it never establishes the current run, generation or authority. Scope/policy/registration changes cannot reuse another scope's bytes. Reject a generation regression within the same domain, not generation 1 after a genuinely new bound boot.

Entries <= 256 KiB; total cache 16 MiB LRU, eviction has no effect on replay evidence. Collection pages <= 100 rows; shown/total and incomplete flags remain per collection. At age > 30 seconds trigger one coalesced refresh; exactly 30 is fresh. Monotonic age only within a boot; restart entries are stale and retain original UTC. Future UTC invalid. Failed refresh retains old facts, marks failed sections cached-unreachable and never changes their observation time.

A cold query starts/joins a bounded refresh and waits up to the shared five-second inclusive source/cleanup budget; it is not guaranteed to fail just because cache is empty. Warm queries reserve a current snapshot immediately and schedule refresh without blocking on source IO. A missing/failed cold source gives a fixed unavailable notice; stale cache gives source-specific age/failure warnings. Fresh policy/group verification remains mandatory even for historical cache. Target warm local p99 < 1 second for 1,000 fake requests measures durable local response reservation, not network delivery; cold path is explicitly up to 5 seconds plus bounded native send, not subsecond. Source stalls must not prevent other groups' fair handling or leave leaked processes.
