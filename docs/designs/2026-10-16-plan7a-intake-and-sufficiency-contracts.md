## 3. Closed grammar, validation layers, and privacy

Proposed later pure implementation: `src/heterodyne/gatekeeper/contracts.py`, `validate.py`, `project.py`, and named offline tests. Python 3.12/msgspec already exist; no dependency is added. The following is the complete v1 grammar. Every object has exactly its listed keys; only `?` keys may be omitted (omitted and explicit null are different). Wire structs are frozen and forbid unknown fields. Reject duplicate JSON keys, nonfinite numbers, invalid UTF-8/surrogates, bool-as-int, and trailing input. `[]` means an empty list, not omitted; `null` is explicit. No untyped Python objects, executable values, or provider-specific payloads are accepted.

**Primitive types.** `ID` is 1..128 ASCII letters/digits or `_:.+-`; `BeadID` uses the existing-ID read profile from product076 admind.approvals.BEAD_ID, fullmatch `[a-z0-9]{1,16}-[a-z0-9.]{1,32}`. Queue6fe's narrower minting regex is not an existing-ID validator. `SHA` is 40 lowercase hex; `Digest` is 64 lowercase hex. `PosInt` is 1..2147483647, `Offset` is 0..2147483647, each excludes bool. `Text` is a nonempty UTF-8 string <=4KiB; `Title` is nonempty <=200 Unicode code points and <=4KiB; `Body` is nonempty <=16KiB. All three are `PublicText`: validation takes an explicit immutable `PrivacyContext={format:1,login_dirs:[Locator],rule_revision:SHA,sha256:Digest}` (at most 16 directories, each at most 512 bytes; digest covers the other fields). Directory values are private validation configuration, not PublicText or model input. The pure implementation reuses the pinned redaction patterns with this explicit context and never calls process-global set_login_dirs or reads environment/config. The whole value must be unchanged by that explicitly configured redaction policy, with no C0/C1 controls except newline/tab. Blank-only text refuses. Full digests remain typed private fields, never a prose redaction bypass. No Unicode normalization occurs. `Locator` is a private nonempty UTF-8 string at most 4 KiB with no C0/C1 controls; it is not PublicText and is never model egress. Login-directory entries additionally have the 512-byte bound above.

`NativeValue` is a bounded JSON tree: null, bool, signed 64-bit integer, `Text`, list of NativeValue, or object of distinct `ID` keys to NativeValue; <=8 container levels, <=512 total tree nodes, <=32 members/items per container. Floats are outside this profile. Every scalar string must pass the same privacy check. This finite inert-data profile preserves admitted values exactly; it is not an action registry or permission to execute an object. Native6fe permits more values by truthiness; unsupported native values yield a local invalid-profile error, not a claim that the native gate rejected them.

**Native reference profile.** Queue6fe `REF_FIELDS=(kind,id,repo,path)`, `_resolve`, and `Resolution.resolved` are the source contract. Plan7A supports this explicit strict subset of native-accepted shapes; it does not normalize/add/remove keys before hashing:

| Ref variant: exact keys and types | Resolved identity |
|---|---|
| `{kind:"file",id:SHA,repo:Locator,path:Locator}` | SHA of the exact native Git blob/tree object returned for that path |
| `{kind:"commit",id:SHA,repo:Locator}` | same SHA (native resolver requires a commit object) |
| `{kind:"range",id:SHA+".."+SHA,repo:Locator}` | same ordered pair string |
| `{kind:"bead",id:BeadID}` | recomputed native linked-ask Digest, including its recursively resolved refs |

Native `_resolve` allows the four named keys and ignores some in individual variants; this v1 profile deliberately rejects unused `repo/path` on bead refs, `path` on commit/range refs, extra range endpoints, and extra ref keys. Repository/path strings are inert native locator values, not fetched, executed, converted to URLs, or claimed public by this pure component. Actual lookup, object existence, linked-bead cycle/depth limits, and infrastructure uncertainty remain native-adapter responsibilities. Private locator values must never be sent to a model merely because this grammar can retain them; the explicit locator-free projection below is mandatory and any different real-adapter egress needs its own reviewed contract.

`NativeAsk` is `{effect:NativeValue,excludes:NativeValue,why:NativeValue,risks:NativeValue,refs:[NativeRef],targets?:[BeadID]}`. The first four must be truthy under native6fe's JSON/Python semantics; refs has 1..32 items; present targets has 1..32 unique IDs. These are exactly queue6fe's ASK_FIELDS and optional-target rule. In particular **purpose is not an accepted native6fe ask key**: product076 Readout's optional purpose does not extend that queue schema. A later queue extension needs an explicitly pinned compatibility revision, not an unseen extra field. `Candidate={title:Title,description:Body,ask:NativeAsk}`. This preserves whole native values, not a rendered summary, and does not replace native lint/digest or later action validation.

`ResolvedIdentity` is the variant-correlated SHA, ordered SHA pair string, or Digest specified in the table. `ResolvedRef={ref:NativeRef,resolved_id:ResolvedIdentity|null}`. `ContextItem={source_id:ID,kind:"task"|"doc"|"diff"|"excerpt",content_id:Digest,text:Text,ref:NativeRef,resolved_id:ResolvedIdentity}` has **all six keys**. `content_id` hashes exactly text UTF-8; resolved_id has the corresponding variant's type from the table. task requires bead ref, doc requires file/commit ref, diff requires range ref, excerpt permits any variant. The narrower sufficiency context profile below supersedes these general correlation rules: only doc/excerpt with file refs and full blob proof is allowed there. Source IDs are unique. An excerpt hash is not proof a whole source was read; caller assertions alone are not provenance. For sufficiency, only file refs resolved to blobs are accepted as ContextItems: text must be the entire UTF-8 blob, without decoding replacement or normalization, and Git SHA-1 of `blob <UTF-8 byte length>\0` plus those bytes must equal resolved_id and the corresponding resolved_refs identity. Reject tree objects and partial excerpts. content_id additionally binds SHA-256 of those bytes. Commit/range/bead refs remain valid native evidence but cannot supply semantic context or automatic quotes in v1 without a later reviewed extraction contract. All sufficiency context must match an exact candidate ref; mismatches refuse before assessment. This bounded whole-blob requirement establishes a directly checkable content proof without reads or native authority.

`Origin={event_ref:ID,creator_ref:ID,session_ref:ID|null}` is common to intake/sufficiency. These are opaque references to upstream authenticated provenance; accepting an ID does not authenticate a sender or create a session. Permission subject is `{task_id:BeadID,session_ref:ID,tool_name:ID}`. Opaque references are private host fields, never an automatic model-egress allowance. `PolicyRevision={id:ID,sha256:Digest}` refers to the host policy snapshot supplied by the eventual policy owner; Plan7A neither loads nor trusts a model-selected policy. It is required on all requests, and changing it invalidates the request binding.

**Request envelope.** Exact common keys are `{format:1,kind:"intake"|"sufficiency"|"permission",request_id:ID,workstream_id:ID,subject_id:ID,revision:PosInt,policy_revision:PolicyRevision,privacy_sha256:Digest,context:[ContextItem],snapshot_sha256:Digest}` plus exactly the kind-specific fields in §§4,5,7. snapshot_sha256 hashes canonical UTF-8 JSON (sorted keys, separators comma/colon, ensure_ascii=false, no Unicode normalization) of this whole request except itself. This is a gatekeeper input identity, not the native context_digest, action key, launch receipt, or Marmot delivery receipt. privacy_sha256 must equal the supplied verified PrivacyContext.sha256; its rule_revision must match the pinned source implementation. Common context may be empty; <=32 items.

**Result envelope.** Exact keys are `{format:1,kind:<same kind>,request_id:ID,revision:PosInt,snapshot_sha256:Digest,outcome:<kind-specific tagged union>}`. outcome uses discriminator `status`, independently of kind. All five echoed identity/version fields must match the validated request. Native approval/task identity is bound by its inclusion in the request hash; there is no additional undeclared echoed approval_id. Every kind has the same exact failure outcome `{status:"unavailable",reason_code:"timeout"|"unavailable"|"bad_output"|"unsafe"|"oversize"|"stale_digest"|"unreadable_policy"}`; no arbitrary diagnostic prose or other fields occur in that variant. A future adapter normalizes exceptions into this envelope only when there is a valid request to bind.

**Local validation result.** `Check[T]` is exactly `{status:"valid",value:T}` or `{status:"invalid",stage:"request"|"result",code:"schema"|"unsafe"|"oversize"|"binding"|"invariant",field:FieldPath|null}`. There are no separate `Invalid`, `UnsafeInput`, `UnsafeResult`, or unwrapped scalar result types. Unsafe content uses code unsafe at its actual stage. Missing required lint is schema-invalid; an explicit failed lint is a valid request variant, handled by §5 precheck. `FieldPath` is an ASCII path of at most 128 bytes: an initial `[a-z][a-z0-9_]{0,31}` followed by at most 8 `.name` or `[0..999]` components (decimal indices without leading zeros); null means whole input. `intake_disposition` returns HoldInvalidInput for invalid host input, `sufficiency_disposition` returns HoldUnavailable, and `permission_disposition` returns EscalateProposal. These functions accept Check values and never echo rejected bytes. Thus the kind, not which validator happened to fail, determines recovery. Model failure is never reinterpreted as malformed host input. Every capitalized projection name in §§4–7 is a local enum value only (CreateMinorProposal, ConfirmMaterialProposal, RawUnreviewedProposal, RawConfirmProposal, HoldInvalidInput, SufficientProposal, EnrichmentProposal, NeedsGrooming, HoldUnavailable, ReturnToOrigin, CannotApproveNotice, AllowProposal, DenyProposal, EscalateProposal). Projection enums carry no hidden fields and create no native metadata. The separate pure `enriched_candidate(request,verified_result)->Check[Candidate]` returns the exact §5 candidate transformation; no other builder is implied. These enums are not wire judgments or native approval decisions.

**Correctable input recovery.** Invalid-profile/oversize/unsafe intake returns HoldInvalidInput with only a content-free field/code receipt. The future origin owner must retain the original safely and issue a safe origin-specific grooming notification; never echo secret bytes or silently drop the submission. A still-unrepresentable native ask (including a valid native float, long string or unused ref key) returns a typed profile gap for origin correction; it cannot self-unhold or be called native-invalid. This deliberately bounded new-intake profile requires explicit human acceptance in §10. It does not change current relay behavior: unsupported shadow inputs are recorded diagnostically and existing valid relay approvals remain unaffected until a separately admitted enforcement release.

**Bounds.** Entire request <=128KiB UTF-8; result <=32KiB; <=32 context items/open tasks, <=16 acceptance criteria/dependency edges; <=64 gaps, <=8 additions. Original/description use Body, other prose Text/Title; NativeValue retains its separate bounds. Exceeding any bound refuses the whole value, without truncation/sampling. A caller can prepare a distinct bounded snapshot, explicitly marking incomplete intake context; it cannot silently retry less context as equivalent input.

Three distinct async Python protocol methods define eventual adapters: `classify(IntakeEgress)->IntakeModelJudgment`, `assess(SufficiencyEgress)->SufficiencyModelJudgment`, `permission(PermissionEgress)->PermissionJudgment`. These are proposed ports, not an installed Hermes API. Each ModelJudgment has exactly its kind's result envelope below, except intake dependencies carry task_id:Alias instead of BeadID and sufficiency additions carry source_id:Alias instead of the private source ID. Alias is decimal 1..32, no leading zeros. The pure host normalizer resolves only those two fields through the frozen egress mapping, rejects unknown aliases, then validates the normalized Judgment against the host request. PermissionJudgment needs no alias substitution. No other field can be remapped or repaired. Pure `egress(request,PrivacyContext)` returns Check of a closed DTO: common `{format,kind,request_id,revision,snapshot_sha256}` plus intake `{original,context_complete,open_tasks:[{alias,title}],context:[{alias,text}]}`, sufficiency `{card:{title,description,effect,excludes,why,risks},refs:[{alias,kind}],context:[{alias,text}]}`, or permission `{tool_name,intent,input,invocation_sha256}` (tool_name equals subject.tool_name and input equals invocation.input exactly; both must pass explicit PublicText validation before egress). Aliases are decimal 1-based strings assigned in request order; intake dependency results use these aliases and the host maps them to exact open-task IDs before validation. Sufficiency addition source_id is likewise the context alias and is mapped before validation. No repo/path, native IDs, Origin, session, policy text, private configuration, or private tool arguments enter these DTOs. Public tool arguments enter only the explicit permission input projection; any private value refuses egress and escalates, rather than changing argument bytes. NativeValue prose in the card must pass the same explicit privacy checks. The host request hash binds the exact private facts even though the egress projection omits them. Projection failure is typed unsafe/oversize; it cannot trigger a model call. This design accepts only explicitly PublicText egress, not a promise that an LLM will redact input. Fakes implement these interfaces for offline contract tests; no external adapter or scheduler is implemented. Validate before any future egress and never forward secrets, credential paths, private locators, raw transcripts, or authentication identities under the excuse of summarization. Prompt injection remains untrusted data. Models' advisory results confer no native authority.

## 4. Intake classification and rewrite

`IntakeRequest` adds exactly `original:Body`, `origin:Origin`, `target:{workstream_id:ID,repo_id:ID}`, `context_complete:bool`, and `open_tasks:[{id:BeadID,title:Title,description_digest:Digest}]`. Target workstream_id must equal the envelope workstream_id; open-task IDs are unique. Host-validated opaque target IDs are provided by the eventual router, not chosen by a model. An empty original refuses. subject_id is a pre-native submission ID allocated by the future ingress owner, not an as-yet nonexistent bead. description_digest is SHA-256 of exact UTF-8 description bytes with no normalization; the description itself is not implied available. All dependency targets must come from open_tasks, so none can target this new submission. Existing-task editing is outside this intake contract. The open-task list is explicitly bounded snapshot context; lack of an entry does not prove that task absent globally.

`IntakeJudgment.outcome` is exactly one of:

- `{status:"proposed",materiality:"minor"|"material",title:Title,description:Body,acceptance:[Text],dependencies:[{task_id:BeadID,type:"blocks"}],change_flags:ChangeFlags,reason:Text}`; acceptance is nonempty, dependencies may be empty.
- The common unavailable outcome from §3.

`ChangeFlags` is an object with exactly these six boolean keys: `target_changed`, `requirements_changed`, `question_to_action`, `destructive`, `outward_facing`, `context_incomplete`. Effective materiality is computed by the host: material if any flag is true, context_complete=false, or the model says material; otherwise minor. A false context_incomplete flag cannot override host context_complete=false. Contradictory declared flags do not create an invalid-result downgrade path. Proposed targets cannot differ from the request: a requested target change is represented in the reason and `target_changed`, for later human confirmation, never an effective target override. Duplicate/self/unknown dependency IDs refuse; a future native adapter still must validate full-graph cycles and eligibility. No arbitrary edge type, task label, agent identity, approval ID, policy change, or executable action belongs in the result.

Model-declared materiality is advisory: an empty/incomplete task snapshot cannot establish a conflict-free dependency plan. The pure projection `intake_disposition(request,verified_result)` returns `HoldInvalidInput`, `CreateMinorProposal`, `ConfirmMaterialProposal`, `RawUnreviewedProposal`, or `RawConfirmProposal`; it creates no bead. Material means the ADR §5.1 list, with uncertainty treated as material. Typos/reference clarification alone can be minor. Deterministic checks enforce the declared flags, but cannot prove that an LLM correctly preserved intent; that is accepted ordinary advisory-model risk. Fixture review specifically covers missed semantic changes. The eventual router retains original and rewrite together for operator correction.

A valid material proposal maps later to `kind:confirm` without `agent:` routing; dispatch waits for authenticated confirmation/correction. For a valid safe request, only a host adapter failure explicitly categorized timeout/unavailable maps to raw-text `unreviewed` intake per ADR §5.1, with an explicit diagnostic. Model-originated unavailable, malformed/unsafe/oversize output, binding failure, and egress refusal map to RawConfirmProposal: original safe text retained as unreviewed, mandatory confirmation before dispatch, never unattended minor fallback. Failure provenance is a local `Attempt={status:"completed",result:Check[Judgment]}|{status:"host_failed",reason_code:"timeout"|"unavailable"}` supplied by the eventual adapter, not a model-selectable result status. This conservative confirmation qualification is presented explicitly in the design approval scope; it does not fabricate a minor rewrite. Full routing must still apply native task/design/policy gates before any raw or confirmed task can run. Plan7A does not implement that route or change the raw fallback into authority.

## 5. Sufficiency is a separate gate

`SufficiencyRequest` adds exactly `approval_id:BeadID`, `native_context_digest:Digest|null`, `lint:Lint`, `candidate:Candidate`, `resolved_refs:[ResolvedRef]`, `groom_failures:0|1|2` (integer, not bool), `origin:Origin`, `submission_id:ID`, `submission_revision:PosInt`, `base_candidate_sha256:Digest`, `enrichment:{status:"unused"}|{status:"used",base_description:Body,additions:[<the exact addition objects below>]}`. subject_id must equal approval_id. resolved_refs is 1..32 entries in exact candidate.ask.refs order, each row.ref equal to that native ref. The authoritative whole candidate comes from the future native adapter, never reconstructed from Readout lines. A caller's assertion of a digest or lint cannot grant native authority.

`Lint` is exactly `{status:"passed",gaps:[]}`, `{status:"failed",gaps:[Text]}` (nonempty), or `{status:"unavailable",reason_code:<common failure enum>}`. Passed requires a nonnull native_context_digest and every resolved_id nonnull; failed allows null identity/digest for confirmed missing or malformed evidence, with genuine gaps; unavailable allows nulls for infrastructure uncertainty without inventing absence. The pure precheck consumes this explicit union before calling assess: failed => NeedsGrooming, unavailable => HoldUnavailable, passed => eligible for assessment only after the supplying native adapter's real checks. Missing lint or contradictory union values are local schema/invariant errors, never model-eligible.

`SufficiencyJudgment.outcome` is exactly one of:

- `{status:"sufficient",reason:Text,additions:[],gaps:[]}`.
- `{status:"enrich",additions:[{source_id:ID,start:Offset,end:Offset,quote:Text}],reason:Text,gaps:[]}`; additions nonempty, unique (source_id,start,end) tuples.
- `{status:"groom",gaps:[{field:"what"|"effect"|"excludes"|"why"|"context"|"risks"|"alternatives"|"refs",detail:Text}],reason:Text,additions:[]}`; gaps nonempty.
- The common unavailable outcome from §3.

The semantic question is ADR §5.9: can an operator decide from this card alone without guessing? Required what/effect/excludes/why/context/risks/alternatives and immutable evidence must remain intelligible together. A link's existence does not substitute for decision context. An LLM cannot approve missing typed action fields, undisclosed effects, or unpinned refs. Native `ask` keys remain exactly the queue's current schema; no new `gatekeeper_*` key is smuggled into native metadata.ask.

For `enrich`, offsets are Unicode code-point offsets into one supplied context item's text, `0<=start<end<=len(text)`, `quote == text[start:end]`. No ellipsis or paraphrase is accepted as an exact quote. The pure enrichment proposal preserves title and every NativeAsk field byte-for-byte; it appends only `\n\nGatekeeper-added context (source <source_id>; ask reference <N>):\n<quote>` to description, in additions order. This literal marker prefix is reserved: unused input descriptions containing `Gatekeeper-added context (` anywhere are invalid. Used input must be exactly reconstructed from marker-free base_description and the retained validated additions; arbitrary preexisting markers or edits refuse. N is the 1-based position of the byte-equivalent ContextItem.ref in candidate.ask.refs; no match => NeedsGrooming. Identical duplicate refs use their first position. The marker names a root-ask ordinal only. It is never an approve-bead `--doc N` argument: native Resolution.docs can deduplicate or expand linked evidence. Any later document command needs a fresh validated native docs mapping, not this number. This deliberately limits automatic enrichment to already supplied pinned evidence. Unsupported assertions or any required change to effect/excludes/refs return `NeedsGrooming`, not a broader rewrite. Source mapping and quote offsets are retained in private proposed evidence, and the visible description uses the exact marker above; the existing native card shows the unchanged pinned refs themselves. The complete transformed candidate must pass all original privacy/profile/request bounds and description <=16 KiB. The sum of appended marker+quote bytes is at most 8 KiB, in addition to <=8 additions; aggregate overflow returns NeedsGrooming atomically, without a partial candidate.

Enrichment is **not sufficient**. A later consumer must atomically replace the whole candidate object, recompute native lint/resolution/digest and card, and obtain a fresh sufficient judgment over that exact new candidate. At most one enrichment cycle per (submission_id, submission_revision). This identity is allocated by the future durable consumer from an external submitter revision; native digest changes caused by enrichment do not change it. base_candidate_sha256 covers the exact original candidate, unchanged across the enrichment/reassessment pair: unused must hash candidate directly; used must hash the reconstructed candidate with base_description and unchanged title/ask. Used additions must pass the same quote/source checks; enrichment replay metadata is a proposed durable-consumer contract, never a model claim. A used enrichment plus another enrich result yields NeedsGrooming. The consumer must persist this transition; a fresh model request, reassessment digest, or restart cannot reset it. A genuine external corrected submission may advance submission_revision while preserving the saturated grooming count. An old sufficient judgment is invalid for a new digest, source snapshot, policy revision, or changed card content. No supplement can be approved off-card or behind a free-text digest marker.

The pure `sufficiency_disposition(request,verified_result)` projection returns `SufficientProposal`, `EnrichmentProposal`, `NeedsGrooming`, or `HoldUnavailable`. None posts a card or grants approval. A passing semantic proposal does not bypass native `postable`, group authentication, redaction, whole-card size, action validation, or human approval. Future posting must fresh-check both native state and the exact judgment binding after any await, outside then inside the short existing commit boundary as appropriate to its final design; Plan7A claims no implemented atomic integration.

## 6. Grooming, unavailable results, and terminal recovery

Pure `groom_disposition(groom_failures)` takes the count AFTER processing the current confirmed failure: 0/1 maps to ReturnToOrigin and 2 to CannotApproveNotice; it does not mutate counters. The retained count saturates at 2, never grows to an unrepresentable 3. Initial failure with no returned revision has count 0; first genuine returned revision still failing sets 1; second sets 2. Operator-groomed later submissions are still assessable with count 2: a sufficient result can proceed, another failure remains CannotApproveNotice. No automatic third return-to-origin is created. A future consumer durably increments failures only after a genuine returned revision is re-evaluated and still fails, not on retries, duplicate events, model outages, or delivery uncertainty. Submission revision identity is independent of the per-candidate native digest as specified in §5. Native digest still binds each assessment snapshot. A stale reply cannot consume a newer revision's budget. Grooming steers the **originating parked session** or the recorded creator, never a replacement agent invented for this purpose; it also counts within the existing three-nudge/no-progress budget when actually delivered as steering.

At two failed grooms the ADR requires a control-group cannot-approve-as-written notice listing gaps, deny as the default, and no approval buttons. This means **recommend deny**, not automatically record denial on silence. The operator can explicitly deny or groom; there is no approve-as-written path. Missing origin, dead session, exhausted nudge budget, or unknown delivery holds for an authenticated Marmot question. The eventual consumer retains the pending ask and origin evidence, releases unrelated work, and never fabricates a resumed session or resolved notice. No counter is reset by restart, a fresh model request, or task reassignment.

Timeout, invalid/unsafe/oversize input or output, endpoint error, stale native digest, and unreadable policy all remain typed failures (stale_digest and unreadable_policy are explicit reason_code members). For sufficiency the result holds or returns correctable input gaps to origin; no outage becomes a human approval request for the incomplete ask. A separate content-free operational notice/question may explain the hold through the authorized control route. Recovery is a fresh native read and explicit resubmission of a corrected revision or restoration of the same dependency, with prior evidence retained; no automatic looping retry, self-unhold, alternate writer, or permission-classifier workaround.

Before the release shipping BOTH wsd and the semantic gatekeeper, any eventual relay judgment is **shadow only**. It cannot block or authorize historical valid phone approvals. That release must enforce passing sufficiency for every relayed approval, with no interval where both ship without enforcement. Plan7A neither ships a gatekeeper nor ends the interim exception. Activating either shadow or enforcement requires its own reviewed integration, real predecessor completion, and deployment authority.

## 7. Permission port: no decision/approval conflation

`PermissionRequest` adds exactly `subject:{task_id:BeadID,session_ref:ID,tool_name:ID}`, `intent:Text`, `invocation:{cwd_id:ID,input:NativeValue,sha256:Digest}`, `effective_budget_ms:PosInt`, and `elapsed_ms:0..2147483647` (integers, not bool). subject_id must equal subject.task_id. invocation.sha256 is the canonical JSON SHA-256 of `{subject,cwd_id,input,policy_revision}` with the same canonicalization as the request; exact arguments, session, tool and opaque cwd identity are thus bound. The host invocation is inert data and is never executed by this port; only its exact privacy-safe input projection may enter the explicit permission egress DTO. AllowProposal applies only to these exact bytes. The eventual Plan5 adapter must validate the actual cwd identity/action mapping and argument equivalence before any execution. No fixture action_ref, constant tier, or executable payload port is invented here. The permission egress carries exact privacy-safe tool/input data; a descriptive intent alone is insufficient. Context and policy remain host-controlled, and permission result is advisory until actual hook/native input equality is established by later integration. effective_budget_ms is the frozen effective workstream timeout configuration in milliseconds, bounded 1..60000 for this proposed profile. A larger or unreadable policy value is a typed unreadable_policy hold/escalation, not an assertion that the installed configurable setting is a hard 60 seconds.

`PermissionJudgment.outcome` is exactly `{status:"allow",reason:Text}`, `{status:"deny",reason:Text}`, `{status:"escalate",reason:Text}`, or the common unavailable outcome from §3. There is no scalar string judgment or alternate exception shape. A result of another kind cannot be decoded as PermissionJudgment. `permission_disposition` maps local invalid input/result or unavailable to EscalateProposal and any elapsed_ms>=effective_budget_ms to EscalateProposal before considering allow/deny. Otherwise valid allow maps to AllowProposal, deny to DenyProposal, and escalate to EscalateProposal. The future integration must enforce the ADR's **total effective configured** grey-zone budget (at most 60 seconds in this profile) across queueing/model/validation, with no retry reset. Plan7A performs no wait or scheduling; elapsed_ms is an injected fixture value, not a production clock attestation.

Deterministic hard-deny and operator-only floors are evaluated **before** this port and cannot be downgraded by `allow`. No existing action, policy, secret-access, deployment, or message-send authority changes. `allow` means only an advisory grey-zone result under the unchanged sandbox/native gates; an action still requires its own authorized path and wsd-act validation. Permission failure escalates under §5.3; sufficiency failure cannot bypass §5.9 by being mislabeled an escalation. The later Plan5 integration owns durable audit of tier/decider/reason, action state, idempotency, decision write/readback, and unknown execution reconciliation. Plan7A has no approval metadata writer or executor credentials.
