## 1. Authority, scope and preserved contract

The approved predecessor is `e8b5db3fb3e506ff909540dfb298b2c873446448:docs/adr/2026-10-16-fulfilled-question-lifecycle.md`.
Its question/merge-only eligibility, complete-context declaration, controller terminal-receipt authority, unchanged original answers/status and immutable fulfillment receipts, native-approval exclusion, replay keys and rollback history remain binding.
The historical code review approved only an offline PoC with `ENABLED=False`; it explicitly required revision before deployment. Its eight findings motivate this amendment, not activation consent.
This design adds bounded diagnostics and verification and corrects six local contract defects. It does not add summarization, provenance backfill, external completion proof, automatic operation replay, automatic disposal, or approval reconciliation.
All existing legacy Ask DTOs, ten wire statuses, fulfillment request/receipt schemas and canonical digest domains remain unchanged. New diagnostic DTOs are opt-in. The opt-in fulfillment view retains its v1 fields and adds the finite lifecycle value `unverified` and nullable binding only when binding reconstruction is unavailable; the immutable receipt remains readable. This means no current verification proof, never new eligibility or completion authority. Legacy Ask/Get projections remain byte-compatible.
Explicit predecessor deviations requiring human approval are asynchronous verification with conservative counting instead of full rebuild before serving posts, explicit quiesced projection migration instead of ordinary Store-open migration, and immutable duplicate-receipt classification independent of derived validity. The new opt-in lifecycle value, nullable unavailable binding and diagnostics must be disclosed to each fulfillment client before activation.
Implementation must still land disabled. Enabling any producer or migrating a real database requires a separately authenticated Marmot deployment decision with published design, actual source/configuration pins, deviations and rollback scope.

## 2. Visible pending-notice recovery (historical finding 1)

An answer's durable `inbound.sender_key` is the only existing requester-owner source. NULL remains unknown; display labels, present operator membership, cached senders and same-UID access cannot reconstruct historical consent.
Unknown ownership remains quarantined; revoked ownership remains suppressed under the existing fresh-policy delivery gate. No diagnostic makes either deliverable.
Propose and identical re-propose return their existing result type but replace misleading queued/retained messages with one exact code: `notice-pending`, `notice-delivered`, `notice-quarantined`, `notice-suppressed`, `notice-expired`, or `notice-unavailable`.
Get retains its existing view grammar; its message reports the same pending-notice diagnostic when applicable. These codes describe observation, not a promise of future delivery.
A new local same-UID opt-in request is exactly `{"type":"fulfillment.inspect"}`. Unknown fields are refused; there is no limit, cursor or pagination option.
Its closed reply is `{schema:"fulfillment-inspect-v1", entries:[Entry]}` within the existing 128-KiB reply limit. Entry is `{ask_id, intent_id, digest, created_at, state, reason, actions}`. IDs/timestamps retain their predecessor bounds; each entry must serialize within 1 KiB, so all 40 plus envelope fit. Invalid stored metadata yields a fixed unavailable response without materializing its unbounded value.
Actions is an ordered subset of `get`, `dispose`, `replace`, `controller-receipt`, `hold`. The CLI is `admind ask fulfillment inspect --json`; no native writes, network fetches or notice retries.
One read snapshot selects all current pending intents, ordered by intent_id with LIMIT 41. The existing cap is 40; a 41st row is a fixed integrity diagnostic, not silently omitted work. No full answer bodies, declaration, raw owner keys or notice text are returned.

| State | Fixed reason | Supported next action |
| --- | --- | --- |
| pending | delivery-pending | get, dispose, replace, hold |
| delivered | delivery-complete | get, dispose, hold |
| quarantined | unproven-owner | dispose, controller-receipt, hold |
| suppressed | requester-revoked | dispose, controller-receipt, hold |
| expired | intent-expired | dispose, replace, controller-receipt, hold |
| unavailable | delivery-unresolved | get, dispose, controller-receipt, hold |

Inspect reads the exact intent's bounded outbox group, ownership and existing guard state in one read snapshot. Known unknown provenance reports quarantined even before the outbox worker has classified it; fresh-policy revoked ownership reports suppressed even before delivery. Unreadable policy or ambiguous ownership metadata is unavailable. Reuse the existing pure ownership/policy checks without issuing a send or mutating its queue. Expiry takes precedence; all chunks sent with IDs and exact reassembly is delivered; any unknown/missing/inconsistent/failed or possibly-issued part is unavailable. Uniform quarantine/suppression yields that state; mixed states are unavailable. Otherwise the intact pending group is pending.
Before materializing notice text, validate the intent's recorded `parts` as an integer 1..3,500 and use the existing BINARY key index with the literal range `key >= 'fulfill-intent:X:' AND key < 'fulfill-intent:X;'` (bound X is the validated intent ID), ordered by key, LIMIT parts+1. Do not use LIKE. Validate exactly the recorded part count, all distinct indices 0..parts-1 and exact group metadata; reject missing/excess rows before reassembly. Bound raw byte lengths before loading text and then enforce the approved notice's total <=3,500 Unicode characters and 40 LF lines. A malformed group is unavailable, never truncated or retried. Inspect always returns the complete <=40-row catalog or a fixed integrity/bounds refusal, not a misleading partial inventory.
The global cap remains 40 current pending intents, including expired/quarantined/suppressed ones, and one per ask. Inspect/get/dispose/controller apply remain available at the cap. There is no 24-hour automatic release.
Dispose and explicit replacement retain the existing expected-intent digest, tombstone and audit semantics. Disposal releases only that pending slot, not capacity or replay history. Replacement always creates a fresh intent/notice and requires freshly proven current ownership; a quarantined or suppressed current intent cannot be replaced to repair provenance (`notice-owner-unavailable`). Dispose or a genuinely bound controller receipt is the supported route. Unknown provenance is never backfilled; policy restoration may make the existing owner current, but replacement still requires an explicit new request and fresh checks.
Retired/expired/consumed intents can never authorize a later `!fulfill`, including replies to previously delivered chunks. Retirement does not erase a possibly delivered/unknown outbox row or resend it. Controller receipt remains an alternative only when its genuine terminal evidence and binding exist.
Complete context still must fit 3,500 characters and 40 LF lines and pass redaction unchanged. There is no excerpt/summarization fallback. The exact refusal is `notice-redaction-or-bounds`; explanation belongs in documentation, not the machine code (finding 6).

## 3. Reconcile and transaction/confirmation corrections (findings 2–6)

Reconcile keeps its existing manifest limit 256 KiB, 1..20 distinct asks, digest-bound continuation and fulfillment-reconcile-v1 result grammar. Validate the whole local input before any apply.
Each entry has its own bounded decode/validation/transport boundary. An invalid local receipt is incomplete and advances; a valid server refusal maps to its existing typed outcome and advances. Applied this run remains `applied`; observed existing identical receipt remains `already-applied`.
A malformed/legacy reply, invalid Get projection, `Invalid`, `DecodeError` or unavailable transport during a server exchange yields `unavailable` for that entry, stops, and returns all preceding results plus the cursor at that unresolved entry. Never discard already committed results in command-level generic-error handling.
Continuation starts with read-only Get for the same exact receipt/binding. A positive matching immutable stored request_digest/receipt proves already-applied even if validity, epoch or generation is unverified/conflicting; a different stored request_digest is a conflict. Lifecycle.duplicate() uses immutable request_digest equality only, never the mutable valid bit or verification stamps. Get exposes the immutable receipt and identity before lifecycle verification, with lifecycle unverified/eligible=false where appropriate. This proves metadata application only, not present capacity suppression or external-effect success. A malformed immutable receipt is unavailable; never replace it. A different identity holds. Absence is not proof an external operation did not occur. Only the predecessor's identical metadata application/readback rules are permitted; never replay the completed external operation.
`Store.transaction` tracks the outer transaction's read-only mode. Nested writer entry under a read-only outer block raises fixed `read-only-transaction` before yielding or changing depth. Nested reads under either mode and nested writers under a writer retain existing atomicity. Clear depth/mode on BEGIN, COMMIT and exception failures. This is a trusted API restriction, not a sandbox against arbitrary raw SQLite access.
The daemon intercepts literal `!fulfill` only when ENABLED is true. Disabled behavior follows the exact pre-feature command/bump/ask routing, without a new authorization reply.
When enabled, fresh authorization and nonempty durable `inbound_sender(mid)` must both succeed; confirmation reads that durable principal and records it in the immutable receipt in the same mutation transaction. A missing cache entry cannot become an empty principal, and a cache value cannot override durable identity. Unauthorized, missing-principal or latched `!fulfill` uses the existing `deny_rows(mid)` inside that transaction: durable inbound is dropped, the fixed existing UNVERIFIED reply is queued only when not latched, and a latch queues no response. Do not use finish(), mark done or invent a fulfillment-specific authorization reply.
Persistent reply failure leaves durable inbound work recoverable; a fixed refusal reply is never fabricated as delivered.

## 4. Bounded verification projection (finding 7)

The core's current startup rebuild scans and hashes all retained history under one writer transaction. Replace that implementation; a schema/version flag alone is not verification.
Keep every original receipt byte, receipt ID, operation core, consumed answer reference and audit row. Receipt binding/canonicalization remains fulfillment-v1; the new schema version describes only derived validity.
New additive tables are `fulfillment_projection_meta(singleton INTEGER PRIMARY KEY CHECK(singleton=1), epoch TEXT NOT NULL, scheme TEXT NOT NULL, scan_cursor TEXT)` and `fulfillment_generations(ask_id TEXT PRIMARY KEY, generation INTEGER NOT NULL CHECK(typeof(generation)='integer' AND generation>=0 AND generation<=9223372036854775806))`.
Meta contains a fresh 64-lowercase-hex epoch and exact scheme `fulfillment-projection-v2`. Keep the complete original eight-column ask_fulfillments CREATE TABLE SQL byte-identical: no ALTER, changed whitespace, column addition or positional INSERT rewrite is needed. Store stamps only in additive `fulfillment_verifications(ask_id TEXT PRIMARY KEY, epoch TEXT NOT NULL, generation INTEGER NOT NULL, state TEXT NOT NULL CHECK(state IN ('valid','conflict','too-large')))`; generation uses the same integer range as fulfillment_generations.
Add `fulfillment_dirty(ask_id TEXT PRIMARY KEY, generation INTEGER NOT NULL)` and an index on fulfillment_verifications(epoch,ask_id); both dirty and verification primary keys index ask_id. Epoch is not derived from a binary version or a human's assertion that nothing changed.
A record suppresses capacity only if its receipt valid=1, its joined verification state=valid, verification epoch equals current epoch and verification generation equals that ask's current generation. Missing generations, stamps or meta never suppress.
Unverified, dirty, too-large and conflict receipts remain capacity-active, including when their retained ask's raw status is terminal. A receipt whose ask is missing is an orphan integrity diagnostic and a fulfillment mutation/view HOLD for that ID. It is not a fabricated AskRow, capacity slot or global posting HOLD; no absent ask can be suppressed.
All list/count/eligibility projections use that one predicate. A current exact verification stamp can be reused without rehashing complete history. Get still exposes a well-formed immutable receipt identity when the projection is unverified or damaged, with lifecycle unverified and eligible=false. If the original ask/binding cannot be reconstructed, Get returns result unavailable/message binding-unavailable with its existing view fields, binding=null, receipt=the readable immutable receipt, lifecycle=unverified and eligible=false; reconcile checks immutable receipt identity before requiring a fresh binding. This cannot authorize a new apply. A malformed immutable receipt itself still yields unavailable without claiming a readable identity. It never says eligible/fulfilled on the strength of old valid=1 alone. Fulfillment mutations requiring a new binding remain held until that binding is verifiable.

### 4.1 Exact mutation coverage, including old binaries

The implementation must ship literal deterministic DDL for these named triggers; compare its complete stored sqlite_master definitions and supporting table/index schemas with the pinned implementation before suppression. No IF-NOT-EXISTS success, version-only trust, or PRAGMA schema_version-only trust.
BUMP(k) executes only WHEN k is non-NULL AND EXISTS(SELECT 1 FROM ask_fulfillments WHERE ask_id=k). Its same-transaction statements upsert/increment that generation, set the matching receipt valid=0, delete its fulfillment_verifications row, and upsert dirty(k,current generation). Thus asks/answers with no receipt perform no generation/dirty writes; approval asks cannot acquire these rows. fq2_receipt_insert creates the first generation after its receipt exists. Overflow aborts the originating write; never wraps or converts to REAL.
The trigger set is finite and names are fixed:

| Trigger | Event and exact coverage |
| --- | --- |
| fq2_asks_insert | BEFORE INSERT asks: BUMP(NEW.ask_id), covering new rows and INSERT OR REPLACE same-ID victims |
| fq2_asks_update | BEFORE UPDATE OF ask_id,kind,poster,title,body,pr_url,head_sha,bead,digest,question_form,choices,links,created_at,status: BUMP distinct OLD/NEW ask_id |
| fq2_asks_delete | BEFORE DELETE asks: BUMP(OLD.ask_id), including foreign-key cascades if introduced by supported migration |
| fq2_answers_insert | BEFORE INSERT ask_answers: BUMP NEW.ask_id and every existing victim ask_id matching NEW.message_id OR (NEW.ask_id,NEW.seq) |
| fq2_answers_update | BEFORE UPDATE ask_answers (all columns): BUMP OLD/NEW ask_id and every existing victim matching NEW.message_id OR (NEW.ask_id,NEW.seq) |
| fq2_answers_delete | BEFORE DELETE ask_answers: BUMP OLD.ask_id; covers explicit and cascading deletion |
| fq2_receipt_insert | AFTER INSERT ask_fulfillments: BUMP NEW.ask_id before the new implementation verifies/stamps it |
| fq2_receipt_immutable | BEFORE UPDATE OF ask_id,request_digest,receipt_id,receipt,namespace,operation_id,core_digest: abort `fulfillment-history-protected` |
| fq2_receipt_delete | BEFORE DELETE ask_fulfillments: abort `fulfillment-history-protected` |
| fq2_store_id_update | BEFORE UPDATE of kv's key/value affecting OLD or NEW key ask_store_id: abort `fulfillment-history-protected` |
| fq2_store_id_delete | BEFORE DELETE kv WHERE OLD.key=ask_store_id: abort `fulfillment-history-protected` |
| fq2_store_id_insert | BEFORE INSERT kv WHERE NEW.key=ask_store_id AND that key exists: abort `fulfillment-history-protected`, including REPLACE |

The exact identity table is `kv(key TEXT PRIMARY KEY,value TEXT NOT NULL)` in Store.SCHEMA. Its initial identity creation precedes trigger installation; UPDATE matching either OLD.key or NEW.key, INSERT OR REPLACE, and DELETE are all covered.
All 12 hashed ask fields are enumerated above. Eligibility adds status; identity adds ask_id and global ask_store_id. Answers include ask_id,seq,kind,operator,message_id,text,at,choice, including notes and changes to ordering/consumed-ID membership.
truncated/card_parts/attempt/outcome/decided_by/updated_at/refreshed_from/last_activity do not enter this binding or eligibility; activity-only updates must not dirty a receipt. They still retain their original behavior.
Victim checks are bounded by the two current answer uniqueness constraints, at most two distinct victims plus OLD/NEW. This explicitly covers REPLACE conflict deletions even if a legacy connection has recursive_triggers off; do not rely on its implicit DELETE trigger firing. No foreign-key exists on ask_answers at this baseline; any later cascading schema must demonstrate the same coverage before enrollment.
Mutation triggers make old binaries invalidate valid immediately in the transaction that changes binding/eligibility. A crash/rollback cannot leave new answers with an old suppressing cache. Old code may not write verification stamps; its valid=1 writes alone cannot restore new-code suppression.
Global identity changes or receipt deletion are refused rather than silently losing immutable evidence. Direct trusted-host tampering, disabling schema guards or arbitrary hostile same-UID SQL is not a security guarantee of this design.

### 4.2 Integrity gate, startup and repair

Before each suppression-bearing count/list/view and each new fulfillment mutation, validate meta identity/shape and the exact finite DDL set inside the same Store snapshot. Immutable identical-receipt readback is not a new mutation and does not require derived validity. Missing/modified triggers/tables/indexes or missing/malformed meta produce fixed `fulfillment-projection-unavailable`; no capacity suppression is allowed while asynchronous work proceeds.
If the projection is damaged, capacity_count/list fall back to the conservative unsuppressed predicate: each existing ask with original status-active OR any retained receipt is counted once, without consulting stamp/meta/generation tables. The original core receipt table must remain readable; failure of the base store itself is an ordinary store error, not an empty count. This fallback is never below the valid projection count, preserves original approval-limit behavior, and does not refuse approval posting merely because the optional projection is damaged. Only fulfillment mutations/verified lifecycle capabilities HOLD; readable immutable receipt identity and legacy inspection remain available. Never recreate missing triggers and keep old stamps trusted.
Normal startup performs only bounded schema/meta validation, starts with unverified history capacity-active, and schedules bounded verification. It does not hash all histories synchronously before starting unrelated services.
An unmigrated v1 store is a distinct mode: the new Store constructor must detect without changing it. Legacy read-only Ask/Get inspection remains available; fulfillment and new posting paths return fixed fulfillment-migration-required. No ordinary daemon/CLI open runs the new projection migration. This deliberate temporary pre-migration posting refusal differs from the post-migration damage fallback above.
The dedicated local operator command is `admind ask fulfillment migrate --plan --json` or `admind ask fulfillment migrate --apply --json`; unknown/mixed modes refuse. Plan reads schema/counts only. Apply is solely an explicit deployment step after authenticated deployment authority, supported writer quiescence and complete coherent database backup/rollback receipt have been recorded by the deployment controller; the command is not an authority substitute and enabling a producer is separate. Apply rechecks exact v1 or exact already-migrated schema after the supported stopped-writer checks and under SQLite BEGIN EXCLUSIVE for the migration, refuses unknown layouts, installs only additive tables/indexes/triggers plus fresh epoch atomically, and emits old/new schema hashes and backup/authority receipt references. Repeated exact migrated apply is readback-only; damaged v2 requires explicit repair, not implicit migration. No new enforcement primitive or deployed migration command is claimed here. Historical receipt bytes and original DDL stay intact; no full-history hash or per-row stamp update is required.
Schema creation/index construction can itself take time proportional to retained data: measure it offline on the actual migration inventory and approve its downtime separately. It is not routine daemon-start work.
Repair after schema damage requires approved stopped-writer repair/rollforward. Restore the expected schema and replace epoch atomically; every old stamp becomes unusable before any suppression. Do not infer missing mutations from an unchanged binary or reuse an epoch after repair.

### 4.3 Finite resumable verification

Each pass visits at most 20 receipt IDs using indexed keyset selection and persists its cursor in projection metadata separately from immutable history. Dirty work and epoch-unverified work each receive at least one slot when both exist, preventing a busy dirty ask starving old history.
A record is processed at most once per pass. No fresh attempt is an assertion that a previous attempt did not happen. Verification has no external effect or notice resend.
Bound each ask to at most the source MAX_ANSWERS=50 answer/note rows, canonical ask+answer input <=8 MiB and receipt bytes <=128 KiB; batch total input including receipt bytes <=20 MiB. These deliberately generous finite bounds accommodate legitimate source maxima rather than the rejected 256-KiB design. At the pinned source, MAX_REQUEST=262144 bytes, MAX_REPLY=1048576 bytes and binding.HISTORY_BYTES=460800 bytes. Sixfold JSON escape allowance for request/history plus MAX_REPLY envelope allowance is 6*(262144+460800)+1048576=5386240 bytes, below 8 MiB; this covers four-byte UTF-8 and six-byte control-character escapes, existing body/title/choice/link maxima and bounded history metadata. Fixtures must construct maximum accepted histories using both Unicode and escaping, plus maximum metadata accepted by the pinned binding budget; no fixture silently shrinks source limits. More than two maximum-sized units still make bounded progress across passes; stop selection before exhausting batch bytes and preserve its next cursor. First use indexed LIMIT 51 and SQLite byte-length checks before loading fields. Reject malformed UTF-8/surrogates and oversized canonical serialization conservatively. No truncation or SELECT-all fallback.
Rows exceeding any bound are marked too-large at their observed generation and remain capacity-active with a fixed manual-HOLD diagnostic. They are skipped until generation/epoch changes or an explicit bounded verification request; other IDs continue. Manual resolution needs a separately approved higher-bound/archival design, not journal edits or consent fabrication.
Read/hash one bounded binding through existing Store.read_snapshot() on a single dedicated worker thread, never Store.transaction(read_only=True) on the event loop or the live Store lock. Its independent read-only WAL connection has the existing one-second connection timeout. A brief writer transaction rechecks epoch, exact schema and generation before publishing verification-row stamps/validity and removing that exact dirty generation. A concurrent mutation leaves it unverified; do not loop until it becomes quiet.
The existing SQLite busy timeout remains 5 seconds; no await, network, transport or hash loop occurs under the writer lock. A pass's work limits bound input and iterations, not OS scheduling time or cryptographic protection against root.
Schedule one coalesced verification worker after migrated startup and after a new-code dirty insertion; legacy SQL dirtiness is detected by an indexed poll at most every 30 seconds while idle. While backlog remains, wait one second between completed passes; failures use fixed 30-second backoff with an inspectable verification-unavailable diagnostic. Never spin, start overlapping workers or cancel/abandon a still-running transaction thread. Each pass has a ten-second cooperative deadline checked between bounded ask units; timeout retains completed stamps/cursor, reports degraded and backs off. Hashing one bounded unit or OS/SQLite scheduling may exceed that deadline; no false hard real-time guarantee is claimed. In a healthy fixture where each pass completes within ten seconds and inputs stop changing, both dirty/epoch queues receive at least one slot per pass and N receipts converge within 30+11*N seconds. Contention, oversized/corrupt rows or unstable generations can extend convergence; counts stay conservative and diagnostics remain available.
Progress/cursor/stamp writes are atomic and restartable. An interrupted pass repeats only pure verification. Conflicts never become completed merely because a later startup ran.
Known rollback compatibility is limited to the exact predecessor product source `07637745fe75dc614109a0b8ba72d3489f262a97` and this merged disabled core `a73e91d367bd626556371f33a46e25f003243c6e`, only after real offline forward/backward fixtures execute those exact pinned Store and Lifecycle implementations against the migrated database, including actual a73 Store construction and its positional eight-value receipt INSERT, legacy ask/answer writes and trigger invalidation. A simulated equivalent schema or mocked constructor is insufficient. The new implementation must validate the original core DDL separately from additive projection DDL so its own old-v1 detection does not auto-migrate. No arbitrary old binary is declared compatible.
Rollback stops the activated writer, preserves the whole database and projection schema, and restores approved code/config only. The pre-core binary counts answered asks again; the core can see conservative invalid bits. Forward startup validates all trigger/schema bytes and verifies dirty/unverified records before suppressing them. Never restore a stale backup over genuine new history.

## 5. COUNT and lock placement (finding 8)

Replace both daemon post-capacity materializations with capacity_count(), retaining the identical shared predicate and checks before and after every relevant await. No full bodies/answer rows are materialized merely to compare MAX_OPEN=20.
