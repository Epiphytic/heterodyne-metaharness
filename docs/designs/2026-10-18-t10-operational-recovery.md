# T10 operational recovery amendment — initial design

Author: Codex. Design task: btq-7wvub. Status: UNREVIEWED, NOT APPROVED, NOT IMPLEMENTED. This document proposes an amendment; filing it as an ADR does not enact it. One actual Claude Opus HIGH design review is to be followed by one author incorporation and a separate genuine human design decision through Marmot. Deployment remains a separate decision.

## 1. Problem, authority and scope

The retained T10 seventh code review reported REVISE, including two critical operational defects: an approved publication whose Store result cannot be reconciled can hold an adapter forever; a lost native-create or admind-post reply can be called ASK_UNPOSTABLE even when a real approval exists. The controller disposition accepts both and holds activation. This proposal does not erase that review, approve its code, or clear another finding.

The governing source is Plan4c commit `4ac749bd5722be8c1baa96e38cadbf9bbb2687e1`, `docs/superpowers/plans/2026-10-13-plan4c-managed-installs.md`, E13 and Task 10. The implementation inspected is immutable `167b1b9783b760b25f8180485bcb7482b7deef59`; it is a source contract, not proof that publication is deployed. Its Store can recover its own intent and return an outcome, but has no inspection/quarantine operation. Its existing AskCancel does not correlate lost posts or undo a native approval decision.

Human approval of this amendment would enact only these changes:

1. Replace Task 10's `outcome(None) -> failed` rule with an explicit unresolved HOLD. Missing evidence, malformed evidence, wrong-name publication and transient read failure do not prove failure or absence.
2. Add bounded exact-operation inspection and positive settlement. Add exact-CAS, Marmot-authorized quarantine which transfers protection of an enumerable artifact set to the Store before releasing the adapter-wide recovery hold.
3. Replace E13's claim that a wrong-state row always becomes failed and a later install creates another approval with truthful creation/post/withdrawal outcomes and source-owned correlation. New unknown outcomes cannot silently generate a replacement operation.
4. Add Journal, Store/helper and admind protocol support specified below. Amend Task 10's closed command/action lists accordingly. No service installation, scheduler rearm, runtime selection, removal, physical rollback or native approval-bead edit is authorized by a recovery command.

E13's prohibition on native approval-bead writes after creation is explicitly retained. T10 never closes, reopens, edits, denies or approves its original approval bead. A recovery authorization is a separate, controller-created genuine approval, read by T10; the ordinary controller/admind decision machinery may write that authorization under its existing authority. This is not permission for T10 to impersonate the controller. Native approval and an operational recovery disposition are separate facts.

## 2. Closed operator interface

The proposed CLI is `wsctl harness recovery inspect <staging-id>`, `... settle <staging-id> --expect <snapshot-digest>`, `... prepare-quarantine <staging-id> --expect <snapshot-digest>`, and `... quarantine <recovery-id> --approval <bead-id>`. Approval lifecycle uses `... approval-status <staging-id>` and `... withdraw <staging-id> --expect <row-digest> --approval <bead-id>`. These are proposed commands, not current instructions to execute.

All identifiers use existing closed staging/bead grammars or a generated UUID; no SQL, filesystem path, adapter-wide wildcard, command text or arbitrary failure reason is accepted. Unknown/duplicate JSON fields, wrong types, oversized input and ambiguous identifiers refuse before writes. JSON request cap is 16 KiB; response cap is 1 MiB. A command names one staging row, not a batch. Repeating an operation ID with identical intent returns its durable result; different intent is a conflict. A human authorization cannot be reused for another row or changed snapshot.

Inspection performs no mkdir, migration, sweep, recover, publish or repair. It returns a typed result: `complete`, `busy`, `unavailable`, `incomplete` or `conflict`, with bounded constant reasons. Only complete yields a usable snapshot. Snapshot fields bind schema, stable Journal/store identities and configured Store root identity, row revision, staging ID, adapter, expected canonical install, manifest digest, original approval bead/context digest, creation/post/withdrawal states, operation/event revisions, exact Store evidence descriptors and active selection/launch references. Observed timestamps are separate from the canonical digest. Raw package text, answer text, secret material and arbitrary paths are withheld from ordinary output; the bounded local evidence artifact is permission 0600 and still scanned before any Marmot rendering.

Store inspection uses an existing-root fd, no-follow opens and its shared lock; Journal reads use a consistent read transaction. Since these are different locks, inspection rechecks both versions before returning. A change returns conflict, never a mixed snapshot. Lock acquisition is bounded at five seconds; the whole inspection has a 30-second monotonic deadline. Up to 4096 namespace entries, 256 evidence records and 1 MiB of metadata may be examined; each metadata file is at most 64 KiB. Counts beyond a cap, invalid filenames, symlink traversal, conflicting roots, unreadable entries or unknown schemas return incomplete. No recursive package-content walk is required or allowed in this diagnostic call. Rehash/verification needed for positive publication uses the existing Store verification bounds and may return unavailable, without weakening proof.

The exact Store namespace includes staged manifests, staging roots/build locks, publishing intents, published receipts, failure records, relevant adapter metadata and candidate install roots. Inspection is confined to the configured Store and derives paths from validated identities. An arbitrary user-provided path is never an artifact. Complete enumeration requires the Store's own records and identity checks to close every implicated reference, including a wrong-name receipt. A directory name alone does not establish ownership. A missing/malformed reference whose possible target cannot be bounded makes the set incomplete, not empty.

## 3. Positive settlement without new effect authority

`settle` compares the snapshot while holding the T10 operation lock, then obtains the Store's current, locked evidence. The Journal CAS requires the same operation revision and an unresolved/approved state. Its result records before/after snapshots and evidence hashes once.

| Store evidence | Permitted result |
| --- | --- |
| Matching durable publication receipt for this staging, exact adapter/install/manifest and published state, validated by Store | Journal `published`, with the actual receipt reference. No second publication. |
| Valid staged manifest matching the original approved digest and intact original E13 approval | Existing idempotent Store recovery/publication, with the same staging ID and original digest; ordinary issuance and readback rules apply. |
| Store-owned durable failure for this exact operation | Journal `failed`, with that constant and receipt. |
| None, wrong name, unknown schema, changed snapshot, I/O failure, broken/publishing state | Keep recovery HOLD. Report the actual reason; no invented failure, absence or receipt. |

Existence, process death, age, a timeout and a human assertion that installation probably failed never qualify as positive publication/failure evidence. No positive settlement bypasses original selection/runtime checks. Reconciliation of an already issued publication is not permission to publish different content.

## 4. Authenticated quarantine, protection before release

Quarantine is an administrative disposition of uncertainty, not a declaration that an effect did not happen. It does not delete or move package trees, manufacture a publication receipt, undo native approval, or mark uncertain content safe. It terminally fences this staging operation and conservatively excludes every implicated artifact from selection, launch, ordinary remove/prune and staging sweep. A separate future reviewed disposal/recovery operation is required to release those artifact protections. This initial amendment does not add it.

`prepare-quarantine` CAS-reserves a recovery UUID in the Journal and fences new publication for that staging. It must refuse if a live local publication is in flight; it never stops a thread or releases a live Store lock by timeout. Under the Store lock it records a durable, idempotent preparation for that UUID, snapshot and exact enumerable artifact set. This preparation protects the set against publish/recover/sweep/remove/verify rewrites while awaiting a decision. Crashing during preparation leaves conservative protection/adapter HOLD; it cannot make an object collectible. The supported inspection command shows the preparation and its completion status.

The controller requests a genuine Marmot approval for the prepared intent. The full consent scope binds recovery UUID, row/store identities, original approval and manifest, original unresolved reason, exact artifact descriptors and preparation digest, adapter hold to be released, and these exclusions: no deletion, selection, publication, native-bead mutation or proof of absence. T10 reuses `approval_readout`, `queue.show`, the existing `ask_digest`, and `approvals.verdict` with an exact recovery effect predicate; it requires current authorized approver, closed authentic approval and matching posted/approved/context digests. The exact reviewed intent is in the native ask refs/body; no new digest algorithm or author-created approval artifact substitutes for the existing machinery. If normal rendering/secret/size limits cannot present the complete material scope, no executable approval is requested until the controller supplies a supported complete immutable readout. Recovery requests must remain usable through existing Marmot even if install publication is held; they do not depend on the broken install card becoming terminal.

`quarantine` checks that genuine decision outside local locks. It then reacquires locks in the fixed order: T10 operation lock, Store lock, short Journal transaction. No network/native read occurs under those locks. It rechecks the prepared snapshot and revisions; any changed intent or artifact identity invalidates the authorization and keeps HOLD. The Store owner writes and fsyncs an immutable quarantine record, plus durable artifact protection indexes, before returning a quarantine receipt. The receipt binds UUID, preparation/intent digests, Store identity, exact artifact identities and original staging. Only then may the Journal CAS record terminal `quarantined`, its receipt and decision provenance and stop treating this row as adapter-wide OPEN.

There is no cross-database atomic transaction. The ordering is the safety proof: before the Store receipt, the row still blocks the adapter; after the Store receipt but before Journal CAS, both protections apply. On restart, an exact matching quarantine receipt can complete that CAS without another human approval or reissuing effects. A changed/missing/corrupt receipt keeps HOLD. The Store must load quarantine protections before any startup recovery, sweeping or mutation. An unrecognized/corrupt protection record fails closed for the affected Store; an ordinary old client/helper may not operate around it.

Artifact descriptors include validated relative slot, root device/inode and evidence hashes, with explicit absent-at-preparation slots where needed. A replacement at a protected slot is a conflict and remains protected, not a way to evade the record. Unknown aliases, incomplete artifact enumeration or an unbounded set cannot be quarantined to release the adapter. The command emits a durable bounded diagnostic and a controller escalation identifier. The controller uses Marmot for a separately scoped recovery plan (for example restoring a trusted Store backup); manual DB edits, selecting a different root and terminal consent are not substitute authority. If admind is unavailable, keep HOLD and read-only diagnostics while restoring that actual approval channel. There is no automatic timeout escape.

Quarantine does not remove launch/selection protection. A current/previous selection, unresolved launch or live session referencing an implicated install remains held through the existing pin/in-use checks and the new Store protection check. Only unrelated, positively verified installs can be selected once the adapter hold is released. With the same-UID LocalStore fallback this is a trusted-process convention, not isolation against the service user; helper ownership remains stronger but is not proof against root or disk loss.

## 5. Truthful approval outcomes and source-owned mapping

The Journal gains a durable operation UUID and explicit creation/post states before external issuance: `not-issued`, `issuing`, `confirmed`, `refused`, `unknown`; confirmed creation carries exact bead/context, and confirmed post carries exact ask ID and source receipt. `refused` means a parsed authoritative pre-effect refusal, not socket timeout, invalid JSON, process timeout, Journal failure or disconnected reply. These leave unknown/issuing and preserve the original intent. `approval_result` and CLI report those distinctions. Restart must not turn a staged row with possible external issuance into ASK_UNPOSTABLE.

Native create remains at most once automatically. Before calling create, persist its operation identity and exact immutable ask intent; include the correlation identity as non-decision metadata at creation. An exact native receipt plus readback can adopt a committed create. A lost receipt triggers bounded read-only correlation lookup (maximum 100 candidates with explicit completeness). No match is not proof that a timed-out create was not committed; no second create is allowed merely from absence. Multiple matches/conflicting digest remain HOLD. An operator may authorize adoption of one exact positively identified matching bead through Marmot, without editing it. Truly unresolved creation requires separately scoped native recovery; this amendment does not invent a native idempotency API.

For admind, add a proposed closed source-owned `approval.operation.v1` protocol with `post`, `status`, `withdraw` modes. The key is the durable T10 operation UUID under a pinned source identity plus Journal identity; the bound payload is exact bead ID/context digest and intent hash. The service UID remains a trusted producer boundary, not a new unforgeable enrollment mechanism. No caller-supplied decision, operator name, answer, DB path or arbitrary scope is trusted. This protocol is separate from unrestricted title-based lookup and is not claimed to exist today.

Under admind's existing post serialization and one SQLite transaction, bind that key to an ask row and its durable outbox parts BEFORE enqueue. Exact repeats return the original ask/status/receipt without creating, refreshing, superseding or consuming another capacity slot. A changed payload is refused. `status` reads that exact mapping, including a terminal tombstone. A committed key/ask mapping survives a lost reply. A request with a missing key can be repeated safely with the same key only through this idempotent server; the client never falls back to legacy AskPost. The protocol must never bypass current principal policy, membership/readout gates, limits or redaction. Capacity refusal is truthful pre-effect only if no mapping/outbox was committed.

`withdraw` first CAS-fences publication in the T10 Journal, under the same lock used by `advance`, recovery and settle. A terminal/fenced row cannot publish on a later approval. If publication already issued, withdrawal returns recovery-required and does not claim to revoke that effect. Only a non-issued or safely reconciled operation can proceed as a no-publication withdrawal.

Then admind atomically binds a withdrawn tombstone to the operation key, even if the original post has not arrived. A delayed post with that key cannot create a card. If its ask is open/answered, cancellation and the existing durable notice are performed in the same transaction after a fresh status CAS. The decision worker must use the same state transition guard immediately before claiming `deciding`; no stale AnswerRow can commit after cancellation. If deciding/uncertain or a native commit is already issued, do not cancel or assert denial: return decision-in-flight, preserve the fence and reconcile native readback. If already approved/denied/stale/blocked/superseded/cancelled, return the actual status and immutable answer/decision references; never rewrite approval as cancellation. Any late completed approval is recorded as a real approval for a withdrawn local operation and cannot reactivate it.

A withdrawal authorization names this operation/key, row revision, existing bead/context and known ask mapping, and explicitly says it does not revoke native consent or undo publication. It uses the same genuine Marmot validation as quarantine. The existing generic AskCancel remains compatible but is insufficient proof of this end-to-end withdrawal. The new source mapping is retained as a tombstone while its T10 operation or approval can be replayed; no automatic expiration erases idempotency. Storage capacity exhaustion returns a bounded visible HOLD before a new operation; archival requires exact export/identity retention and separately approved retention policy. Journal/store/admind loss never permits a new UUID to masquerade as retry of the old operation.

## 6. Persistence, locks, migration and implementation boundaries

Journal migration adds operation UUID/revision, truthful creation/post/withdrawal phases, recovery preparation and receipt references; immutable harness_events retain before/after digests, actor/authority references, actual constants and timestamps. Store adds versioned preparation/quarantine records and protection lookup used by publish/recover/sweep/remove/selection verification. Store Protocol, HelperStore/LocalStore and `store_core` request decoding gain identical typed inspect/prepare/quarantine operations. The helper checks peer UID and configured Store exactly as today; it verifies preparation/token CAS itself, while genuine Marmot decision validation belongs to T10. This is not independent helper authentication of a human. Unsupported old helper versions refuse the new feature; no fallback bypasses quarantine.

Adminds's AskRequest/Store migrations add the scoped operation mapping and CAS transitions used by both withdrawal and the decision worker; existing ask rows, answers, attempts, outbox and notices remain canonical. No second question/decision database is introduced. WSD's queue port gains only bounded read-only correlation lookup needed to adopt known creates, with explicit incomplete results; no raw native SQL or writing repair helper. CLI/control schemas gain only the closed commands above. Unit/type fixtures must exercise both Store backends and actual message codecs.

Operation locks precede Store locks; Journal transactions are short and never span socket/network work. Adminds's state CAS and outbox transaction use its own serialization, never call back into WSD. Pending Journal fences remain authoritative across those separate domains. Competing settle/quarantine/withdraw/publish commands serialize by operation and exact revision; a second command gets conflict or its identical recorded result. Startup reconstructs fences before pickup and isolates per-row errors; global untrusted Store protection metadata remains a global Store HOLD. No PID/timeout-based lock clearing.

Migration leaves an old uncertain row unresolved with an explicit `legacy-unmapped` state; it does not infer not-issued from an empty ask_id or absence of receipt. Positive old receipts may settle under section 3; a legacy unknown artifact set uses section 4 only if a complete inspection is possible. A legacy uncorrelated lost create/post cannot be automatically replayed or silently relabeled as a new operation. Operator adoption must name its authentic existing evidence. Downgrade after writing quarantine or new mapping formats is unsafe: stop publication and restore a compatible verified binary, keeping databases, quarantines, IDs and history. Do not roll back only the schema or erase protective records.

## 7. Offline acceptance and activation gates

Implementation must first show failing regressions using temporary Journal/LocalStore/helper sockets and fake queue/readout/admind ports. No test calls real bd, native queues, services or operators. Required cases:

- Positive matching publication, failure and staged idempotent recovery; None, wrong-name receipt, broken state, transient EIO, malformed and over-cap evidence remain truthful HOLD.
- Inspection is byte-for-byte nonmutating, bounded and rejects symlinks/path traversal/duplicate keys; changed Journal/Store versions cannot produce a complete mixed snapshot.
- Crash after each preparation/protection/receipt write and before/after Journal terminal CAS; protected artifacts survive restart and ordinary sweep/remove/prune. Failed fsync never releases the adapter. Unknown set cannot release it. Replacement/alias/conflicting root cannot evade protection.
- Stale or forged authority, wrong scope/digest/approver, reused authorization, changed artifact and concurrent publication refuse. A current/live launch remains protected. Unrelated verified install selection becomes possible only after the exact quarantine receipt is durable.
- Create committed/reply lost with matching receipt adopts once; no receipt, multiple matches, truncated lookup and a delayed completion cannot cause another create. Empty ask_id does not imply no effect.
- Post committed/reply lost, key repeated/rebound, capacity/latch refusal, malformed reply, Journal write failure and restart preserve exact mapping. One durable key produces at most one logical ask and no new limits bypass.
- Withdraw-before-post, answer race, stale decision worker, deciding/native-commit race, late approval, notice failure and response loss preserve actual statuses and the local no-publication fence. A cancellation never becomes evidence that publication was undone.
- Both Store backends encode the same operations; old helpers refuse; read-only clients and manual legacy ask consumers remain compatible; missing migration or protection metadata fails closed. Concurrency tests verify bounded lock waits and absence of network work under locks.

Design approval authorizes implementation only. Activation requires separately reviewed source, configured typing/lint and named offline acceptance, an isolated crash/restart demonstration of both Store backends, exact deployed code/helper/admind schema compatibility, verified backup/restore, and a separate Marmot deployment request linking this amendment and actual deviations. No active operation is disposed during deployment. Inventory all legacy unknown rows first and retain holds unless a supported receipt/adoption/quarantine path applies.

The other R7 findings remain activation prerequisites, not solved by this amendment: taint alert races; non-published selector handling; bounded responsive HARNESS_LANE scheduling; process-group Git deadlines; executable bytecode provenance; startup JournalBusy isolation; repeated in-use scans and cleanup debt. Their actual dispositions remain intact. This proposal does not claim deployment acceptance, turn on timers or start the 72-hour release clock.

## 8. Human decision and honest limitations

The eventual Marmot design request must explicitly approve section 1's four amendments, conservative quarantine/protection before adapter release, source-owned post/withdrawal mapping including decision races, legacy HOLD treatment and the trusted service-UID residual. It must link this exact immutable design and original Plan4c. No reviewer result or author signature is human consent. Any deployment request is separate.

Known bounded limit: an unenumerable or lost-evidence operation may still require a separately scoped restoration/recovery plan. This is an explicit, observable escalation path, not an automatic clearing command. Quarantine may retain artifacts indefinitely; this design deliberately provides no disposal authority. Same-host backups do not survive host loss, and a process crash test does not prove power-loss durability. Restoring receipt/source identity is a prerequisite to recovery, never permission to invent one.
