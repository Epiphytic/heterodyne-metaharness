# T10 operational recovery amendment — incorporated proposal

Author: Codex. Design task: btq-7wvub. Status: ONE HIGH REVIEW REVISE; findings incorporated once; NOT HUMAN APPROVED, NOT IMPLEMENTED. The actual review and ten ordered dispositions are retained under `docs/reviews/7wvub-*`. No second design review or validation is requested or claimed. This canonical proposal and its ADR-path pointer do not enact an ADR or approval. A separate genuine human design decision through Marmot and separate deployment decision remain required.

## 1. Problem, authority and scope

The retained T10 seventh code review reported REVISE, including two critical operational defects: an approved publication whose Store result cannot be reconciled can hold an adapter forever; a lost native-create or admind-post reply can be called ASK_UNPOSTABLE even when a real approval exists. The controller disposition accepts both and holds activation. This proposal does not erase that review, approve its code, or clear another finding.

The governing source is Plan4c commit `4ac749bd5722be8c1baa96e38cadbf9bbb2687e1`, `docs/superpowers/plans/2026-10-13-plan4c-managed-installs.md`, E13 and Task 10. The implementation inspected is immutable `167b1b9783b760b25f8180485bcb7482b7deef59`; it is a source contract, not proof that publication is deployed. Its Store can recover its own intent and return an outcome, but has no inspection/quarantine operation. Its existing AskCancel does not correlate lost posts or undo a native approval decision.

Human approval of this amendment would enact only these changes:

1. Replace Task 10's `outcome(None) -> failed` rule with an explicit unresolved HOLD. Missing evidence, malformed evidence, wrong-name publication and transient read failure do not prove failure or absence.
2. Add bounded exact-operation inspection and positive settlement. Add exact-CAS, Marmot-authorized quarantine which transfers protection of an enumerable artifact set to the Store before releasing the adapter-wide recovery hold.
3. Replace E13's claim that a wrong-state row always becomes failed and a later install creates another approval with truthful creation/post/withdrawal outcomes and source-owned correlation. New unknown outcomes cannot silently generate a replacement operation.
4. Add Journal, Store/helper and admind protocol support specified below. Amend Task 10's closed command/action lists accordingly. This includes early protection at HOLD inception, durable Store generations, publish issuance/fencing and an incompatible Store epoch migration as explicit new design scope. No service installation, scheduler rearm, runtime selection, removal, physical rollback or native approval-bead edit is authorized by a recovery command. The epoch migration itself is a separate deployment operation, never a recovery command.

E13's prohibition on native approval-bead writes after creation is explicitly retained. T10 never closes, reopens, edits, denies or approves its original approval bead. A recovery authorization is a separate, controller-created genuine approval, read by T10; the ordinary controller/admind decision machinery may write that authorization under its existing authority. This is not permission for T10 to impersonate the controller. Native approval and an operational recovery disposition are separate facts.

## 2. Closed operator interface

The proposed CLI is `wsctl harness recovery inspect <staging-id>`, `... settle <staging-id> --expect <snapshot-digest>`, `... prepare-quarantine <staging-id> --expect <snapshot-digest>`, and `... quarantine <recovery-id> --approval <bead-id>`. Approval lifecycle uses `... approval-status <staging-id>`, `... prepare-withdraw <staging-id> --expect <snapshot-digest>`, `... bind-approval <recovery-id> --approval <bead-id>`, and `... withdraw <recovery-id> --approval <bead-id>`. Both preparation commands export a T10-composed immutable authorization intent; bind-approval records its one native authorization bead after exact readback. The original install approval may be absent for a withdrawal; the separate recovery authorization is never absent. These are proposed commands, not current instructions to execute.

All identifiers use existing closed staging/bead grammars or a generated UUID; no SQL, filesystem path, adapter-wide wildcard, command text or arbitrary failure reason is accepted. Unknown/duplicate JSON fields, wrong types, oversized input and ambiguous identifiers refuse before writes. JSON request cap is 16 KiB; response cap is 1 MiB. A command names one staging row, not a batch. Repeating an operation ID with identical intent returns its durable result; different intent is a conflict. A human authorization cannot be reused for another row or changed snapshot.

Inspection performs no mkdir, migration, sweep, recover, publish or repair. It returns a typed result: `complete`, `busy`, `unavailable`, `incomplete` or `conflict`, with bounded constant reasons. Only complete yields a usable snapshot. Snapshot fields bind schema, stable Journal/store identities and configured Store root identity, row revision, staging ID, adapter, expected canonical install, manifest digest, original approval bead/context digest, creation/post/withdrawal states, operation/event revisions, exact Store evidence descriptors and active selection/launch references. Observed timestamps are separate from the canonical digest. Raw package text, answer text, secret material and arbitrary paths are withheld from ordinary output; the bounded local evidence artifact is permission 0600 and still scanned before any Marmot rendering.

Store inspection is a new dedicated read-only dispatch, before and separate from the old `handle` recover/sweep prologue. It uses the already migrated existing Store root, no-follow opens and its shared lock; it cannot initialize or repair it. Journal reads use a consistent read transaction. The snapshot includes the durable Store generation and dirty/complete flag described in section 6. Inspection reads Journal revision J1, Store snapshot generation S1, Journal revision J2, then Store generation S2 with no prologue; it returns complete only if J1=J2 and S1=S2 and the Store generation is complete. Otherwise it returns conflict/incomplete. This establishes one overlapping consistent observation, not a cross-store transaction. No re-enumeration is substituted for a missing generation. Lock acquisition is bounded at five seconds; the whole inspection has a 30-second monotonic deadline. Up to 4096 namespace entries, 256 evidence records and 1 MiB of metadata may be examined; each metadata file is at most 64 KiB. Counts beyond a cap, invalid filenames, symlink traversal, conflicting roots, unreadable entries or unknown schemas return incomplete. No recursive package-content walk is required or allowed in this diagnostic call. Rehash/verification needed for positive publication uses the existing Store verification bounds and may return unavailable, without weakening proof.

The exact Store namespace includes staged manifests, staging roots/build locks, publishing intents, published receipts, failure records, relevant adapter metadata and candidate install roots. Inspection is confined to the configured Store and derives paths from validated identities. An arbitrary user-provided path is never an artifact. Complete enumeration requires the Store's own records and identity checks to close every implicated reference, including a wrong-name receipt. A directory name alone does not establish ownership. A missing/malformed reference whose possible target cannot be bounded makes the set incomplete, not empty.

## 3. Positive settlement without new effect authority

`settle` first obtains any original E13 readout, queue.show and digest recomputation outside local locks. The retained observation binds the exact original bead, recorded context, complete original approval payload, read time and operation revision; it expires after 30 monotonic seconds. It then follows section 6 lock order and compares the expected Journal revision, fence and Store generation against the snapshot. No native read occurs inside those locks. A matching readout is an observation of genuine consent, not a transactional lock on the native queue: native consent may change immediately after that read; this existing distributed boundary is disclosed, never described as atomic revocation. Any changed local revision/Store evidence or expired/incomplete observation refuses. An unresolved/approved row is held throughout; before every actual publication call it must durably CAS `publish_phase=issuing` with a unique attempt ID under the same operation revision and Store hold (section 6). Its result records before/after snapshots and evidence hashes once.

| Store evidence | Permitted result |
| --- | --- |
| Matching durable publication receipt for this staging, exact adapter/install/manifest and published state, validated by Store | Journal `published`, with the actual receipt reference. No second publication. |
| Valid staged manifest matching the original approved digest and intact original E13 approval | Existing idempotent Store recovery/publication, with the same staging ID and original digest; ordinary issuance and readback rules apply. |
| New typed, positive pre-intent refusal receipt for this exact operation, with verified no publication issuance | Journal `failed`, with the constant, provenance and receipt. |
| None, wrong name, unknown schema, changed snapshot, I/O failure, broken/publishing state | Keep recovery HOLD. Report the actual reason; no invented failure, absence or receipt. |

Store evidence becomes a closed tagged result: `published` (exact verified receipt), `staged` (valid exact manifest), `positive-refusal` (new durable receipt written at the pre-intent refusal boundary, with operation/attempt, manifest, generation, constant and no-publication provenance), `recovery-abandonment`, `unreadable`, `unknown`, or `conflict`. Only positive-refusal permits terminal failure, and only if the Journal/Store issuance records agree that no publication could have issued. Existing untyped `.failed` records, `_recover_one` synthesized RECOVERY_FAILED, `_abandon`, `_state` broken and `_outcome` INSTALL_BROKEN never become positive-refusal. Historical provenance that cannot be proved stays unknown/HOLD; no migration manufactures it from absence.

Existence, process death, age, a timeout and a human assertion that installation probably failed never qualify as positive publication/failure evidence. No positive settlement bypasses original selection/runtime checks. Reconciliation of an already issued publication is not permission to publish different content.

## 4. Authenticated quarantine, protection before release

Quarantine is an administrative disposition of uncertainty, not a declaration that an effect did not happen. It does not delete or move package trees, manufacture a publication receipt, undo native approval, or mark uncertain content safe. It terminally fences this staging operation and conservatively excludes every implicated artifact from selection, launch, ordinary remove/prune and staging sweep. A separate future reviewed disposal/recovery operation is required to release those artifact protections. This initial amendment does not add it.

Protection starts BEFORE approval or HOLD becomes visible, not at quarantine preparation. The new `arm-hold` Store operation records and fsyncs the staging/operation identity, known exact references and unresolved slots before the Journal CAS can enter approved/HOLD. All `_recover`, `_recover_one`, `_abandon`, `_sweep`, `_remove_install`, publish and verification-rewrite paths check this index before mutation, including the ambient handle prologue. Ambient recovery skips protected operations; only a revision-bound explicit T10 recovery command may advance them. Selection/launch also reject protected artifacts. If ownership cannot be enumerated yet, a conservative Store-wide protection prevents ambient mutation/selection until complete inspection, rather than treating unknown slots as absent. Failure to persist protection leaves the adapter held and the Store unavailable for ambient mutation. Startup/migration enroll all legacy approved/unresolved rows before enabling ANY prologue or tick; the deployment must stop old Store clients first (section 6).

`prepare-quarantine` CAS-reserves a recovery UUID in the Journal and upgrades the existing hold to a no-new-publication fence for that staging. It must refuse if a live local publication is in flight; it never stops a thread or releases a live Store lock by timeout. Under the Store lock it records a durable, idempotent preparation for that UUID, snapshot and exact enumerable artifact set. This preparation protects the set against publish/recover/sweep/remove/verify rewrites while awaiting a decision. Crashing during preparation leaves conservative protection/adapter HOLD; it cannot make an object collectible. The supported inspection command shows the preparation and its completion status.

T10 itself uses existing `approvals.compose` to construct the complete canonical recovery title, description, metadata.ask and exact effect from the preparation. It exports those bytes plus the refs and computes their existing queue.ask_digest outside locks; a short CAS records the composed bytes, digest and recovery UUID against the unchanged preparation. Complete scope includes recovery UUID, row/store identities, original approval (or explicit absent/unknown), manifest, unresolved reason, exact artifact descriptors, preparation digest, hold to release and exclusions: no deletion, selection, publication, native-bead mutation or proof of absence. If existing rendering/secret/size rules cannot present that complete scope, preparation is non-executable; no partial ask or alternate caller-authored effect text is accepted.

The controller creates the separate genuine Marmot authorization from this exact exported intent. `bind-approval` reads that native bead outside locks, verifies its title/description/metadata.ask byte-for-byte against T10's retained composition, recomputes its digest and CAS-binds exactly one bead ID to this recovery UUID. A conflicting ID never substitutes for it. `quarantine` and `withdraw` accept only that bound ID and call existing approval_readout, queue.show, ask_digest and `approvals.verdict(Expected(recorded_bead, recorded_digest, exact_effect), ...)`; they compare the full retained payload as well as predicate 10. They never obtain Expected.context_digest from the candidate bead itself. A genuine denial records a terminal denied recovery UUID; it cannot be rebound or automatically re-prepared against the same snapshot. Any later human reconsideration is an explicit new intent referencing that denial, not an automatic retry. T10 does not create or edit the authorization bead. Original install approval lifecycle remains untouched. Recovery cards use existing Marmot independently of whether the install card can become terminal.

`quarantine` checks that genuine decision outside local locks. It then follows the fixed order: all affected workstream guard locks in deterministic workstream order, per-staging operation lock, Store lock, short Journal transaction. Section 6 defines the direct LocalStore transaction and the HelperStore receipt-then-CAS variant; the client never holds a Store lock while calling the helper. No network/native read occurs under those locks. It rechecks the prepared snapshot and revisions; any changed intent or artifact identity invalidates the authorization and keeps HOLD. The Store owner writes and fsyncs an immutable quarantine record, plus durable artifact protection indexes, before returning a quarantine receipt. The receipt binds UUID, preparation/intent digests, Store identity, exact artifact identities and original staging. Only then may the Journal CAS record terminal `quarantined`, its receipt and decision provenance and stop treating this row as adapter-wide OPEN.

There is no cross-database atomic transaction. The ordering is the safety proof: before the Store receipt, the row still blocks the adapter; after the Store receipt but before Journal CAS, both protections apply. On restart, an exact matching quarantine receipt can complete that CAS without another human approval or reissuing effects. A changed/missing/corrupt receipt keeps HOLD. The Store must load quarantine protections before any startup recovery, sweeping or mutation. An unrecognized/corrupt protection record fails closed for the affected Store. Section 6 defines the incompatible configured-root epoch which makes the pinned old binary refuse instead of silently ignoring the new records.

Artifact descriptors include validated relative slot, root device/inode and evidence hashes, with explicit absent-at-preparation slots where needed. A replacement at a protected slot is a conflict and remains protected, not a way to evade the record. Unknown aliases, incomplete artifact enumeration or an unbounded set cannot be quarantined to release the adapter. The command emits a durable bounded diagnostic and a controller escalation identifier. The controller uses Marmot for a separately scoped recovery plan (for example restoring a trusted Store backup); manual DB edits, selecting a different root and terminal consent are not substitute authority. If admind is unavailable, keep HOLD and read-only diagnostics while restoring that actual approval channel. There is no automatic timeout escape.

Quarantine does not remove launch/selection protection. A current/previous selection, unresolved launch or live session referencing an implicated install remains held through the existing pin/in-use checks and the new Store protection check. Only unrelated, positively verified installs can be selected once the adapter hold is released. With the same-UID LocalStore fallback this is a trusted-process convention, not isolation against the service user; helper ownership remains stronger but is not proof against root or disk loss.

## 5. Truthful approval outcomes and source-owned mapping

The Journal gains a durable operation UUID and explicit creation/post states before external issuance: `not-issued`, `issuing`, `confirmed`, `refused`, `unknown`; confirmed creation carries exact bead/context, and confirmed post carries exact ask ID and source receipt. `refused` means a parsed authoritative pre-effect refusal, not socket timeout, invalid JSON, process timeout, Journal failure or disconnected reply. These leave unknown/issuing and preserve the original intent. `approval_result` and CLI report those distinctions. Restart must not turn a staged row with possible external issuance into ASK_UNPOSTABLE.

Native create remains at most once automatically. Before calling create, persist its operation identity and exact immutable ask intent; include the correlation identity as non-decision metadata at creation. An exact native receipt plus readback can adopt a committed create. A lost receipt triggers bounded read-only correlation lookup (maximum 100 candidates with explicit completeness). No match is not proof that a timed-out create was not committed; no second create is allowed merely from absence. Multiple matches/conflicting digest remain HOLD. An operator may authorize adoption of one exact positively identified matching bead through Marmot, without editing it. No native idempotency API is invented. Unknown native creation does not prevent the local no-publication exit below; any uncorrelated native effect remains an honest orphan/unknown diagnostic, not proof of absence.

For admind, add a proposed closed source-owned `approval.operation.v1` protocol with `post`, `status`, `withdraw` modes. The key is the durable T10 operation UUID under a pinned source identity plus Journal identity; the bound payload is exact bead ID/context digest and intent hash. The service UID remains a trusted producer boundary, not a new unforgeable enrollment mechanism. No caller-supplied decision, operator name, answer, DB path or arbitrary scope is trusted. This protocol is separate from unrestricted title-based lookup and is not claimed to exist today.

Under admind's existing post serialization and one SQLite transaction, bind the key to the original bead and its WHOLE ask lineage, current revision, all ask IDs/refreshed_from links and durable outbox parts BEFORE enqueue. Exact repeats return the original ask/status/receipt without creating, refreshing, superseding or consuming another capacity slot. A changed payload is refused. `status` reads that exact lineage mapping, including a terminal tombstone. R29 refresh and commit_approval must check the bead-to-key mapping and tombstone in the same state transition transaction, carry the key onto every descendant and refuse refresh/new supersession when withdrawn. A legacy AskPost for a bead already bound to a key is refused; it may not create a competing unkeyed card. Existing unrelated legacy asks remain compatible. Migration must enumerate all existing same-bead lineage rows or refuse enrollment as incomplete; no oldest/current-only shortcut. A committed key/ask mapping survives a lost reply. A request with a missing key can be repeated safely with the same key only through this idempotent server; the client never falls back to legacy AskPost. The protocol must never bypass current principal policy, membership/readout gates, limits or redaction. Capacity refusal is truthful pre-effect only if no mapping/outbox was committed.

`withdraw` first durably CAS-fences the operation under its operation lock; every publication path checks this revision. Journal phases distinguish `never-issued`, `issuing` (attempt UUID and exact Store token committed BEFORE invoking either backend), `published`, `positive-refusal`, `unknown`, and `fenced`. An exception/timeout after issuing remains unknown, never reverted to never-issued. The Store implements `fence-publication(operation, expected_generation, fence_id)`: under its exclusive lock it durably installs a fence checked before `_publish`, explicit recovery and every delayed helper request. If a publish wins that lock, the fence returns its actual published/unknown evidence and cannot certify withdrawal; if the fence wins, a waiting/delayed publish is refused. Only an exact durable Store `fenced-no-publication` receipt, establishing no committed/pending ambiguous publication or explicit safely cancelled pre-effect intent, allows terminal no-publication withdrawal. Unknown Store evidence retains protection and uses quarantine/settle; the Journal alone is not enough. No process is killed to obtain a fence.

For creation/post `issuing` or `unknown` rows with no known original bead, a supported local withdrawal is still possible: prepare-withdraw binds the operation/snapshot with original bead and mapping explicitly absent or unknown, obtains its separate genuine Marmot authorization, then records the Journal fence and the Store no-publication receipt. This does not require finding the original bead first. The original staged/posted expiry policy also applies to issuing/unknown creation/post rows, but only via this durable local publication fence, Store receipt and source-key tombstone; an issued publication never expires as absent. A local terminal `withdrawn-no-publication`/`expired-no-publication` result releases the name/adapter reservation, retains all evidence and does not assert native cancellation. Any bead discovered or created later is recorded as an orphan approval for that fenced operation and can never reactivate it. Legacy unmapped posts may remain visible remotely; this is disclosed, not a reason to fabricate their cancellation.

Then admind atomically binds a withdrawn tombstone to the operation key, even if the original post has not arrived. A delayed post with that key cannot create a card. Every open/answered ask in the bound bead lineage is cancelled with the existing durable notice in the same transaction after fresh state CASes. No sibling refresh can remain answerable. The decision worker must use the same state transition guard immediately before claiming `deciding`; no stale AnswerRow can commit after cancellation. If deciding/uncertain or a native commit is already issued, do not cancel or assert denial: return decision-in-flight, preserve the fence and reconcile native readback. If already approved/denied/stale/blocked/superseded/cancelled, return the actual status and immutable answer/decision references; never rewrite approval as cancellation. Any late completed approval is recorded as a real approval for a withdrawn local operation and cannot reactivate it.

A withdrawal authorization names this operation/key, row revision, existing bead/context and whole known ask lineage, or their explicit unknown/absent state, and explicitly says it does not revoke native consent or undo publication. It uses the same genuine Marmot validation as quarantine. The existing generic AskCancel remains compatible but is insufficient proof of this end-to-end withdrawal. The new source mapping is retained as a tombstone while its T10 operation or approval can be replayed; no automatic expiration erases idempotency. Storage capacity exhaustion returns a bounded visible HOLD before a new operation; archival requires exact export/identity retention and separately approved retention policy. Journal/store/admind loss never permits a new UUID to masquerade as retry of the old operation.

## 6. Persistence, locks, migration and implementation boundaries

Journal migration adds stable Journal identity, per-staging operation UUID/revision, creation/post/withdrawal and publish phases/attempt IDs, hold/fence/preparation references, canonical recovery composition/digest, one bound authorization bead and receipt references. Immutable harness_events retain before/after digests, actor/authority references, constants and times. Store Protocol, HelperStore/LocalStore and store_core decoding gain identical closed `inspect`, `generation`, `arm-hold`, `fence-publication`, `prepare-quarantine` and `quarantine` operations, plus typed outcome provenance. All request checks precede mutation. The helper verifies UID, configured Store, exact CAS and tokens; genuine Marmot validation belongs to T10, not independently to the helper.

Store epoch 2 has a stable random Store identity and durable monotonic generation with a complete/dirty phase. Under its exclusive lock EVERY mutation (including ambient recovery/sweep, protection, failure/receipt, stage, publish, verify rewrite, removal and maintenance) first fsyncs a new dirty generation, then performs writes and fsyncs completion. A crash leaves dirty, not an old apparently current generation. A read never repairs it; explicit owned recovery can complete it while protections remain. Generation reservation failure prevents the mutation. No receipt is valid for a different Store identity/epoch; counters cannot wrap/reset on restore without explicit compatible recovery.

The pinned 167b1b9 `_open_store` only opens its configured path with O_DIRECTORY|O_NOFOLLOW; metadata unknown to it cannot fence it. Therefore epoch 2 requires a deployment-only incompatible layout transition, not a silently added JSON flag. With all old clients/helpers stopped and fds closed under exclusive administrative maintenance, retain a verified backup, rename the existing root to a reserved owner-controlled sibling payload directory and replace its original configured logical path with a private regular epoch descriptor. The descriptor binds schema/Store UUID, one validated sibling basename (no arbitrary path/symlink), device/inode identity and migration ID; new clients open that exact existing payload fd using no-follow identity checks. Missing/incomplete/malformed descriptor refuses; no mkdir, v1 fallback or automatic empty Store creation is allowed. The pinned old `_open_store` fails O_DIRECTORY on the regular descriptor, covering old locked handlers and unlocked read_staged/open_install/read_meta. The new lock is taken inside the payload; no process can retain the old root lock/fd across deployment. If interrupted before descriptor commit, deployment remains stopped/HOLD and resumes the recorded migration, never starts either version in the intermediate layout. Directly configuring an old binary to the hidden payload remains outside the trusted same-UID administrative boundary; no claim of hostile-UID isolation is made. Rollback must restore a compatible epoch-2 binary and retain protections, not point an old helper at the payload. This layout/consumer migration is a human-disclosed deployment prerequisite, not authority in a recovery command.

Admind's AskRequest/Store migrations add the scoped operation mapping and CAS transitions used by both withdrawal and the decision worker; existing ask rows, answers, attempts, outbox and notices remain canonical. No second question/decision database is introduced. WSD's queue port gains only bounded read-only correlation lookup needed to adopt known creates, with explicit incomplete results; no raw native SQL or writing repair helper. CLI/control schemas gain only the closed commands above. Unit/type fixtures must exercise both Store backends and actual message codecs.

Full local lock order is: affected workstream guard locks sorted by workstream ID, one per-staging operation lock, Store lock, short Journal transaction. Inspection's shared Store reads follow the same bounded discipline without mutation. Never acquire a guard from inside an operation/Store/Journal lock. Existing `_guarded` remove/prune and all publish/settle/quarantine/withdraw/selection paths must use this order. Waits are bounded at five seconds per attempt and 30 seconds overall; busy is visible and leaves protection intact. No PID/timeout lock clearing.

This requires refactoring the CURRENT global HarnessOps RLock: it becomes registry/short in-memory bookkeeping only, not an operation lock around advance. Each row is selected/read briefly, then native/readout/git/admind I/O runs with no local lock held. The per-staging lock is a new bounded registry-owned lock shared by all local paths. A row revision captured before external reads is checked in the final posted→approved CAS along with the unchanged fence, exact retained composition/manifest, current Store generation and observation deadline. Guard acquisition happens before that operation lock; Store arm-hold precedes the final Journal approved CAS. No helper/socket/native call occurs while a Journal transaction or global RLock is held. A Store operation takes/rechecks its own Store lock; T10 passes exact expected generation/operation/fence and does not recursively acquire that lock via a helper. For LocalStore, a direct transaction-scoped owner API can hold Store→Journal while calling only fd-local code; HelperStore instead returns an immutable generation-bound protection/fence receipt, followed by Journal CAS. Separate domains are not falsely called atomic: failure between Store and Journal retains both holds. Publication's durable issuing CAS is written under operation lock and Journal transaction, transaction closes, then Store publish acquires its own lock and validates token/fence. This never holds Journal while acquiring Store. Admind's CAS/outbox serialization never calls back into WSD.

Migration leaves an old uncertain row unresolved with an explicit `legacy-unmapped` state; it does not infer not-issued from an empty ask_id or absence of receipt. Positive old receipts may settle under section 3; a legacy unknown artifact set uses section 4 only if a complete inspection is possible. A legacy uncorrelated lost create/post cannot be automatically replayed or silently relabeled as a new operation. Operator adoption must name its authentic existing evidence. Downgrade after epoch migration or writing quarantine/new mapping formats is unsafe: stop publication and restore a compatible verified epoch-2 binary, keeping databases, quarantines, IDs and history. Do not roll back only the schema or erase protective records.

## 7. Offline acceptance and activation gates

Implementation must first show failing regressions using temporary Journal/LocalStore/helper sockets and fake queue/readout/admind ports. No test calls real bd, native queues, services or operators. Required cases:

- Positive matching publication, failure and staged idempotent recovery; None, wrong-name receipt, broken state, transient EIO, malformed and over-cap evidence remain truthful HOLD.
- Inspection has its own no-prologue dispatch and is byte-for-byte nonmutating, bounded and rejects symlinks/path traversal/duplicate keys; changed Journal/Store generations or dirty state cannot produce a complete mixed snapshot. Unknown generation refuses.
- At HOLD inception, unrelated handle list/outcome/recover/sweep/remove and failing recovery cannot erase evidence; every ambient/direct Store entrypoint checks protection. Inject transient EIO, missing record and malformed intent: synthesized failed/broken evidence remains HOLD, never positive-refusal.
- Execute the exact pinned old store_core against the epoch-2 configured root: every handler plus unlocked staged/open_install/meta entrypoint refuses without changing payload. Exercise interrupted layout migration, generation/fsync failure and old-fd retirement before startup.
- Crash after each preparation/protection/receipt write and before/after Journal terminal CAS; protected artifacts survive restart and ordinary sweep/remove/prune. Failed fsync never releases the adapter. Unknown set cannot release it. Replacement/alias/conflicting root cannot evade protection.
- Stale or forged authority, wrong scope/digest/approver, reused authorization, changed artifact and concurrent publication refuse. A current/live launch remains protected. Unrelated verified install selection becomes possible only after the exact quarantine receipt is durable.
- Create committed/reply lost with matching receipt adopts once; no receipt, multiple matches, truncated lookup and a delayed completion cannot cause another create. Empty ask_id does not imply no effect.
- Post committed/reply lost, key repeated/rebound, capacity/latch refusal, malformed reply, Journal write failure and restart preserve exact mapping. One durable key produces at most one logical ask and no new limits bypass.
- Withdraw-before-post, publish-helper-timeout-before-lock, publish-wins-lock, fence-wins-lock, answer race, stale decision worker, refresh/supersession across all lineage rows, deciding/native-commit race, late approval, notice failure and response loss preserve actual statuses and the Store-backed local no-publication fence.
- Beadless create/post unknown can reach locally terminal withdrawal/expiry with durable no-publication proof; delayed creates/cards are retained as orphan history. Denied recovery UUID cannot bind a second authorization; forged/understated composition or bead-supplied expected digest refuses. A cancellation never becomes evidence that publication was undone.
- Both Store backends encode the same operations; old helpers refuse; read-only clients and manual legacy ask consumers remain compatible; missing migration or protection metadata fails closed. Concurrency tests verify bounded lock waits and absence of network work under locks.

Design approval authorizes implementation only. Activation requires separately reviewed source, configured typing/lint and named offline acceptance, an isolated crash/restart demonstration of both Store backends, exact deployed code/helper/admind schema compatibility, verified backup/restore, and a separate Marmot deployment request linking this amendment and actual deviations. No active operation is disposed during deployment. Inventory all legacy unknown rows first and retain holds unless a supported receipt/adoption/quarantine path applies.

The other R7 findings remain activation prerequisites, not solved by this amendment: taint alert races; non-published selector handling; bounded responsive HARNESS_LANE scheduling; process-group Git deadlines; executable bytecode provenance; startup JournalBusy isolation; repeated in-use scans and cleanup debt. Their actual dispositions remain intact. This proposal does not claim deployment acceptance, turn on timers or start the 72-hour release clock.

## 8. Human decision and honest limitations

The eventual Marmot design request must explicitly approve section 1's four amendments, early HOLD protection, typed positive failure provenance, durable issuance/Store fences and generations, full-lineage post/withdrawal mapping, locally terminal beadless withdrawal, the incompatible Store layout/consumer migration, T10-produced recovery composition/single-bead denial binding, legacy HOLD treatment and the trusted service-UID residual. It must disclose that these are proposed APIs, the original install bead remains immutable to T10, and native consent observation cannot be atomic with local Store effects. It must link this exact immutable design and original Plan4c. No reviewer result or author signature is human consent. Any deployment request is separate.

Known bounded limit: an unenumerable or lost-evidence operation may still require a separately scoped restoration/recovery plan. This is an explicit, observable escalation path, not an automatic clearing command. Quarantine may retain artifacts indefinitely; this design deliberately provides no disposal authority. Same-host backups do not survive host loss, and a process crash test does not prove power-loss durability. Restoring receipt/source identity is a prerequisite to recovery, never permission to invent one.
