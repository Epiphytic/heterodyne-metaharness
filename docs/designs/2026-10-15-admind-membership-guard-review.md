**Round-2 findings, as d4 handles them:**
- **Finding 1 (blocker, fixed):** the outbox always sends the oldest pending row first (`store.py:463–468`), and `outbox_pass` stops as soon as that row can't go (`daemon.py:2898–2906`). d4 now moves held, quarantined, suppressed and not-yet-due rows into non-pending statuses that `next_pending` never selects. Membership notices are queued only when they are due, at most one unsent at a time. Tests 8 and 9 now put a blocked row first and check that later replies, notices and cards still send.
- **Finding 2 (major, fixed):** d4 allows `operators remove NAME` for a policy key that isn't confirmed. Today that is refused at `daemon.py:1641–1644`. A successful remove leaves the confirmed set unchanged, because the existing `applied()` set subtraction does nothing for a key that isn't in it. A later add confirms the key only if the add itself explicitly succeeds. A "duplicate add" error grants nothing. The last-confirmed-operator rule is kept. Test 12 covers this sequence.
- **Findings 3–6:** each is either built in (4: the provisional count is explicit and test 13 covers it) or listed as a PoC limit (3, 5, 6). Each deferral is reasonable and contradicts no operator decision.
- **Binding decisions:** joins, leaves, admin changes and count changes never latch. Authority is still confirmed keys ∩ freshly read policy. The only global latches left are the startup and migration recovery ones. Approval and identity checks are unchanged.

**Findings:** none block. Fold them into the implementation plan.

1. **[minor] Two kinds of notice share the `membership:` key prefix.** The result notice for a local add or remove is written as `membership:{change_id}` (`daemon.py:1740-ish`, in `settle_membership`). If the new send-time cadence check matches on that prefix, an "Operator X was added" notice could wait up to one cadence (60 s by default). **Remedy:** give event snapshots their own key prefix, so the cadence applies only to them.
2. **[minor] Chunks of one reply should be quarantined together.** `resolve_thread` sends a continuation chunk as a top-level post if its parent is not sent (`store.py:412–426`, fallback reasons "parent-pending" and "parent-failed"). **Remedy:** state that a reply's chunks (`<prefix>:<i>`) move into or out of quarantine as one group, so one chunk can never go out on its own.
3. **[minor] An unreadable policy will stall system messages too.** `outbox_pass` returns at the first row it can't send. So while the policy can't be read, a sender-bound row at the front also holds back the notices and approval cards behind it. This fails closed, which is acceptable for the PoC. **Remedy:** say so explicitly, or skip past blocked rows the same way as quarantined ones.
4. **[nit] The schema change needs a table rebuild.** The outbox `status` column has a fixed `CHECK` list (`store.py:50`). SQLite can't change that in place, so new statuses mean rebuilding the table inside one transaction. List that in the plan.
5. **[nit] Two count checks in the code must change or stay, and the plan should say which.** `rearm` refuses any count below 2 (`daemon.py:1793`), but d4 says rearm recovers at count 1, so that check changes. The `to < 2` floor in `change_membership` (`daemon.py:1688`) can stay.
6. **[nit] Nearly every old pending reply will be quarantined.** The inbound table stores no sender today (`store.py:370`), so old sender-bound rows can't prove who asked for them. Ask cards and reminders can usually recover their link through their deterministic keys. During deployment, report the held count before `admind rearm`; d4 already requires reporting held counts.
