# Fulfilled questions: release capacity without rewriting decisions (d1)

Design task: `btq-1b5km`. Author: Codex. Proposed, inactive, not implementation or deployment authority. This revision is for the controller's one Claude Opus HIGH design review, author fixes, then genuine human design approval through Marmot admind. No review or human approval is claimed here.

## 1. Problem, evidence and source boundary

At product source `07637745fe75dc614109a0b8ba72d3489f262a97`, `store.ASK_ACTIVE` includes `open`, `answered`, `deciding`, and `uncertain`; `asks.MAX_OPEN` is 20. Both question posting and native approval posting count those rows. Thus an answered question continues consuming capacity after its authorized operation is completed. An answer proves a human response, not performance of an operation.

The controller retained private before/after evidence for two explicitly fulfilled questions. Supported cancellation released their slots, and the exact original authenticated answers survived. This was a bounded historical repair, not a general rule that answered means completed. No raw private card text, operator messages or transcript is republished here. The source map records hashes of the bounded evidence, not its contents. Do not retrospectively relabel those cancellations as a new fulfilled operation.

The isolated task branch starts at old source `2c0c5b5b775ee652d2ce32c192091aa2314e5b32`. Operative research uses immutable product076 objects; no runtime code is being changed or represented as deployed by this design. Implementation must reconcile its actual claimed source against the mapped interfaces before editing. This proposal adds an admind capability; it is not installed today.

## 2. Chosen boundary and invariants

Use an append-only fulfillment overlay owned by admind, not an additional wire status and not mutation of original decision data. A question's stored `status` remains `answered`. Fulfillment means that the exact response-bound requested operation was completed, as attested by a trusted local controller, or explicitly confirmed completed by a currently authenticated operator. It means neither approval revocation nor new consent.

The following bytes remain immutable: original ask fields, card/source identity, creation time, ordered answers (including original operator, source message ID, time, text and choice), native approval pins, completed-operation receipt and original operation history. A fulfillment receipt references these facts. It never sets an answer, rewrites `outcome`/`decided_by`, changes a Bead, reruns an operation, renews an approval, or declares an unknown effect successful.

V1 eligibility is only `kind=question`, `status=answered`, at least one retained authenticated `kind=answer` row and no prior fulfillment. Merge and native approval asks retain their current workflows; native `approved` is already terminal. An empty note, delivery receipt, title, local poster string, thumbs-up without its retained authenticated source, or question choice alone cannot establish completion. Unanswered, deciding, uncertain, denied, blocked, stale, superseded and cancelled asks cannot be fulfilled. Historical cancelled-but-answered rows are not silently migrated.

## 3. Authority and operation correlation

Two explicit routes are proposed; neither runs automatically merely on answer arrival.

1. **Trusted controller completion:** a local controller calls the proposed fulfillment endpoint with the exact intent and terminal operation receipt. The service must check Unix peer UID equals the configured service UID using kernel credentials; unavailable credentials fail closed. This is a new required check, not a claim about today's `ctl.Peer`, which exposes only PID for audit. UID/PID are recorded by the server, never accepted from JSON. Same-UID controller processes are trusted administrators; this is not process enrollment, cryptographic producer authentication, or resistance to a malicious same-UID process. `actor_label` is audit text and confers no authority. The receipt is explicitly a trusted controller's completion attestation; admind does not independently prove all external effects.
2. **Operator confirmation:** a currently authenticated Marmot operator can explicitly confirm a staged exact fulfillment intent using a proposed fixed `!fulfill <ask-id> <full-intent-sha256>` verb. The command is accepted only through the existing verified group/principal-policy path, not raw terminal text or a claimed operator name. It confirms completed work, not permission to perform work. The response says so. This is a recovery alternative, not a new required human approval for each normal completion. It creates no new capped ask and therefore remains available at capacity20. If Marmot authentication/transport is unavailable, retain the pending record and diagnose; no chat or terminal human-consent substitute.

Before either route, the caller supplies a completion receipt with closed schema: `schema=operation-completion-v1`, operation ID (1–128 ASCII `[A-Za-z0-9._:-]`), producer namespace (1–64 same grammar), exact ask identity, exact consumed-answer digest, requested-operation digest, original authority digest, `state=completed`, terminal result digest, and up to eight immutable evidence references. Each reference is an opaque registered artifact ID (1–128 same grammar) plus SHA256, not an arbitrary path, URL fetch, command, JSON expression or native database query. The registration/receipt adapter resolves IDs within its admitted local receipt root using bounded regular-file reads, rejects symlinks/path traversal, and verifies bytes. No network verification or subprocess occurs inside admind's transaction. Adapter implementation and exact actual completion-receipt schema of the owning controller must be source-pinned in the implementation task; no current producer API is invented here.

A producer may have a terminal receipt for a completed denial/no-op decision. Its requested-operation digest must explicitly identify that disposition, not an omitted side effect. A partial operation, operation-issued marker, timeout, transport success, shell exit without required readback, or uncertain outcome is not `completed`. For existing workflows without a machine-correlated receipt, use operator confirmation of an exact staged intent and declared evidence; do not manufacture a receipt adapter or auto-complete. Both routes preserve the distinction between operator response and operation completion.

The caller must identify which exact retained answer(s) its existing policy consumed. Multiple/conflicting answers are not resolved by this endpoint. Its full ordered-answer digest is a concurrency fence; a newly arrived answer invalidates the prepared intent. Existing operation policy remains responsible for whether the consumed answer was authorized. Fulfillment cannot make an invalid operation valid or repair missing historical consent.

## 4. Canonical identities and proposed API

Add a durable random `ask_store_id` to admind metadata exactly once, transactionally, with no invented historical ask identity. Existing database backup/restore must retain it. Bind every new receipt to `{ask_store_id, ask_id, created_at, ask_sha256}`. Canonical ask bytes include kind, poster, title, body, PR/head, bead/digest, form/choices/links and original creation time using a versioned deterministic JSON encoding. Exclude mutable status/activity/delivery observations. The separate canonical ordered-answer digest includes all retained answer row fields and sequence; do not normalize original timestamps or text. Digests are SHA256 over canonical UTF-8 bytes with a domain/version prefix. Publish the exact encoding and golden fixtures in implementation; do not hash an unversioned display string.

Proposed commands and wire operations, not current commands:

- `admind ask fulfillment prepare --ask ID --receipt FILE --json`: bounded server-side preparation, returns canonical intent bytes, full digest and exact observations. FILE is a CLI-only input; the wire carries bounded validated bytes, never a daemon file path. Preparation writes one pending intent in admind so the operator alternative can refer to an exact known digest. It never changes capacity or sends a card.
- `admind ask fulfillment apply --intent FILE --json`: trusted-controller route. The wire carries the exact prepared bytes/digest. It cannot specify `operator`, peer UID, pass flag or successful after-state. Explicit application is required; prepare does not grant authority.
- `admind ask fulfillment get ID --json`: opt-in lifecycle read, includes original ask/answer identity, fulfillment receipt or null and a current capacity projection. It is diagnostic, not authorization. Missing ask is refused, never evidence of completion.
- `admind ask fulfillment reconcile --receipts MANIFEST --limit N --plan|--apply --json`: local client preparation described below. No unrestricted daemon directory scan or global auto-resolution.

`--receipt FILE`/`--intent FILE` readers enforce no-follow regular files owned by the local service user, maximum64KiB, and no credential-shaped public output. A single wire request is at most64KiB, within existing262144-byte outer bound; a single reply at most128KiB, within existing1MiB. Closed schemas reject duplicate JSON keys, unknown fields, unbounded integers, non-UTF8, NaN, overlong strings and recursive objects. User-provided titles/reasons are not trusted proof. Intent contains schema version, exact ask and full answers digest, exact receipt digest, expected fulfillment=null, resolution=`fulfilled`, route, and operation identity; the digest covers every field. Maximum eight evidence references and a 512-character redacted explanatory label. There is no arbitrary patch/status setter.

Use a dedicated tagged fulfillment request union and reply namespace inside the existing protected local socket, with strict dispatch and explicit client opt-in. Unknown operations on old servers fail visibly before changing state. Do not append fields to the existing `AskView`, `AskSummary` or `AskReply` without a separate negotiated version: old strict DTO consumers may reject them. The CLI's old post/get/wait/list/cancel output schema remains unchanged.

## 5. Atomic application, audit and idempotency

Reuse the existing Store transaction discipline (`RLock`, `BEGIN IMMEDIATE`, no await inside). Acquire the same daemon work lock that serializes answer/decision handling, then the posting lock when capacity-facing mutation is necessary; the implementation must establish one consistent order (work lock, posting lock, Store transaction), and no handler may acquire it in reverse. Preparation validates and persists a bounded pending intent; apply re-reads ask, all answers, intent and existing fulfillment inside the transaction. A server-side UID check happens before staging/applying local requests. Operator route revalidates current principal policy immediately before committing.

One transaction inserts the unique immutable fulfillment row, consumes its pending intent, inserts an immutable authority/before-after audit record, and queues at most one redacted fulfillment notice via the existing durable outbox. The authoritative audit record lives in the same Store transaction; the existing external audit log is a supplemental mirror. A failure to mirror after commit must not undo or repeat the terminal operation. Store audit records never include raw answer text, raw receipt bodies, secret tokens or arbitrary paths.

Receipt fields: schema, ask identity/digests, original `answered` status and original-answer count/digest, operation identity and receipt digest, route, server-observed UID/PID or verified operator source-message/principal identity, prior fulfillment=null, resulting lifecycle=`fulfilled`, before/after active-count observations, created UTC, full intent digest, and durable receipt ID. The count observations describe the transaction, not a permanent global count. Completed operation bytes remain with their original owner; admind retains its bounded digest-bound attestation and evidence IDs.

Enforce uniqueness on ask identity and on `(producer namespace, operation ID)`. An exact duplicate returns the same receipt with `already-applied`; differing bytes for either key refuse `conflict`, without another notice. Unknown socket response: query fulfillment by exact ask identity; identical receipt means committed, absence permits retry of the same intent, mismatch holds. Retry only the metadata commit, never the external operation. Crash before commit leaves no fulfilled projection; crash after commit leaves the receipt and outbox intent together. A new answer versus apply race is serialized: if answer commits first, apply refuses stale; if fulfillment commits first, subsequent answer/reaction is refused with “already fulfilled; original answer retained,” not appended or made active again.

## 6. Capacity, listings, repeat and consumer compatibility

Keep the existing ten wire status values and their meanings (four active plus six terminal). Define a separate query `capacity_active`: original status in ASK_ACTIVE AND no fulfillment receipt. Both post_ask and approval_post_refusal, their post-await rechecks, list grouping, in-flight counts, reminders, `!asks`, summary generation and scheduling queries must use this projection consistently. No per-row N+1 reads: indexed anti-join/NOT EXISTS on the receipt key. Native `deciding`/`uncertain` busy guards remain unchanged and can never be hidden by an ineligible fulfillment. MAX_OPEN20, MAX_PER_HOUR30 and MAX_IN_FLIGHT2 remain unchanged; fulfillment is not a new ask and does not refund the hourly post budget.

Original `get` returns `status=answered` and byte-identical answer fields after fulfillment; it is a response/authority history API, not a capacity query. Old `list` keeps its exact DTO and returns capacity-active plus20 newest inactive-or-fulfilled entries, with each ask once. A fulfilled entry has original `answered` status; this deliberate limitation is explained in CLI help. The new lifecycle command and human `!asks` line show `fulfilled` explicitly as a lifecycle label separate from wire status. Existing original status selectors used to inspect historical answers must retain raw-status semantics; add a distinct query for capacity rather than silently changing every `asks_with_status` call.

`!details`/explicit history lookup continue showing original card and response, plus a clearly separate fulfillment label/receipt ID in lifecycle-aware rendering. `!asks repeat`, automatic bumps and outstanding reminders exclude fulfilled asks. Explicit resend of an original fulfilled card is diagnostic only, labelled “fulfilled; no new answer or authority”; no active ask, new decision, operation or hourly-post reset is created. Current cancel refuses a fulfilled ask with a fixed explanation and receipt reference, preserving the receipt; never erase fulfillment via cancellation. Reopening requires a genuinely new request under ordinary policy, not deletion of the old receipt.

Consumer activation is an implementation acceptance boundary: inventory exact current wake/status parsers, Handoff/manage, supervisor and read consumers before rollout. Existing product clients continue accepting their current statuses without adding `fulfilled` as an unrecognized status. A wake bound to a completed operation must first check its own terminal operation receipt; the new lifecycle reader can suppress redundant wake work only after full identity matching. Legacy clients may still see `answered` and wake; that cannot authorize reexecution because original operation idempotency/readback gates remain mandatory. Where that property is absent, update and review the actual consumer before enabling automatic fulfillment for its producer. An unsupported producer stays manual; do not globally block unrelated eligible producers or infer a new response from lifecycle metadata.

The separate wake design at `59ffe75c32932b60597fd2c43a945a98e383957a` is a design contract, not evidence of an installed consumer. Its nine-row status table omits product `uncertain`; its unknown-status rule already holds observation without inferring resolution. The fulfillment adapter must preserve that fail-closed treatment: `uncertain` remains HOLD and capacity-active, never terminal or fulfilled. No wake design byte, enum or review requirement is changed here. Fulfillment preserves `answered` and all original answer bytes, so lifecycle metadata alone must not become a new answer fingerprint or wake authority. Record exact consumer compatibility in implementation evidence; core manual fulfillment does not depend on deploying the bridge.

## 7. Bounded reconciliation and recovery

No timer scans all answered questions and declares success. Reconciliation is a supported explicit local command using a caller-supplied bounded manifest of terminal operation receipts, default plan mode. N is1–20, manifest at most256KiB, maximum20 distinct asks and one intent per ask. It fetches the opt-in exact lifecycle view, validates receipt bindings, and emits one typed result per ask: `eligible`, `already-applied`, `stale`, `unsupported`, `incomplete`, `conflict`, or `unavailable`. A plan is not permission to execute the requested operation. Apply revalidates independently and runs one atomic metadata application at a time. Return partial outcomes and a stable continuation key; no automatic replay after uncertain response. Failure of one entry does not imply success of unprocessed entries. No general claimant impersonation or task status/dep modification is included.

Pending intents are capped at40 total, at most one current digest per ask, max64KiB each; replacements require explicit stale-intent disposal, preserve its digest audit and do not bypass count. Unapplied intents expire after24h using service UTC (expiry affects only ability to confirm, not answers/authority/operation); applied receipts do not expire. Cleanup and capacity checks run transactionally. At full pending capacity, read/get/apply existing and explicit stale cleanup remain available. Fulfillment metadata through the trusted local route remains available when the20-active cap or latch prevents new posts, analogous to existing local cancellation availability. The operator verb still requires current inbound authorization, including its latch/trust gates; it never bypasses an authentication failure. A latch therefore may defer that route while leaving trusted local receipt reconciliation available. No unsolicited new external ask is required to finish known work.

If an operation has unknown effects, keep its question active; reconcile the actual operation through its existing supported recovery path. Do not retry the operation to obtain nicer evidence. If a historical receipt is missing, use explicit authenticated operator confirmation of a digest-bound intent after actual investigation, or retain hold. Store corruption/loss freezes metadata application; restore the exact supported backup/catalog and original store identity before interpretation. Missing state is not negative proof, and does not permit ask-ID reuse or bulk completion.

## 8. Storage, migration and rollback

Use admind's existing Store, outbox, authenticated inbound messages and answer rows, not a second daemon or standalone completion database. Proposed additive tables: `ask_fulfillments` (unique ask identity and operation identity, immutable bounded receipt), `ask_fulfillment_intents` (bounded pending canonical bytes and state), and `ask_fulfillment_audit` (transactional bounded metadata per attempt/disposition). Add store identity/schema capability metadata and indexes. The exact DDL and migration guard must be reviewed with implementation. No backfill of old answered/cancelled rows. Migration must run before serving; failed migration leaves the old state intact and startup fails visibly. Read-only tools must not instantiate the mutating Store constructor to inspect a backup.

Retain fulfillment rows, identities and replay keys as long as their original asks remain retained; no deletion by age. Existing asks are not automatically pruned, so v1 does not claim bounded lifetime disk usage. Cap pending bytes as above; cap supplemental retry-audit entries per intent at8 with exact aggregate count and last fixed failure code thereafter. One authoritative immutable fulfillment record and one application audit always survive. Capacity-exhausted disk/Store errors refuse mutation and preserve evidence; a reviewed archive policy with immutable digest lookup is required before pruning replay keys. Do not silently rotate away authority to meet a storage number.

Deployment is a separate Marmot ask linking the approved design, reviewed source and deviations. Snapshot database coherently with its supported backup mechanism, code/config/schema capability and consumer versions; WAL is not a standalone database backup. Test restoration offline. Rollback stops the new writer, preserves the complete database and receipts, and restores reviewed old code/config: old code sees original answered rows and may again count them toward20, but cannot lose the answers or grant new consent. Do not restore an older database over later genuine answers/operations to regain capacity. Continued old operation may require manual hold for capacity; forward repair is safer. No timers, run/session/native task identity or deployment are changed by this design filing.

## 9. Required implementation evidence

Use named offline tests with temporary Store/files and fake Marmot/native/executor adapters; no live sender, service or model. Cover:

- 20 active asks including fulfilled candidates; successful fulfillment releases exactly one slot; unanswered and merely answered-without-completion never release; native approval post recheck uses same projection; hourly/in-flight caps unchanged.
- Exact original AskGet JSON/answers/source preserved; old strict DTO decode and all ten product status fixtures; new opt-in schema rejects unsupported versions; list/history dedup and explicit lifecycle label.
- Wrong ask/store/creation/body/answers/operation/authority/evidence digest; two answers/conflict; stale answer race; unknown/partial effects; missing/forged receipt; same operation reused on another ask; no arbitrary paths/symlinks or command execution.
- UID verification failure and wrong UID refused before mutation; labels never authenticate; real fake-transport inbound policy checks for operator confirmation, revoked principal, duplicate message and full digest mismatch. No terminal path can manufacture human consent.
- Atomic crash points before/after insert/audit/outbox and response loss; exact retry same receipt/no second notice; conflicting duplicate; audit mirror failure after commit; read-only query cannot change state; no external operation replay.
- At-cap/latched explicit recovery, bounded manifest partial outcomes and resumability; pending cap/expiry/stale cleanup; no automatic answer/time-based fulfillment; original cancelled evidence unchanged.
- Reminders/repeat/resend and stale wake consumers; own terminal operation receipt prevents reexecution; unsupported producer remains held without locking others; backup/restore/rollback retain all actual identities and answers.

These are future acceptance requirements, not tests run for this design. No routine second design review is requested; one HIGH review, incorporate findings, then genuine human design approval.

## 10. Human design decision and implementation sequence

The governing relay specification at product076, `docs/superpowers/specs/2026-10-05-admind-marmot-relay-design.md`, currently defines R15 active capacity directly by four statuses and R24 listing by active status. Human approval must explicitly amend those clauses to the separate fulfillment-aware capacity projection while preserving all numeric limits. It must also approve the narrow R13 qualification refusing additional answers after fulfillment, the new local trusted completion route with R16 residual trust disclosure, and the R17 local metadata-recovery exception described above. Native approval semantics R5–R12 and decision-attempt recovery R23/R26 are unchanged. These are proposed amendments in this same design decision, not a claim of existing authority or a redundant later approval layer.


The Marmot design ask must explicitly adopt: the fulfillment overlay instead of an additional wire status; original answers/status retained; routine trusted same-UID completion attestation with honest residual trust; opt-in new lifecycle API and unchanged old DTO; exact operation correlation and no execution inference; optional authenticated capacity-independent operator completion verb; bounded manual reconciliation and pending retention; producer-specific compatibility gate; and rollback's possible return of capacity pressure without loss of history. Approval authorizes implementation only, not runtime mutation, receipt migration, automatic scans, deployment or completion of particular historical requests.

Implement one coherent product task for schema/endpoint/CLI/operator verb/projections/tests. A concrete controller producer adapter and affected wake consumer belong in their actual repository task(s), each pinned to this design and exact real source; do not invent native target IDs or bundle unrelated Plan6/7/8 features. Land disabled capability first, review source under current operator code policy, prove offline compatibility, then request separate deployment with exact activated producers. No dependency on future Plan5/6 is required to implement the core manual/attested lifecycle. Existing future delivery/retention designs must reconcile their definition of active/settled before co-activation; this proposal does not silently amend their storage or consent contracts.
