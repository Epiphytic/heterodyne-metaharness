## Authority and revocation

Persisted `group_operators` is the set admind previously confirmed through its own successful local membership operations. Observation of events or counts never adds/removes a key. Effective authority is that persisted set intersected with freshly loaded policy keys. A key that left can remain confirmed; MLS protects later epochs, and policy removal explicitly revokes trust.

Read and validate policy at each message/reaction ingress and synchronously immediately before every side effect: command execution, agent paste, ask answer/approval decision, details request and every outbound chunk. Recheck after any intervening await, including waits for locks. Replace the cached effective set atomically only on successful policy parse. On read/validation failure, fail that gate closed and audit a fixed reason; never fall back to stale authority. No permanent latch for a transient policy read failure. A later successful read restores operation. Reads use the existing validated loader and never echo policy contents.

Requester identity must survive queues and restarts. Add durable sender provenance for accepted requests and explicit outbound ownership: sender-bound rows carry the authenticated requester key, including commands, agent replies, summaries, backstop batches, details and all continuations. Multi-request batches carry all constituent requester keys and send only while all remain current, or are rebuilt excluding revoked items without emitting them. System notices and approval cards explicitly carry system ownership. Never infer ownership from body text, a display name, a thread target or null alone.

Before each send load fresh policy, apply the normal live-subscription/group gate and validate each sender-bound owner against confirmed∩policy. Revoked rows become terminally suppressed with audit; they never enter a backstop/retry or block later notices. An unreadable policy temporarily blocks rows without discarding them. New schema must distinguish legacy/unknown ownership from system ownership. Legacy pending rows may recover exact provenance through durable request links; otherwise atomically move them to a distinct durable held/quarantined status without deletion or sending. Held/quarantined and terminally suppressed rows are excluded from `next_pending` selection; they must never remain selectable pending rows. Preserve their payload, threading, request links and original status in migration evidence. Recovery from quarantine is an explicit operator decision after provenance validation, never an automatic retry. A held row cannot block later command replies, notices, approval cards or other eligible rows. No migration may classify an unproven legacy row as system-owned. Preserve original records and report held counts. The already completed external effect cannot be undone by a policy edit during its execution; its next effect/send is checked afresh.

## Membership observation

Events for other groups are ignored and do not increment this group's generation/event counters. This group's five allowlisted membership/admin event kinds are audited, recorded in a bounded notice accumulator and request a coalesced check (one running plus one requested). They never latch, change authority or decide whose key changed.

Serialize all count reads/adoptions through a single count-check lock. A check captures subscription generation, acknowledgement and membership epoch. After the response, reject a superseded generation, changed epoch, active local transition or lost acknowledgement before adopting anything. A stale response changes neither count, notice accumulator nor group_ok/observing of the replacement subscription. A stable successful count >=1 adopts the numeric count and establishes group_ok; observation additionally requires the current acknowledged subscription. Equal count is successful too. Adoption changes `expected_members`, never `group_operators`. No event arithmetic is used to settle a local operation.

A failed count read or a reported count <1 leaves the group unverified, blocks side effects through the existing live-group gate, audits a fixed reason and retries on the existing bounded check schedule. It does not write a global latch. The current Python control contract does not prove a definitive removed-from-group signal; do not manufacture one from an arbitrary error code or zero fixture. If connectivity/membership cannot recover, notify local operator diagnostics and seek an operator recovery decision; never automatically call init or replace identity/history. This replaces d2's unsupported zero-count latch/new-group claim. The distinction is a temporary inability to send, not a latched state requiring a shell reset.

## Local add/remove and settlement

Keep transition_lock and the existing brief work/dispatch/send serialization while a local membership RPC executes. Adopt a fresh baseline count using the same validated check discipline; do not hold the count-check lock recursively. Membership events during the operation are accumulated and request a later recount, never latch or force an otherwise successful operation to fail.

Judge an operation solely by its own wn-agent response: explicit success commits the requested confirmed-set addition/removal and clears pending atomically; explicit peer failure aborts without changing the confirmed set. A post-call count may be adopted when stable, but cannot reverse either judgment. If there is no stable valid post-call count, the recorded expected count may become `pending.to_count` as a provisional local estimate after explicit success; it proves neither member identity nor current membership. Mark that estimate as provisional in state/audit. The next valid current-generation check replaces it, clears its provisional flag and never latches on a mismatch. Failed or unknown RPCs do not install a successful-operation estimate. An add of an already-confirmed key is permitted for recovery; explicit success is idempotent with respect to the set, and explicit rejection leaves it untouched. Do not infer 'already a member' from count alone. For a confirmed key, keep the last-policy-confirmed-operator removal prohibition; it is an authority safeguard, not proof of actual group membership. Also allow `operators remove NAME` when NAME is a freshly loaded policy operator but is not confirmed: resolve its exact policy key, issue the normal journaled remove RPC, and on explicit success leave the confirmed set unchanged (set subtraction is a no-op); explicit failure also leaves it unchanged. The last-confirmed-operator prohibition cannot apply to removing an unconfirmed key. Unknown results retain the same unresolved-transition hold. This permits recovery from an unknown add that actually succeeded even when wn-agent rejects duplicate adds. After explicit rearm clears that unknown transition, run remove for the unconfirmed policy key; on explicit successful removal run add, whose explicit success finally confirms it. If remove explicitly reports failure because the member was already absent, no key is granted; an add can then succeed normally. Generic failure is not treated as evidence of absence: another add may be attempted by operator choice but grants authority only on its own explicit success. Do not broaden removal to arbitrary supplied keys outside policy or infer authority from a duplicate-add error.

A timeout, broken connection, cancellation/exception after journaling or missing response is unknown, not success. Retain a durable unresolved transition, refuse further local membership changes, and report operator recovery needed. Release `changing` after in-process cleanup so existing confirmed-policy operators can keep commanding, answering and approving once subscription/group verification recovers. Do not silently retry the mutation or modify authority. A subscription replacement alone does not turn explicit success into failure; it leaves group verification false until the replacement is checked. Keep serialized count/membership epoch rules so a response read before the operation cannot overwrite the later count.

Startup with an unresolved pending mutation keeps the existing global unknown-state latch; recovery is explicit rearm. Round 2 finding 3 is deliberately deferred for this PoC: using the in-process membership-only hold across startup would improve availability, but changing that recovery invariant adds scope. Restart after an unknown local mutation therefore still requires rearm; no authority is granted or removed on startup. This is documented and tested, not a claim that all unknown mutations preserve availability across crashes. This conservative startup case and the unknown-authority migration case remain explicit exceptions, never triggered merely by a membership event/count mismatch. They are recovery safeguards, not membership observations. In-process unknown mutation has its own hold, not the global latch. No new global latch is introduced for local RPC ambiguity or subscription replacement.

## Rearm and remaining latches

Keep rearm's stable-subscription/event checks. With an existing readable confirmed set, rearm adopts a valid count >=1, keeps exactly confirmed∩fresh policy, clears pending mutation and global latch, then revalidates the subscription. It never adds a key based on count. Thus it can recover current count 3 without temporary policy edits and can recover at count 1. The operator still checks the real group's membership in their client first.

Before plan-2 migration, absent `group_operators` retains today's explicit unknown-authority latch. Migration of a single known operator retains existing behavior. Rearm may retain the existing count==1+all-policy migration assertion only when the confirmed record is absent and the operator explicitly invokes rearm after visual verification; this is a declared recovery assertion, not background discovery. Malformed persisted authority fails closed for operator repair; never silently replace it. Inventory all existing latch calls during implementation and demonstrate no membership/count/subscription path can invoke them. Remaining global latches: unknown-authority startup/migration; unresolved local mutation discovered at startup; any already existing non-membership integrity safeguard identified in that inventory. No automatic rearm.

## Bounded notices

Maintain one durable accumulator per group: first/last observed count, allowlisted event-kind flags, saturating event counters, pending flag and window sequence. Events are described as observed signals, never counts of distinct people. Counts only say 'from F to T; identities unavailable'. Equal-count join/leave and admin-only signals still produce a notice. Authority set preservation is explicit. Constant-size state prevents replay floods from growing storage; individual events retain existing audit treatment.

A timer on the existing group-check cadence flushes the accumulator even without further events. Do not put a future-due membership notice into the pending outbox. Under a shared notice enqueue/send serialization boundary, enqueue one snapshot only when no unsent membership notice exists and the most recent successful membership-notice delivery was at least group_check_seconds ago. Otherwise retain the constant-size durable accumulator and schedule its next eligible check. At most one undelivered membership snapshot exists in addition to that accumulator. The delivery path checks that serialized eligibility again; a clock rollback or recovered legacy row that is now not due moves the row out of selectable pending status into durable delayed state until due, rather than returning with it at the head of the outbox. Selection excludes all not-due delayed rows. Persist the last successful membership send timestamp and snapshot sequence atomically with marking that send complete; while a send outcome is unknown, keep its single snapshot unresolved and do not enqueue another one. Continue other eligible outbox rows through the existing per-row retry rules. A network retry may retain existing retry behavior, but cadence/quarantine alone must never block unrelated rows. Successful delivery releases the next accumulated notice only after a full cadence, so blocked posting cannot create a later burst. Do not clear accumulated state until the snapshot is durably queued, and do not discard newer signals while finishing an older snapshot. Restart-safe persisted sequence/timing uses wall-clock deadlines bounded by one cadence; tests cover restart and clock changes. A membership snapshot already enqueued is immediately eligible under ordinary conditions; there is no normal pending cadence wait. General ask/notice sends retain their existing rules. Count 1 does not prove absence of every operator; retain bounded notice state normally, with no new loop or speculative recipients.

## Explicit PoC limits from round 2

- Unknown local mutation followed by restart retains the existing startup latch and requires rearm (finding 3, deferred availability improvement).
- A confirmed-set membership prefilter may drop an unconfirmed sender before loading policy, because absence from that set is sufficient to deny; every potentially authorized ingress/effect still uses a fresh policy read (finding 5, optional optimization).
- Rearm can be repeatedly refused if another client keeps changing membership while the read is in flight (finding 6). Preserve its race guard for the PoC; do not claim eventual recovery under continuous adversarial churn.
- Provisional local count handling is now explicit (finding 4). Neither a provisional nor observed count is authority evidence.
