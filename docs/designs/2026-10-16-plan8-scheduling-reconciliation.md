# Plan8: deterministic scheduling, reconciliation and independent supervision

Author: Codex. Task: btq-8d487. Revision: d1, 2026-10-16.
Status: proposed design; no cross-model review or human approval yet.
Product source baseline: `07637745fe75dc614109a0b8ba72d3489f262a97`.

## 1. Purpose and authority

Keep unattended work moving through supported interfaces, and make a stalled control plane visible without using an LLM as a clock. This design chooses one recurring scheduling owner, defines the independent five-minute babysitter, and specifies installation and recovery boundaries. It does not install anything or certify an existing service as healthy.

The governing ADR is revision 17 at `a27acecee8274e6ad8dc65def436614d42b5cb04`, `docs/adr/0001-workstreams-v2.md`, especially §§3.3, 5, 6, 8, 9, 10 and 15–17. The genuine approval is `btq-ovngv`, approved by Liam at `2026-10-14T15:57:38Z` through Marmot relay identifier `189fd6bb97ba`, binding the full ADR object `a27acecee8274e6ad8dc65def436614d42b5cb04`. These exact authority facts were supplied by the controller; the author did not query the queue or reauthenticate the decision. Earlier preparation used revision `58615ac6...`; that remains historical research and is not substituted for the current approved object. Source text and a closed task alone are not approval authentication.

Only changed designs and deployments require new blocking human approvals under the operator's current direction. Ordinary implementation within an approved contract does not acquire a new approval per helper or scheduled invocation. Existing native approval, dependency, ownership, identity and finite review-budget gates remain in force. Questions and approval requests go through authenticated Marmot admind. An unavailable approval channel means hold and diagnosis; this design provides no terminal-conversation substitute for consent.

## 2. What exists and what this adds

At the baseline, `wsd/daemon.py:634–703` starts internal recurring pickup and reconciliation tasks. `wsd tick pickup|reconcile [--ws NAME]` already sends a control-socket request; the receiver serializes work on each workstream's existing lane and coalesces compatible jobs. Startup recovers every workstream before pickup. Shutdown drains admitted work and leaves agent scopes separate from the daemon unit. The existing `wsd/unit.py` renderer generates the daemon service, not the scheduling units proposed here.

ADR17 §9 instead names service-manager timers. Installing them on top of the current internal loops would create two recurring owners. The primary decision here is **systemd owns recurring wakes on the supported managed Linux installation**. WSD remains the only authority for pickup/reconciliation effects. It retains startup recovery, event-triggered work, per-workstream locks and quota deadline wakes. Quota wakes are distinct one-shot state-machine deadlines, not a second pickup backstop.

Proposed configuration, commands, schemas and units below are implementation contracts, not available APIs at 076. Plan5 executor integration, Plan6 presentation/reminder interfaces and Plan7 sufficiency are separate dependencies. This design neither implements nor approves those contracts. The initial implementation can deliver owner selection, pickup/reconcile timers, deterministic job admission and independent health reporting while unavailable jobs remain explicitly disabled.

## 3. Scheduling owners and job registry

| Job | Sole recurring owner and cadence | Effect owner | Activation condition |
|---|---|---|---|
| Pickup backstop | systemd, every 60 seconds | Existing WSD pickup lane | External-owner compatibility implemented and installed |
| Reconcile | systemd, every five minutes | Existing WSD recovery/runtime/native adapters | Same; unresolved target actions still require actual executor/reconciler support |
| Five-minute babysitter | Separate systemd oneshot/timer, every five minutes | Read-only health observation and durable alert writer | New Plan8 health snapshot contract and approved deployment |
| Forge poll | systemd, every 60 seconds | Future approved Plan5 intake adapter | Disabled until actual forge/intake contract is admitted |
| Reminder sweep | systemd, every 15 minutes | Future approved Plan6C policy and delivery ledger | Disabled until that exact contract is implemented and compatible |
| Daily digest | systemd calendar wake, default 08:00 UTC | Future approved Plan6 presentation/digest producer | Same; explicit installation timezone and configured civil time |
| User schedules | Disabled in v1; no timer rendered | No v1 command or file-Bead target registry | Requires a separately reviewed concrete registry and schema before activation |
| Journal backup | systemd calendar wake, default 03:15 UTC | Existing `Journal.backup` through a new supported maintenance entry point | Reviewed backup entry point and deployment manifest |
| Beads backup | Existing separately managed owner | Queue repository's supported backup tool | Retain its actual owner; Plan8 must not create a duplicate |
| admind automatic bump | Existing admind loop | admind ask/outbox store | Existing policy; never repurposed as the WSD reminder sweep |

The five-minute babysitter is not the five-minute reconcile job. Reconcile can mutate only through existing WSD protocols; babysitter cannot claim, resume, release, close, approve, replay effects, launch a review or reset a review budget. It is also not the current Hermes escalation timer or the old pane-watching maintenance babysitter. Installed filenames in preparation are observations, not authority to stop or repurpose them.

admind's `autobump_loop` checks open asks on its own cadence. Its `ask_bump_hours` and last-activity behavior can repeat after renewed inactivity; it is not proof of a one-reminder-only WSD policy. Plan6C must establish a single reminder policy owner for its own card namespace before activation. If current transport cannot suppress competing automatic bumps for those cards, compatibility work is required; no global change to unrelated asks is assumed.

## 4. Selecting the owner without duplicate loops

Add a validated host-only `[wsd] timer_owner = "internal" | "systemd"`. Default `internal` preserves existing installations. This field joins the restart view; reload cannot switch owner beneath a running daemon. Internal mode retains exactly the current recurring loops and refuses external *scheduled* ingress. Systemd mode creates neither internal pickup nor internal reconcile loops. Existing manual `tick` stays available as an explicit operator action in both modes; it is not a scheduler lease or permission bypass.

Add a typed scheduled ingress carrying installation ID, schedule generation, registered job ID and durable occurrence ID. It is accepted only for the configured owner/generation after the daemon verifies the installed manifest binding; it cannot supply arbitrary argv, native actor, task state or decision. Job selection reaches the same existing lane methods as a manual tick. A hand-written `tick` does not masquerade as a scheduled receipt. Owner mismatch, stale generation or unsupported job is an explicit refusal.

The installer renders one immutable schedule manifest and its units from the same reviewed release/configuration. The manifest binds service UID, canonical config/state directories, release and unit hashes, queue location identity (without credentials), workstream allowlist, owner and generation. The daemon verifies the manifest against its loaded configuration before opening scheduled ingress. This is an installation consistency check under the trusted service UID, not authentication against a malicious process with that same UID or OS isolation. An agent or untrusted task cannot gain authority by supplying a matching manifest; existing native and deployment trust boundaries still apply. A duplicate activation of a oneshot unit is prevented by systemd; lane coalescing and occurrence dedup remain necessary for socket retries or manual duplicate requests. No alternate process takes over by lease expiry.

A mode switch is a maintenance transaction: stop the previous recurring owner, quiesce scheduled admission, drain existing WSD jobs using its supported shutdown, record the exact predecessor configuration/units, write the new validated configuration/manifest/units, start the daemon in the new mode, then enable its matching timers. On failure, leave the new timers disabled and report an explicit hold. Rollback first disables the new timers, then restores the predecessor's exact configuration/unit bytes and owner mode. Never enable internal mode while external timers remain active. A failed readback prevents claiming that ownership transferred successfully.

The fixed proposed job enum is `pickup`, `reconcile`, `babysitter`, `forge_poll`, `reminder_sweep`, `daily_digest`, `user_schedules` and `journal_backup`. Each enum selects one reviewed adapter in the installed registry. Only `pickup` and `reconcile` map to the current WSD tick jobs. Babysitter and user-schedule evaluation are separate deterministic entry points; optional enum values refuse activation without their actual compatible adapter. Unknown strings are errors, never dynamic imports or executable names. The `user_schedules` enum is reserved and always refuses activation in v1; §8 defines the explicit scope boundary.

## 5. Occurrence ledger and bounded execution

Use a separate private Plan8 schedule ledger, not new ad hoc writes to WSD's decision journal or the native Beads database. Schema v1 records installation ID, configuration generation, job ID, occurrence key, due time, admitted time, state, bounded attempt details and exact effect/receipt reference. SQLite transactions and a single writer lock provide local admission serialization. Construction/migration is an explicit maintenance operation; read-only inspection opens an existing schema without migrations or write locks. Unsupported schema versions hold scheduled admission, preserve data and expose the recovery reason.

States are `due`, `admitted`, `running`, `complete`, `definite-unsent`, `uncertain`, `held` and `skipped`. Persist the occurrence before any external operation. The registered scheduling effect is explicit per adapter: for pickup/reconcile it is **durable acceptance of a wake**, not completion of the work triggered by that wake. For transport/Bead/backup adapters it is their defined enqueue/native-create/backup receipt, never an inferred remote outcome. `complete` always names that scheduling effect and receipt type; actual job outcome is a separate `pending`, `succeeded`, `failed`, `held` or `unknown` observation with its own owner-provided reference. A queueing acknowledgment must not be rendered as completed task work, review approval or Marmot delivery.

Current `wsd tick` acknowledges a control request but does not provide the proposed durable occurrence receipt. Add a narrow scheduled-ingress receipt contract before enabling external recurring pickup/reconcile. Request v1 is a strict JSON object with exactly `version` (integer 1), `operation` (`scheduled-tick` or `tick-status`), `installation_id`, `generation`, `job`, `occurrence_id` and `request_id`. Installation, generation and request IDs are lowercase UUIDs (36 ASCII bytes); occurrence ID is a lowercase SHA-256 hex digest (64 ASCII bytes); job is the fixed enum, with only pickup/reconcile allowed here. Unknown, duplicate or missing keys, noncanonical encodings and values of wrong type are rejected. Targets are resolved from the installed manifest, never supplied by the request. Both frame and decoded JSON are limited to 16 KiB; target allowlist is at most 128 workstream IDs, each 1–64 ASCII characters matching `[A-Za-z0-9_-]+`. Reject an oversized installation instead of truncating its targets. The receipt binds the canonical request tuple, exact target set/configuration hash and installation receipt; request ID correlates transport attempts and is not the dedup key.

WSD holds one scheduled-admission lock while validating owner/generation/readiness and transactionally inserting the occurrence and its complete accepted intent into the Plan8 ledger. The single SQLite commit is the acceptance boundary: before commit no lane enqueue or effect call is allowed; after commit the durable intent is authoritative. A repeated identical tuple returns the same receipt; conflicting payload for an existing tuple is refused. An accepted response contains exactly `version`, `request_id`, `status`, `tuple`, `receipt_id` and `target_set_hash`; tuple has exactly installation ID, generation, job and occurrence ID under the request types, receipt ID is a lowercase UUID and target-set hash is lowercase 64-hex SHA-256; `status=accepted` means that committed wake intent, not finished work. No native mutation occurs in this transaction. WSD startup recovers committed intents before opening scheduled ingress. It reads the same ledger through its supported owner API, not by constructing a second mutating WSD Journal.

Crash states are explicit: before commit, no accepted intent and no lane issue; after commit/before enqueue, recover the accepted intent; after enqueue/before dispatch marking, coalesce/recover the same intent under the existing lane and action gates; after lane completion/before outcome recording, reconcile using actual lane/action receipts and retain unknown when proof is unavailable. Persist dispatch observation and actual outcome separately; a dispatch flag alone is never proof an external action completed. A lane must retain the occurrence reference while coalescing. WSD owns this recovery, without promising exactly one physical execution or replaying an unresolved action. The runner marks its scheduling effect complete on durable acceptance immediately.

Provide bounded read-only `tick-status` for exactly that tuple, under the same admission lock and authoritative ledger snapshot. It does not migrate, construct a queue or mutate. Response statuses are `accepted`, `not-issued`, `unknown` or `unavailable`; unknown schema/generation, maintenance or ledger read failure cannot return not-issued. For a valid current generation, not-issued means no committed intent exists and, because dispatch requires that commit and the lock excludes concurrent admission during the read, no prior dispatch could have occurred for that tuple. Status response has exactly the accepted response keys plus `snapshot_hash` (lowercase 64-hex) and `reason` (closed enum `none`, `not_ready`, `maintenance`, `ledger_unavailable`, `schema_mismatch`, `generation_mismatch`); receipt ID and target-set hash are null unless accepted, and snapshot hash is null unless an authoritative healthy snapshot exists. Freeform error text and extra keys are refused. The healthy snapshot requires recovery complete with intact generation/history, never a fresh empty replacement for missing data. The response binds generation, tuple, request ID and snapshot hash. It is a point-in-time absence proof, not a lease: retry uses the same tuple and atomic insertion, so a concurrent later issuer cannot cause a second accepted intent. Timeout after possible issue holds the runner occurrence uncertain until accepted or this exact not-issued proof settles it; generic missing data cannot authorize replay. Accepted prevents replay of the same wake even if the job later fails; subsequent distinct periodic wakes still honor unresolved-action gates.

Non-WSD adapters must expose similarly exact receipt semantics in their approved producer contracts before activation. Plan8 does not manufacture them from a transport return value. No receipt means no assertion that an effect did not occur.

Each runner pass admits at most 64 due occurrences and stops admitting after 30 seconds. Each control request has a five-second total connect/write/read deadline, a 16 KiB request limit and a 16 KiB response limit; malformed/oversized responses hold the occurrence. At most one initial request and one status lookup per occurrence occur in a pass, with the 30-second pass deadline taking precedence. A refused or incomplete frame cannot be interpreted as acceptance; ongoing WSD work remains owned by its lane after a caller timeout. Limit the runner to one concurrent pass per installation. Remaining due rows remain durable for later passes, with backlog count and oldest age visible. These bounds do not guarantee that an arbitrarily large installation completes every job within its nominal cadence. Health reporting explicitly identifies overdue/backlogged jobs rather than presenting them as on time.

Interval occurrence identity is independent of daemon PID, boot ID, timer activation and process restart. The immutable generation manifest supplies UTC anchor `A`, interval `P` from the fixed registry and a nonoverlapping start boundary. Slot `k=floor((UTC_now-A)/P)` has key SHA-256 of the canonical version/installation/generation/job/slot tuple; negative or pre-boundary slots are ineligible. On restart, retain the same anchor, generation and dedup keys. Coalesce all unadmitted missed slots to the latest eligible slot and durably record the skipped slot range; do not replay every elapsed interval. Never coalesce an admitted or uncertain occurrence away. The independent babysitter may observe during a clock hold, but clock-dependent effect jobs do not admit until readiness is true.

Global `clock_ready` is a proposed producer contract exposed with generation, boot ID, clock-epoch ID, UTC sample, monotonic sample, last durable admitted UTC high-water, readiness status and typed reason. Each new boot/process starts unready. Readiness requires completed ledger recovery, valid timezone/configuration and two UTC/monotonic observations at least 30 seconds apart with absolute elapsed-time difference at most two seconds, plus UTC not behind the durable admitted high-water. Across a new boot, also require affirmative OS time-synchronization evidence from the reviewed platform adapter; elapsed time or an old persisted ready flag is not that evidence. If unavailable, clock-dependent jobs hold visibly until the supported time service provides it; no manual terminal grant bypasses this gate. While running, a wall/monotonic discrepancy over two seconds, backward UTC, loss of synchronization or boot/config mismatch clears readiness and increments a durable clock epoch before further admission. A forward jump may coalesce only after readiness is re-established; it cannot create a success receipt. This is a new interface requirement, not a claim that current WSD or provisional 6C already exposes it. 6C must consume the same readiness/epoch contract before reminder/digest activation, preserving its own stricter time predicates.

For calendar jobs, the key includes installation, schedule ID, configuration generation and intended civil slot represented by timezone, local date/time and UTC offset. DST repeated times execute at most one configured occurrence, first by default; nonexistent times advance to the first valid instant after the gap. Freeze that mapping at admission. Backward time never clears an admitted key. Monotonic deadlines bound local calls; durable UTC/civil keys and high-water survive restarts, while monotonic values are never compared across boots.

A terminal row may compact to its occurrence key, outcome, effect reference/hash and timestamps after 30 days; do not erase dedup keys while the configuration remains replayable. Default finite capacity is 100,000 compact keys per active schedule generation. Before exhaustion, stop new admission for that generation and emit a capacity hold. A supported operator maintenance command can archive a retired generation with an exact manifest, verify no due/running/uncertain rows, and install a new nonoverlapping future start boundary. It does not silently forget past keys or retrospectively replay them. Archive/rollback must preserve those boundaries. The design makes no claim of infinite storage or exactly-once remote effects.

## 6. Reconciliation and preservation of identity

Keep the existing startup sequence and WSD lock domains. Read authoritative native state and runtime/session receipts, reconcile uncertain actions through their actual owner, recover parked/session state, then consider pickup. A caller cannot reconstruct identity from a transcript or choose a new actor because an old worker appears idle.

For a managed session retain native bead ID and assignee, task binding, session key, adapter profile, recorded thread/session ID, launch generation, credential-key reference and group mapping. Do not change accounts to escape `account_changed`. ADR17 permits re-gating that condition only on startup, configuration reload or explicit supported operator release; periodic reconciliation must not treat itself as a fresh startup. Two actual failed supported resumes may escalate to needs-human under the existing protocol. Absence of output, missing heartbeat, elapsed time or a watcher guess is not a failed-resume receipt.

An uncertain native write, launch, target action, send or review remains held. Plan8 may wake the responsible reconciler and report its held reason; it cannot bypass authentic approvals, dependency blockers, genuine worker cessation or native close evidence. Operator reclaim/status/dependency changes use the reviewed management APIs with exact expectations and durable audit. Task/session/group history and worktrees survive recovery and rollback.

The current `HoldingReconciler` is intentionally not an executor-effect oracle. A periodic wake must not claim that Plan5 target reconciliation is implemented. Plan5 owns its action ledger and state changes; Plan8 stores only occurrence/effect references. Plan5 does not depend on the Plan8 timer to expose its callable reconciliation seam, preventing a dependency cycle.

## 7. Independent babysitter and honest health

Add a bounded, versioned health snapshot producer inside WSD, written atomically to a private file after startup, each job transition and every 30 seconds through a dedicated lightweight heartbeat. It contains installation/generation, boot/process instance, snapshot sequence and UTC timestamp, owner mode, recovery status, last successful pickup/reconcile times, bounded job/backlog counters and typed hold codes. It contains no prompts, transcripts, credentials, freeform task text or private message bodies. The heartbeat must be produced by the serving event loop, not a separate thread that could keep advertising health after the event loop stalls.

The external babysitter reads this file and its own previous observation without constructing `Journal`, importing a queue factory or querying credentials. It may request a bounded control-socket status only through an explicitly bounded read-only health endpoint; the existing general `status` path is not asserted to be side-effect free. Until that endpoint exists, snapshot-only health reports its limited basis. It verifies file ownership, regular-file/no-symlink shape, schema, installation/generation and bounded size (256 KiB); malformed, stale or missing data becomes `unknown`/`unavailable`, never an inferred task failure. Snapshot absence is expected during an explicitly recorded maintenance window, which remains visible and expires to unknown rather than suppressing alerts forever.

A snapshot is stale when its declared UTC write time is more than 90 seconds old, more than 30 seconds in the future, or inconsistent with its boot/process instance. The observer also records local monotonic observation time and snapshot sequence: an unchanged sequence across at least 90 monotonic seconds is stale even if wall time moves backward. On its first sample after observer restart, it can use sane UTC age but cannot invent an earlier monotonic sample. Invalid clock/boot evidence is `unknown`, not healthy. Within the same live process, a newer sequence with a recent sane timestamp restores liveness evidence; a new process must have its own startup/recovery state.

The observer runs every five minutes with a 30-second total read/report deadline. It reports stale/unavailable on the first failing observation; the nominal worst detection delay after the 90-second freshness threshold is one five-minute interval plus that execution deadline, not a five-minute recovery guarantee. It does not wait two more observer passes. For a healthy daemon with old job success, report the exact overdue job separately from process liveness. One failure notice per installation/generation/episode and one recovery notice use deterministic opaque keys. A restarted observer reloads its durable episode record; a backward clock jump does not silently resolve an episode. The observer never restarts agents or calls a model.

Reuse `admind/alerts.py`'s existing local-file contract: atomic `<id>.json` with `id`, RFC3339 `created_at` and safe plain `text`, each filename 1–64 allowed characters. Keys are opaque shortened digests, not raw 64-hex identifiers in rendered text. The alert text is bounded and redacted; secret-shape refusal remains active. admind's membership/current-policy guard still governs relay. A file is durable local reporting, not proof that an operator received it. If admind is down/latched, preserve the file and a local structured diagnostic suitable for the service manager journal; state that remote delivery is unconfirmed. Do not create approval cards for routine health FYIs or use a local notice to confer consent.

The alert reader currently scans its directory; Plan8 therefore bounds its own outstanding files (one failure and one recovery per episode, at most 256 unsettled episodes). Capacity prevents further scheduled admission and emits a local capacity failure rather than generating unbounded files. A reviewed cleanup path archives acknowledged/retired episodes and preserves dedup records. No automatic cleanup assumes that an outbox row equals remote delivery.

## 8. Reminder, digest and user schedule joins

The corrected Plan6C draft is `ee9203f5b2d8567a557b0876ada4dd54e99e0463`, `docs/designs/2026-10-16-plan6c-durable-delivery.md`, with `docs/reviews/plan6c-delivery-inputs.json` at the same revision. It is **UNREVIEWED and proposed**, not implementation authority or an installed interface. It provides a concrete alignment target for the delivery bridge, one-reminder ownership, complete-copy acknowledgments, uncertainty and the 08:00 UTC closed-yesterday digest. Its own active review may change these seams. Plan8 pins this snapshot for honest coordination, while requiring actual final compatible contracts before dependent adapter activation. It does not treat the draft as a new approval writer or bypass the prerequisites listed in that draft.

Plan6C owns reminder due predicates, exactly which complete-copy acknowledgments count, four-hour timing, ten-minute delivery escalation, closure/supersession cancellation, per-card reminder dedup and uncertain-send settlement. Plan8 passes occurrence identity and time to its eventual versioned adapter; it cannot infer delivery from a WSD launch receipt or combine chunks from unrelated copies. Until an approved adapter exists, the job is `disabled: dependency unavailable`, visible in installation and health output. It does not return a synthetic successful no-op.

The digest's approved producer must supply redacted scoped facts for closed-yesterday, open approvals, needs-human and idle workstreams. A daily occurrence is an FYI, not an approval. Its durable send key binds installation, producer contract, scope and civil day. On restart, catch up at most the most recent completed day; older missed days are explicitly counted as skipped and available through supported history queries. Current partial source data is labeled partial; never claim a complete digest from a truncated snapshot. Timezone is an explicit IANA name with default UTC, reviewed in the deployment configuration.

User-defined schedules are explicitly disabled in v1. There is no accepted `schedules.toml` target schema, calendar-expression parser, fixed-command registry member or file-Bead template in this approval scope. Nonempty user schedule configuration and activation of `user_schedules` fail validation before installation; no minute runner is installed. The enabled registry consists only of the fixed jobs in §4, with the exact cadences in §3; optional jobs remain disabled until their named producer compatibility gates pass. This makes v1 bounded without disguising an arbitrary command, prompt or native-write feature as a timer setting.

A future user-schedule design must specify a closed calendar grammar, finite registry and argument schemas, genuine enrolled native-create identity, idempotency/readback and configuration-generation boundaries before implementation. It may reuse this ledger, but this design grants no such effect authority. This explicit deferral does not block core pickup/reconcile, babysitter or backup implementation and does not create another approval gate for routines already within the approved fixed registry.

## 9. Backups, installation and rollback

Reuse `Journal.backup`'s online SQLite backup API; do not copy a live WAL database as a plain file. Add a dedicated supported maintenance request that serializes the backup on the owning WSD journal connection and never calls it inside a transaction. The external job requests a backup and records the returned exact file/hash receipt. A WSD outage is backup unavailable, not permission to open a second mutating Journal constructor. The schedule ledger backs up its own store using its own supported online operation. Beads keeps its separate supported backup owner. These are separately consistent snapshots, not a cross-store atomic checkpoint.

Default retention keeps seven daily and four weekly verified backups per store, private permissions and manifest hashes. Restore validation occurs in a disposable location before any live restore. A restore/recovery action names its authority, exact source snapshots, queue/runtime reconciliation requirements and before/after evidence; timer activation never implicitly authorizes restoration. Do not restore an old schedule ledger while leaving newer effects replayable. Retain dedup/history archives across rollback.

Extend the reviewed release installer and generated-unit mechanisms; do not install an editable checkout or handwrite production units. Existing `deploy/install.sh` supports exact commit/archive hash, preflight, dry-run and managed service adoption. A future Plan8 extension must preserve those checks, root-only staging, service-user ownership and existing config/state paths. Existing `--adopt`/`--no-wsd` semantics are not repurposed to hide timer migration. No existing flags are advertised as implementing this extension today.

The installation receipt inventories previous and proposed units/timers/cron owners with canonical paths, hashes, enablement and running state, installation IDs and explicit collision decisions. It may disable/replace only enumerated owners covered by the deployment decision. An unrelated Hermes manager-pickup, escalation, queue supervisor or Beads backup is not disabled because its interval resembles a Plan8 job. An obsolete pane watcher is retired only by explicit scoped migration authority. Preserve native claims, current session/run IDs, parent pickup state, checkpoint bytes, groups, worktrees and all audit/decision/review journals. The installer must not create a replacement controller to obtain a clean state.

Before live changes, publish the reviewed design and deviations and obtain the genuine Marmot deployment approval with exact release/config/unit hashes and rollback steps. Perform read-only inventory, backup and render/diff preflight first. Apply the owner switch from §4, verify actual scheduled receipt and bounded read-only health, then verify no duplicate recurring owner. Rollback disables new timers before restoring previous mode/units, preserves data and incident receipts, and performs readback. If preservation or readback fails, stop activation and report the conflict instead of guessing the old state. No install or rollback is authorized by this design document itself.

## 10. Dependency order and implementation slices

1. Implement pure registry/calendar validation and occurrence ledger, with fake clocks and no live clients. Add the owner-mode setting/restart binding and typed scheduled ingress. Existing default behavior remains covered.
2. Integrate pickup/reconcile scheduled ingress through existing lanes; render managed timer units and their manifest. Add health snapshot producer and the separate read-only babysitter/alert episode writer. No Plan5/6/7 implementation is required to test these seams.
3. Add supported backup maintenance interfaces and bounded archive/capacity inspection commands. Validate install/rollback with fake service-manager and native adapters.
4. Enable optional forge/reminder/digest jobs only after their exact actual producers/effect contracts are reviewed, admitted and implemented. This is a compatibility check against real versioned interfaces, not a new approval for every routine job or a claim that provisional designs are installed.
5. Deploy only under the separately approved release/configuration, then collect Plan9 evidence. Offline tests and a hosted green build are not live activation or the required three-day approvals-only acceptance clock.

Dependencies point from Plan8 adapters to stable Plan5/6/7 producer interfaces. Those producers expose independently callable APIs and do not require Plan8 scheduling to be complete. Plan9 consumes evidence from both. Existing timer/recovery work (`btq-pyoq5`, `btq-2via5`, `btq-n7w02`), Plan5 (`btq-e7knb`), consumer integration (`btq-fu366`), operator management (`btq-dmiln`), and retention work (`btq-qdyj7`) are reuse/coordination references, not new tasks or claims of current completion. Controller assigns implementation slices through actual Beads dependencies after design approval; this document creates no task state.

## 11. Required verification and acceptance

Offline implementation tests must cover both owner modes and stale-generation refusal; no internal recurring loops in systemd mode; manual/event/quota wake preservation; same-lane serialization and cross-workstream independence; duplicated scheduled request and lost reply; crashes before/after ledger admission/effect receipt; uncertainty without replay; config changes with pending work; downtime coalescing, DST gaps/repeats, forward/backward clocks; resource caps/backlogs; maintenance windows; malformed/symlink/stale health snapshots; no Journal/queue construction in babysitter; one durable failure/recovery episode across restart; membership-latched/unavailable admind with no fake remote receipt; capacity/archive boundaries; native identity/history preservation; and installer collision/refusal/rollback ordering.

Use fake service managers, queues, clocks, runtime adapters and transport; no tests may invoke a real model, production queue, sender or timer. Integration tests must exercise the real CLI/renderer and stored occurrence schema rather than only mocked internal methods. Backup tests restore disposable databases and verify committed content, permissions and independent snapshot limits. Reminder/digest adapters need contract tests against the eventual actual producer versions, including duplicate-bump prevention and partial-data labeling.

Live acceptance separately demonstrates the actual release unit hashes and owner mode, recurring wakes through the registered path, an independent daemon-outage alert, a safely held uncertain outcome, backup/restore rehearsal, both supported adapter identities, and rollback without changing sessions/native tasks/groups/history. No operational step requires tmux attach. Hermes/gatekeeper outage does not stop deterministic allowed flows; unavailable authority still blocks new decisions. Only Plan9's genuine observed interval can establish three days of approvals-only operation. This proposal starts no clock and declares no acceptance.

## 12. Review and remaining gates

The design chooses systemd recurring ownership, backward-compatible internal default, UTC defaults with explicit configurable timezone, bounded coalesced/latest-only catch-up, a separate schedule ledger, and an independent observation-only babysitter. These are reviewable decisions, not unresolved invitations to invent runtime policy. Root will obtain the actual Claude builtin design review (maximum three rounds for this change), publish the frozen reviewed object and obtain genuine Marmot human design approval before implementation. No review has been spent by the author.

Required later inputs are the exact final Plan5/6/7 contracts for optional adapters and the actual deployment inventory/configuration. Their absence disables only dependent jobs; it does not make the core owner/reconcile/health implementation impossible. No generic consent, source header, timeout or automated notice replaces those authentic inputs.
