**Verdict: REVISE.** I reviewed `docs/adr/2026-10-18-admind-maintenance-recovery.md` at d94370eb, against the approved parent design §4 and the exjsy sibling worktree at `/home/openclaw/repos/heterodyne-metaharness-v2-btq-btq-exjsy` (1701018: `store.py`, `daemon.py`). The review was static and read-only. I ran no tests, DB, native or network calls. <!-- install-agnostic: allow=home-path reason=verbatim historical reviewer source location, not an installation default -->

Four findings would let retirement act on unproven, mislabelled or stale state, or need a migration the design doesn't allow:
- A historical hold can become eligible after one retry.
- The CAS can be fooled because the generation counter resets.
- `ask_attempts.settled` has a CHECK that can't be extended additively.
- A native-conflict retirement records `cancelled` where the existing code records `blocked`.

The other six are gaps in coverage, the escalation route, authority, storage and command usability.

10 findings, most severe first:

1. `docs/adr/2026-10-18-admind-maintenance-recovery.md:23`: An attempt is eligible when a receipt exists for its most recent invocation, so a historical pre-proof overlay becomes eligible after one post-upgrade retry. Earlier invocations from before the upgrade stay unproven, which the design's own rule says a fresh native read cannot cover.

   Failure scenario: A pending-maintenance overlay already exists when the schema upgrades. The retry loop runs it once more, the child returns the exact HOLD, and the new code writes a v1 proof. Lines 19-21 now count it as fully proven ('most recent child invocation', 'no invocation since'). Lines 23 and 47 promise such rows stay ineligible, but nothing does that once a new proof exists. Fix: keep a per-attempt invocation counter and a 'proof-capable since begin_attempt' flag, both set by begin_attempt under the new schema. Retire only when every generation from 1 to N has an exact HOLD receipt. Attempts that began before the upgrade stay ineligible permanently.

2. `docs/adr/2026-10-18-admind-maintenance-recovery.md:21`: The per-attempt invocation generation is stored in the proof record, and that record is deleted or invalidated when the next issuing intent is recorded. The counter can therefore reset, which makes the Store CAS on line 29 open to ABA.

   Failure scenario: Process P1 reads the proof (gen 1, HOLD stdout hash H) and does its native read. A second process or stale actor records an issuing intent, which deletes the proof and its counter. That child returns HOLD, and a new proof is written as gen 1 with the same constant hash H, since the HOLD JSON never changes. P1's CAS compares ask, attempt, digest, overlay, gen and proof hash, finds them all equal, and commits a retirement even though an invocation started and ended in between. Line 33 says the CAS alone rejects this. Fix: keep a counter that is never deleted, for example ask_attempts.invocations, and increment it in issue_decision in the same transaction as the issuing marker. The CAS must check that counter.

3. `docs/adr/2026-10-18-admind-maintenance-recovery.md:29`: Marking the attempt 'settled as pre-effect-retired' breaks the existing CHECK on ask_attempts.settled, which allows only refused, recorded, untouched, blocked and uncertain. SQLite cannot alter a CHECK, so this needs a rebuild of the immutable history table, which contradicts 'additive' and 'retain old rows'.

   Failure scenario: The retirement transaction runs UPDATE ask_attempts SET settled='pre-effect-retired' and gets an IntegrityError. The whole retirement rolls back, so the command can never succeed. The other route, a copy-and-rename migration of ask_attempts at startup, risks the history this design says it preserves, and no such migration has been reviewed. Fix: settle through the existing close_attempt with an allowed value ('untouched', or 'blocked' for a conflict). Keep the retirement provenance only in the new additive receipt table.

4. `docs/adr/2026-10-18-admind-maintenance-recovery.md:25`: On a conflicting terminal native decision, the design sets the local ask to 'cancelled / maintenance-retired'. The existing settlement() maps a conflicting native decision to status 'blocked' with the BLOCKED text, so the two paths would disagree.

   Failure scenario: The bead was approved natively by another route and the operator retires the held attempt. The poster agent's `ask get` or `wait` returns cancelled with decided_by set to the operator, which is indistinguishable from a cancel. The poster posts a fresh approval ask for a bead that is already decided, which sends Liam a redundant question and uses a slot. not_open() also replies 'already cancelled by X' instead of 'blocked'. Fix: the conflict branch uses close_attempt(settled='blocked', new_status='blocked') with the existing text, and 'cancelled' is used only when native is undecided.

5. `docs/adr/2026-10-18-admind-maintenance-recovery.md:25`: The native readback branches cover only undecided, conflicting-terminal, exact-match and unknown. The real stop classes that create suspended holds have no stated mapping: not-open, not-approval, not-approver, gate, stale/changed-card and busy (MAINTENANCE_SUSPENDED and maintenance_stop_reason).

   Failure scenario: A bead held as 'not-open' (closed natively without a decision) or 'not-approval' reads back as neither undecided nor a terminal approval decision. Under the line 25 wording it falls into 'unknown/malformed' and stays held forever, so the same 20-slot starvation from exjsy R2 #2 comes back for those reasons. Fix: give an explicit table from each preflight or readout word to retire, reconcile or hold, and say which suspended reasons this command can clear.

6. `docs/adr/2026-10-18-admind-maintenance-recovery.md:21`: The proof lifecycle is tied to 'defer_maintenance', but in exjsy defer_maintenance is also called by retry_maintenance's backoff and by every non-child hold reason. Separately, a pre-launch failure after issue_decision deletes the proof without any child running.

   Failure scenario: (a) If every defer_maintenance writes or refreshes the proof, a backoff or an 'authority'/'native-conflict' hold with no child result produces a fabricated receipt. If those calls clear the proof, a valid proof disappears when the hold is suspended. (b) On a retry, issue_decision records the issuing intent and deletes the proof. ab.decide then raises OSError before spawn (launched=False), and the hold is read-unavailable with no proof. The next retry finds native-conflict and suspends, and that attempt can now never be retired. Fix: create the proof only in the proven_hold branch, carry it forward unchanged on other defer calls, and define the launched=False case (restore the prior receipt in the same transaction, with in-process no-spawn evidence).

7. `docs/adr/2026-10-18-admind-maintenance-recovery.md:39`: Holds that can't be retired still count toward MAX_OPEN=20 forever: issuance-unverified (maintenance-issuing after a crash), historical and missing-proof holds. The 'existing human escalation channel' they are pointed to is never named, and a Marmot ask can't be posted once all 20 slots are taken.

   Failure scenario: Several attempts crash after their issuing marker, so reconcile_issuing leaves them deciding/maintenance-issuing with no overlay. Together with a few historical holds, they fill 20 slots. post_ask returns ASK_TOO_MANY, so the controller can't ask Liam through admind, which breaks 'every decision goes out as a Marmot ask' (~/.hermes/CLAUDE.md). The notice tells him to escalate through a channel that doesn't exist and forbids SQLite edits, so there is no route out. Fix: name the concrete notice-based channel, reserve capacity or explicitly accept the residual starvation, and state which separate design will cover it.

8. `docs/adr/2026-10-18-admind-maintenance-recovery.md:15`: The Store CAS compares against a 'current authority epoch' that doesn't exist in the Store. membership_epoch is in-memory daemon state, and the policy refresh has no epoch. The design also lets any operator retire another operator's held DENY without saying whether policy permits it or notifying the original operator.

   Failure scenario: (a) The implementer has no persisted value for the Store CAS to compare, so the authority race claimed on line 33 isn't actually closed across processes. It is closed only by work_lock (membership transitions also take work_lock), with no await between the check and the commit. The design should say that explicitly. (b) Operator A's '!deny' is held. Operator B retires it, the poster re-posts, and B approves. A's still-pending deny was silently overridden, and A gets no specific notice. Fix: say which authority rule permits retiring another operator's attempt, and thread the acknowledgement to the original operator.

9. `docs/adr/2026-10-18-admind-maintenance-recovery.md:31`: The storage bound rests on 'the existing retention policy', but admind has none for asks, ask_attempts or proofs; only notices are pruned. 'Invalidate' prior proofs is also ambiguous, and the receipt key by recovery inbound ID repeats the dedup the inbound table already does.

   Failure scenario: During a long queue fence, a retryable hold retries every 30 seconds. If each invalidated per-invocation receipt is kept, that is about 2,880 rows per attempt per day, up to 128 attempts, with no pruning, so line 37's 'finite under existing retention' doesn't hold. The receipt-table key on inbound message_id adds a second idempotency mechanism alongside inbound's PRIMARY KEY. Fix: one proof row per attempt replaced in place, plus a counter. Key receipts by unique (ask, attempt) only, and define retention explicitly.

10. `docs/adr/2026-10-18-admind-maintenance-recovery.md:13`: The command requires an ask ID, a 64-hex attempt message ID and a 64-hex '<full-context-digest>', typed as a reply on a phone. Lines 13, 19 and 29 use 'full-context digest', 'stored card digest' and 'full digest' without saying which value it is: the bead card digest or the proof hash.

    Failure scenario: Liam is on a phone and has to reproduce about 130 hex characters exactly in a reply to a notice that is already threaded to that ask and attempt. A single typo gets a refusal, so retirement is impractical in practice. Implementers will also choose different digests, and the command may not bind to the proof generation the operator actually saw. Fix: define the digest precisely. Better, bind it to a short proof token from the hold notice, verified against the full stored proof hash, with the reply thread supplying the ask and attempt.
