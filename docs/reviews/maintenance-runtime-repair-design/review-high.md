**Verdict: REVISE.** The design is not ready for human approval as written. The two-child split is workable, and the problem statement matches the real code. Every listed source blob is identical at b4b8c75 and at 893931a/46fd58, and the design's sha256 matches the inputs record. But the queue bounds conflict with the real timeouts and lock structure, the product withdrawal fix misses several close paths, and the boundary between the aa860 and 6f authorities is not drawn per child.

Scope: I reviewed commit 74b3b0d (ADR, identical design copy, inputs JSON) against the source at b4b8c75 (product), 893931a/46fd58 (queue), 42dc3 (harness), the aa860 and 6f ADRs, and the retained u9 R5, 4kc R6 and y2 R5 reports. Read-only: no edits, tests, queue, native or network actions.

10 findings, most severe first:

1. `docs/adr/2026-10-18-maintenance-runtime-repair-admission.md:37`: The design caps each bead's scope at 5 seconds including external work, but the real admind post timeout is 60 seconds (`ADMIND_TIMEOUT = 60`, bin/btq-supervise:879) and the documented admind post budget is 160 seconds (MARK_SETTLE comment). `post()`, `notice()`, `ask_view()`, `flag()` and `comment()` all run inside `record_scope`. The design also never names `ADMIND_TIMEOUT` among the constants it changes or keeps.

   Failure scenario: Child B shortens the subprocess timeout to the ≤5 s remaining budget. Under normal admind load (outbox and lock contention), posts that would have succeeded in 6–60 s now time out and become 'ambiguous'. Each ambiguous post permanently uses one of max_open_asks=10 until a manual `mark` at least 1 hour later. Ten slow posts stop the supervisor from posting at all. The other option the design allows, 'refuse before launch', means nothing is ever posted. The design must either keep network calls outside the timed admission scope (release the gate before the RPC and re-check before saving) or explicitly re-budget ADMIND_TIMEOUT.

2. `docs/adr/2026-10-18-maintenance-runtime-repair-admission.md:35`: The design says lock order 'remains admission → host serialization → journal'. That is not the current order: `_main` takes the host supervisor flock (`Store.lock`, EX|NB) inside setup and holds it for the whole scan, and every per-bead admission waits for turnstile/gate while already holding it. The proposed order also differs from 6f §5's single global order (turnstile → gate → installation → journal → inner state lock, 'never uses a second lock domain').

   Failure scenario: Rule 'never hold host lock while waiting for turnstile/gate' forces the scan to release the host flock between beads. A timer scan and a manual scan (or hold/mark) can then interleave. Each scan computed `open_asks` once at the start of `act()` and keeps its own `posted` count, so two scans together exceed max_open_asks / max_new_asks_per_scan. Keeping the whole-scan host lock instead breaks the stated rule. The design needs to keep a scan-singleton lock separate from per-record serialization (or recompute open-ask occupancy from disk under serialization in each scope), and amend 6f §5's lock order explicitly.

3. `docs/adr/2026-10-18-maintenance-runtime-repair-admission.md:39`: The design requires child-75 inside act to surface as CLI exit 75, but `Coordinator.operation()` (btq-maintenance.py ~2062) deliberately turns an exit_code-75 exception into `RuntimeError('admitted operation held; effects uncertain')` once an ordinal exists and the record is not complete. That conversion exists so a possibly-issued effect is never labelled not-issued (6f §4).

   Failure scenario: Acceptance case 'inject child75 at act → require actual CLI75' (line 49). Either the implementer removes the conversion, so a post or notice that may have been issued now reports a clean typed HOLD (an unsafe relabel), or the test cannot pass. The design needs three outcomes: pre-ordinal systemic HOLD → 75; post-ordinal uncertain → a distinct non-zero exit, never 75 and never 0; per-record malformed input → local report.

4. `docs/adr/2026-10-18-maintenance-runtime-repair-admission.md:23`: Withdrawn launched-HOLD chains are kept as deciding/held, but the design defines no suspended or terminal state for them. `MAINTENANCE_SUSPENDED` has no withdrawal reason, so `retry_maintenance` keeps firing. The design also adds no capacity or liveness residual for these chains, which now permanently use MAX_OPEN=20 and maintenance capacity 128.

   Failure scenario: Withdraw a bead whose attempt is pending-maintenance with incomplete proof. Every 30 s `retry_maintenance` runs a native `read_and_settle` and `hold_maintenance` (now forbidden from closing), re-deferring as 'pending-maintenance' and re-noticing 'It will retry after fresh card and operator-authority checks' — the same wrong-notice and forever-re-defer defect as 4kc #4, which the design leaves OPEN, now the normal state for every withdrawn chain. With incomplete proof, `!asks retire` is unavailable, so the chain occupies a MAX_OPEN slot forever. A handful of withdrawals locks out new asks with no supported way to release them. The design needs a 'source-withdrawn' suspended reason with truthful notice text, and must state the starvation residual (aa860 already discloses this class).

5. `docs/adr/2026-10-18-maintenance-runtime-repair-admission.md:23`: 'Positive never-issued evidence' is not defined. After the migration, historical rows have `invocations` DEFAULT 0 and `proof_capable_since_begin`=0 even if they launched children before the upgrade. Line 29's identity handling is also left as an either/or ('Alternatively ... retirement-ineligible') with no chosen representation.

   Failure scenario: The implementer uses `invocations == 0` as the never-issued test in the run_attempt false-issue and retry_maintenance branches. A pre-upgrade attempt that actually launched a decision child (invocations=0 by migration default) is withdrawn and closed as cancelled, 'no native decision was issued' — exactly the launched-history erasure the design forbids. The predicate must be `proof_capable_since_begin=1 AND invocations=0 AND outcome not *-issuing`. The design must also choose one identity-drift mechanism (for example, durably clearing `proof_capable_since_begin`) rather than leave the choice to the implementer.

6. `docs/adr/2026-10-18-maintenance-runtime-repair-admission.md:23`: The design lists only two close paths to fix (`retry_maintenance` and the run_attempt false-issue branch). Other paths also cancel, or delete proof for, a launched maintenance chain: `settlement()` untouched+withdrawn → cancelled (daemon.py:1799), the withdrawn branch of `refresh()` (~1733), `close_refused`'s open→cancelled rewrite (1529), and `Store.close_attempt`, which calls `retirement.clear_active` (deleting the proof and recovery notice) for every settle except 'uncertain'.

   Failure scenario: A maintenance retry launches, the child returns an ordinary result or raises after launch (launched=True so `stop` stays None), and readback is untouched while the source is withdrawn. `settlement()`/`refresh()` close it as cancelled 'no native decision was recorded', and `close_attempt` deletes the `maintenance_proofs` row for the earlier HOLD invocations. That contradicts the design's own rules ('Native untouched ... not whole-chain absence proof'; post-Popen 'stays UNKNOWN'). The design must cover these paths and the Store-level `clear_active` invariant, with RED tests for each.

7. `docs/adr/2026-10-18-maintenance-runtime-repair-admission.md:27`: The Service.permit fix specifies 'two reads under Store.lock', but Store.lock is an in-process RLock around autocommit SELECTs. Other processes open their own connections to admind.db (cli.py:76 constructs `Store`), so two separate statements under the lock are not one snapshot.

   Failure scenario: Another process commits a supersession or revocation between the proposals SELECT and the `maintenance_recovery_current` SELECT. The 'coherent observation' is torn, and the RED test only proves the in-process thread race. Use the existing `Store.transaction(read_only=True)`, which takes the lock and starts a deferred snapshot (already used by `Service.get`), and add a cross-connection writer to the barrier test.

8. `docs/adr/2026-10-18-maintenance-runtime-repair-admission.md:49`: Some of child B's RED-first criteria cannot fail on the baseline. 'Backup completes within 30 s OR emits the documented bounded HOLD' already passes, because baseline backup fails with MaintenanceHold('admission busy'). The torn-write test pairs scan with hold/mark/summary-abandon/summary, but at 893931a all four already take the host flock with EX|NB (lines 1676/1716/1752/1812) and refuse while a scan runs.

   Failure scenario: The author runs the required baseline-failure step: the backup criterion passes on unrepaired code, and the multiprocess scan+hold test cannot produce torn bytes. To satisfy 'must fail baseline', a test has to be contrived, or the criterion is silently dropped. Finding y2 #1's reachable writer pair needs to be re-established against the actual code, and the backup criterion should require backup success within 30 s under the scan.

9. `docs/adr/2026-10-18-maintenance-runtime-repair-admission.md:19`: The aa860 and 6f authorities are not kept separate. Child A bundles aa860 retirement and proof surfaces with the 6f/u9e24 `Service.permit` fix under one undefined 'native approval dependencies' gate. The aa860 approval record is never identified. qe3gk is stretched to verify A and B, although its native bead binds only 6f via btq-1yedv's four targets. It also relies on 'jlzk6's enrolled closure', but harness 42dc3 `install_maintenance.py:10` unconditionally raises MaintenanceUnavailable (no publication adapter).

   Failure scenario: The controller creates child A with only btq-1yedv recorded and retirement-semantics edits proceed without a pinned aa860 approval. Or qe3gk accepts A and B under 6f authority it was never granted, and 'real authenticated offline ingress' is met with a manually observed stream rather than reserved-profile proof. The design needs a per-child mapping (A-retirement → aa860 approval ID; A-permit → 6f/btq-1yedv), a new or amended qe3gk dependency, an explicit statement that installed closure is currently unattainable and stays HOLD, and a definition of acceptable ingress evidence that excludes the manual stream.

10. `docs/adr/2026-10-18-maintenance-runtime-repair-admission.md:55`: No child owns the u9 #3 refusal ('refuse unsupported u9 3 projection'). Child A's scope (line 15) leaves out recovery.py `Selector`/`Projection` validation, which still accepts `type: ask` and an arbitrary 64-hex `adapter_sha256`. Line 41 assigns the refusal only to queue child B.

    Failure scenario: After both children merge, admind still registers an ask-selector `clear-proven-cancel` descriptor, delivers a consent notice, accepts `!maintenance settle` and issues a permit for an ask whose retirement was disqualified by identity drift. Only the queue executor refuses later, so the operator is asked for consent to something that can never run, and the admind-side authority gap from u9 #3 remains.
