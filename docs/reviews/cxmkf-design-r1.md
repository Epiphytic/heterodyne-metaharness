- **[BLOCKING] §1.3 K13–K14, §1.6 K23, §2.1:** The choice block cannot always fit in the last chunk. Six valid 80-character choices produce a **542-character footer** and a **1,169-character block including the answer line**, measured offline. At the supported `chunk_chars=200`, keeping that block together necessarily exceeds the limit. Define a consistent refusal or splitting policy, including oversized individual link lines, and test maximum choices at the minimum chunk size.

- **[BLOCKING] §1.1 K4–K6, §1.5 K18–K20:** Notice limits bound notices, but do not adequately bound messages or queued bytes. Link URLs have no specified length cap and sit outside the body budget. A request below the existing 262,144-byte socket limit can therefore create hundreds of lane-1 chunks from one notice, delaying approvals despite both notice limits passing. Cap the complete rendered notice and its part count, including links and framing. Enforce admission checks and insertion atomically under the posting lock; test concurrent submissions and maximum-size links. Q7’s constants are reasonable only with those additional bounds.

- **[BLOCKING] §1.5 K19, §2.1 link tests:** `git branch -r --contains` does not prove the commit is available at the GitHub repository named by `origin`. An offline experiment accepted an unpushed commit after creating only `refs/remotes/other/main`. Even an `origin` tracking ref can be stale or locally fabricated. Restricting the check to origin improves it, but an offline check still cannot guarantee current GitHub availability. Either explicitly accept that weaker guarantee or specify trusted publication evidence or remote verification. Add wrong-remote, changed-origin and stale-ref tests; the proposed fake-tracking-ref fixture currently demonstrates the weakness.

- **[BLOCKING] §1.4 K17a–K17b, Q4; `src/heterodyne/admind/approvals.py:232`:** Review validity is not an approval-purpose discriminator. `postable()` permits both `True` and `None`; it does not establish that every execution approval lacks a design review. An execution approval carrying valid review metadata would be labelled `APPROVAL: design`, and an explicit corrective flag would be refused. Resolve Q4 with an enforceable invariant or use an explicit authoritative purpose field. Keeping a cosmetic label outside the existing digest is acceptable only when it cannot misrepresent the authorization; retaining checked chunks alone does not establish that invariant.

- **[BLOCKING] §1.6 K22; `src/heterodyne/admind/daemon.py:2827`:** Thread resolution omits a reachable state: chunk 0 is `sent` **without a message ID**. The current sender explicitly stores this when `message_ids_hex` is empty. K22 covers sent-with-ID, failed and pending, leaving continuations undefined; treating this as “wait” can stall the entire lane. Specify a terminal fallback for sent-without-ID and a missing parent, persist the resolution, and test restart and retry behavior. Normal sent-with-ID resolution is sound; failed-chunk fallback must continue to leave R8 delivery checks unsatisfied.

Test hostile arguments and configuration behavior, beyond asserting the three `-c` flags. I found no demonstrated shell-command injection in the proposed approach, but those flags alone are not a complete specification.
