10 findings, most severe first:

1. `docs/adr/2026-10-18-gateway-durable-custody.md:45`: CRITICAL: an 'unknown' event can never be closed out. The final receipt forbids the unknown state, and none of the four resolution actions (retain, retry-positive-not-issued, resume-sealed-result, consume-proven-delivery) applies to an issued-but-unsealed result. So an unknown event holds an active slot forever and keeps the inventory not-clear forever, which turns the R3 'locked retained work' problem into a permanent lock instead of fixing it.

   Failure scenario: escalation._run_one marks a result 'uncertain' when the 3600s timeout fires, the answer is empty or uses a non-English script, or the codex exit is unclear. The child receipt becomes 'unknown'. The existing hermes_maintenance_inventory.runs() refuses any receipt that isn't complete or refused, so every later EX publication HOLDs. With enough unknowns, all 256 active slots are taken and intake stops for good. Fix: add a human-consented 'archive-unknown' action through the same independent-consent and EX path. It must not replay or deliver anything. It moves the exact bytes to a terminal slot with an unknown-diagnostic receipt, and the inventory records that as an acknowledged obligation rather than clear state. Also state how the existing inventory check is versioned for it.

2. `docs/adr/2026-10-18-gateway-durable-custody.md:31`: HIGH: the 4096 terminal slots are a lifetime limit with no reuse, pruning or export ('terminal exhaustion stops new intake; future retention requires separate design'). The gateway permanently stops after 4096 events. That is a regression from the current Owner and D788, which retire consumed, complete work.

   Failure scenario: Each escalation event that reaches custody uses one terminal slot that is never released. Once 4096 have been used (or the up-front 32GiB reservation can't be met), every new message is refused permanently. The only way out is a design that doesn't exist yet. Fix: before activation, design a human-approved export or epoch rotation that moves sealed archives to verified external custody and frees their slots. Alternatively, keep only the full 32KiB receipt plus hashes and drop the payload after a consented export. Also state the expected event rate, so 4096 and 32GiB can be checked against real use.

3. `docs/adr/2026-10-18-gateway-durable-custody.md:23`: HIGH: the immutable identity has to be written before the intake ACK, but it includes parent_operation, parent_ordinal, dispatch and prompt_sha256. Those don't exist yet at intake. It also fixes a single dispatch UUID, which rules out the later retries and work generations the design itself allows.

   Failure scenario: Owner.submit acknowledges before any coordinator lease exists. The parent operation is minted inside Runtime.attempt's coordinator.operation, and the dispatch is uuid4 from launch_child. The prompt is built inside escalation._run_one in the detached child. So identity can't be written at intake time. For retries, gateway_child_dispatches has inbox_id as PRIMARY KEY and launch_child returns the old linkage, while run_child refuses any non-null receipt. A retry-positive-not-issued or a generation 2 or 3 can therefore never get a fresh child admission, and the 32-segment history is kept per dispatch rather than per lifetime. Fix: limit the intake identity to event, input and recipient fields. Bind parent operation, dispatch and prompt per attempt as chain records. Specify the dispatch-table schema change, (inbox_id, generation, attempt) → dispatch, and a lifetime segment counter.

4. `docs/adr/2026-10-18-gateway-durable-custody.md:43`: HIGH: the design never says which gateway events enter custody, or who the 'consumer' is. Most events never launch a child: reactions and non-escalation text return a 'handled' value, with no dispatch, prompt or model output. The identity, delivery and consumer-ACK schemas don't fit those events.

   Failure scenario: A reaction or ordinary text goes through Owner.submit and route(). If it is outside custody, the in-memory Owner and its consumed flag still decide acknowledgement, so the R3 lost-work defect stays live for those paths. If it is inside custody, the required fields (dispatch, prompt_sha256, result, delivery, consumer_ack) have no values, and the final receipt allows nulls only for never-issued events. Fix: list the custody event classes and give each one a closed lifecycle. Define 'consumer' precisely: the native gateway caller that acknowledges upstream consumption versus the outbound recipient. Say which existing path remains for anything not in custody.

5. `docs/adr/2026-10-18-gateway-durable-custody.md:39`: HIGH: the output, seal and writer-stopped contracts assume the gateway owns a byte stream with a hard limit set before the model starts. The real writer is `codex exec --dangerously-bypass-approvals-and-sandbox -o answer.txt` in escalation._run_one, which the manifest doesn't pin at all.

   Failure scenario: Codex writes answer.txt itself and has no output cap, and the child only reads the file after exit. Popen creates no process group or cgroup, so a surviving descendant can't be ruled out, and Popen's default close_fds means codex holds no lease FD that could prove it has stopped. Under the design's own rule, activation is therefore HOLD indefinitely, and the reviewed sources never show it. The working-tree escalation.py also differs from the pinned commit, and nothing records that. Fix: add harness/escalation.py and queue_maintenance.detached_idle (committed plus working qualifications) to the manifest. Specify a new escalation port: output goes to a broker-owned, size-limited file or pipe, and the process is reaped via pidfd with proof that its own process group or cgroup is empty. Only then seal, or state explicitly that the current worker cannot qualify.

6. `docs/adr/2026-10-18-gateway-durable-custody-contracts.json:8`: HIGH: resume-sealed-result and the delivery-intent and delivery-proven transitions need a new Hermes continuation entry point, but contracts.json lists no such port. Today delivery runs inline in _run_one immediately after the model returns.

   Failure scenario: The child crashes after sealing the output but before the outbox insert, escalation_answers, inbox state update and _prompt_start_receipt. A human approves resume-sealed-result, but nothing can deliver it. run_child refuses because the receipt is non-null, and no code path runs post-model delivery from sealed bytes. The event stays HOLD while still holding an approved permit. Fix: add a port such as resume_sealed_delivery(event, invocation) plus record_delivery_intent and record_delivery_proof, giving owner, preconditions and SH re-admission. Do the same for ack_consumer's native adapter.

7. `docs/adr/2026-10-18-gateway-durable-custody.md:67`: HIGH: 'preserve prior checks' in the single Hermes inventory contradicts 'a sealed or quiescent result can survive EX'. Nothing stops new model attempts from repeatedly blocking EX either.

   Failure scenario: Existing runs() refuses inbox state 'sending' or 'uncertain' and any child receipt that is 'admitted' or 'unknown'. A sealed result that hasn't been delivered still has an 'admitted' receipt, so the inventory is never clear. Separately, EX refuses while any writer is active, but new dispatch-intent and model-issued transitions can start between EX tries, and codex can run for 3600s, so EX can be blocked indefinitely. Re-hashing up to 2GiB of active chains and blobs under the gate on every try makes this worse. Fix: version the check explicitly so it accepts only custody-sealed admitted receipts. Have EX set a durable epoch barrier that blocks new dispatch-intent and model-issued transitions, with a bounded drain timeout. Compare roots computed incrementally at seal time instead of re-hashing every blob under EX.

8. `docs/adr/2026-10-18-gateway-durable-custody.md:59`: HIGH: resolve_custody writes the 'consumed' record before the 'issuing' write-ahead record, which is the reverse of existing OperationRecovery.settle. The lock order also differs from settle, and the 'original child-ownership locks' it relies on can't prove that the writer has stopped.

   Failure scenario: A crash after consumed.json is written but before issuing.json leaves the permit consumed with no write-ahead program. Recovery is limited to the 'same write-ahead program', so it can't resume. The 30s window then expires, and custody_nonconsumption can't succeed because consumed.json exists, so the event is HOLD forever. Separately, settle takes turnstile, then gate, then the child lease lock (non-blocking), then journal. The design takes journal, then custody, then child-ownership. Custody also spans up to 32 segment operations whose leases are released during idle, so taking those locks proves nothing about a codex process that is still running. Fix: copy settle's ordering, with an issuing write-ahead that embeds the permit before consumed. Fix the lock order to match settle, and define exactly which segment leases are checked, alongside the separate lifecycle proof.

9. `docs/adr/2026-10-18-gateway-durable-custody.md:27`: MEDIUM: the 2MiB control budget leaves out output-chunk, owner, seal, lifecycle and not-issued records. cancel-requested transitions have no limit. Product-side proposals, permits and notices fall outside the custody budget even though the design says 'references cannot evade total bytes'.

   Failure scenario: Up to 1024 gateway-custody-output records of about 400B each (around 400KiB), plus per-attempt owner, seal and lifecycle records across 9 attempts, compete for the 512KiB proof allowance. Each cancelled route() waiter adds another cancel-requested transition, so repeated cancellations can use all 512 transitions. No room is set aside for resolution-applied or consumer-acked, so the event is stuck in HOLD. On the product side, the existing maintenance_recovery_proposals table is capped at 128 rows in total, and NOTICE_PER_HOUR and NOTICE_UNDELIVERED are shared, while custody allows 256 events × 16 proposals with daily expiry and boot binding. Fix: allocate budget for each record type, deduplicate cancels per waiter and cap them, reserve the final transitions, and define a separate product-side custody table limit and notice quota.

10. `docs/adr/2026-10-18-gateway-durable-custody.md:73`: MEDIUM: the design never lists the KKV R3 critical findings 1/2/3/6/7 or maps each to the mechanism and test that resolves it. None of the three implementation roles clearly owns the native consumer ACK capability that activation depends on. The custody command grammar also differs from the existing one.

    Failure scenario: The human approver can't check that this amendment actually closes each R3 critical. Activation needs a demonstrated native consumer ACK that none of the three minted targets is responsible for, so the criticals could stay open indefinitely while the in-memory Owner remains live with no interim mitigation. `!custody settle TOKEN` requires a full 64-hex token, while the existing `!maintenance (settle|revoke) [0-9a-f]{24}` uses 24 hex characters, which is hard to enter on a phone. Fix: add a table mapping each critical to its mechanism and failure-first test, name the owner and target for native consumer ACK, and reuse the existing 24-hex or reply-to-notice binding.
