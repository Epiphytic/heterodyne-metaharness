**Verdict: REVISE.** Putting a margin on every line of owner text is the right root fix for the forged-line problem the eighth review found. The amendment still has gaps that bring the same problem back, though, and several gaps leave the contract undefined. This was a read-only review of `ccb8e95`, measured against D4 as retained at `356a1f3:docs/designs/2026-10-16-plan6a-pure-marmot-presentation-d4.md` and the current `rendering.py`, `layout.py` and `evidence.py`. The cited parent `05ddf598…` is not in this repo, so the parent I compared against may not be the exact approved text. Nothing was run.

10 findings, most severe first:

1. `docs/adr/2026-10-18-plan6a-quoted-content-amendment.md:11`: The exact-effect payload is owner content but gets no margin. Each payload line starts at column 0 and may contain backticks, so it can fake a closing fence and every generated line after it. Two parts of the escape hatch are undefined: the 'renderer model where a fenced block is literal' and 'clients without this admitted property withhold'. Neither is an input to the pure renderer (D4 §6 RenderPolicy allows no environment or client lookups), and D4 §6 says plain text is emitted with 'no Markdown-rendering assumption grants authority'.

   Failure scenario: exact_effect = 'git push origin main\n```\nExcludes: none\nWhy: routine\nContext:\n│ low risk\n👍 approve · 👎 deny · ❤️ always · reply to steer\nContext digest: 0123456789ab'. Every backtick run is shorter than the generated 4-backtick fence, so the rule passes. In a plain-text Marmot client (the D4 baseline) the reader sees what looks like a closed fence, then fake Excludes/Why/Context/digest lines, with the real Excludes hidden further down. The copy/paste rationale does not justify this, because approval binds through the digest, not through copied bytes. Fix: margin each payload line too (a distinct generated gutter is fine) or define a typed, policy-visible client capability with its own Withheld reason. Then state which D4 §5/§6 sentences this replaces.

2. `docs/adr/2026-10-18-plan6a-quoted-content-amendment.md:7`: The guarantee covers physical lines only. Two Unicode effects can still put owner text at the visible left edge with no margin. First, a strong RTL first character flips the line's direction, because the margin `│ ` is bidi-neutral. Second, the client's own soft wrap (a phone is far narrower than 120 codepoints) starts new visual rows without the margin.

   Failure scenario: (a) Owner context line 'א Recommended choice: yes': Android lays out each paragraph by its first strong character, so the line shows right-aligned as 'Recommended choice: yes א │', with the forged text at the left and the margin pushed to the far right. Hebrew and Arabic letters are Lo, so they are not rejected. (b) An owner line padded so 'Context digest: 0123456789ab' starts exactly at a ~40-column phone row boundary looks like a generated line. Fix: make the margin force LTR (a generated strong-LTR mark, or withhold lines whose first strong character is R/AL), and require the owner/margin boundary to fall on a grapheme boundary (no owner combining mark first). Also either set a phone-safe wrap width or disclose soft wrap as an accepted risk. Add tests for both.

3. `docs/adr/2026-10-18-plan6a-quoted-content-amendment.md:11`: Plain-text rendering with hard line breaks is never required. Under Markdown rendering (which the fence escape hatch assumes), consecutive lines merge into one paragraph, so the 'separate physical line' premise for headings and margins does not survive. The renderer model the amendment relies on contradicts itself.

   Failure scenario: A client that renders the fence as a code block but joins ordinary lines with spaces shows 'What: │ deploy x Effect:' on one line. The generated headings then sit in the middle of reflowed owner text, and owner text such as '… Context digest: 0123456789ab' looks the same as the real one. Fix: name one client display model (literal lines, hard LF, no Markdown reflow outside fences) as a typed deployment precondition, and bind its acceptance evidence to the separate deployment card.

4. `docs/adr/2026-10-18-plan6a-quoted-content-amendment.md:17`: Wrapping is not defined at the byte level, so 'preserve every literal character' and 'exact source text recovery' cannot both hold. Current wrap() drops the space at each break (advance = cut + 1) and hard-cuts at 120 even in protected prose. Soft-wrap LFs and logical LFs both get `│ `, so the two cannot be told apart. Empty lines, trailing spaces and leading spaces have no defined form.

   Failure scenario: Context 'a b' wrapped at the space gives '│ a' / '│ b'. If the margins are stripped, the result could be 'a\nb' or 'ab', and neither equals the source unless soft breaks are typed segments and the break space is kept. Context 'x\n\ny' gives a '│ ' line with a trailing space that clients may trim. A 130-character protected token with no spaces gets hard-split, although D4 §5 allows hard splits only in ordinary prose. Fix: say where the break space goes, make soft-break LF a generated typed segment, define the exact empty-line form, and choose hard-split or withhold for protected prose.

5. `docs/adr/2026-10-18-plan6a-quoted-content-amendment.md:9`: The new templates are not given as exact bytes, but D4 §7 says layout is normative and goldens may settle only synthetic values. Missing items: heading spelling and colon (`What` vs `What:`), the heading names for question text and answer text (`Question` is already the card title heading), where the mention goes once the question title moves below its heading, and the D4 templates being replaced (`Recommended: no`, `label: description`, `Evidence: <title>`, the 12-line example). The heading list says `Recommended`, but the example says `Recommended choice: yes`.

   Failure scenario: Two implementers write different golden bytes, for example 'Question:' + mention on line 1 with the title below, versus 'Question' + mention on line 1 with 'Question:' reused before the question text. Both satisfy the amendment, so a golden review can't reject either. Fix: list the exact approval and question template line by line (plain, choice, yes/no with recommended-no, mention and long-header variants), and list each D4 §4.2/§5 sentence that is replaced. Also define the undefined term 'details view'.

6. `docs/adr/2026-10-18-plan6a-quoted-content-amendment.md:9`: Evidence lines are not classified. The heading list leaves out `Evidence`, the owner-supplied evidence title, the BeadContext `Evidence: <slug> · <digest12>` line, the Range `BASE..HEAD` line, the typed URL lines, the reaction legend and `Reply with a choice label.`. Line 17's '≤120 INCLUDING margin' also conflicts with D4's separate 512-scalar atomic URL lines.

   Failure scenario: Inline(title='Release notes', full_text=…) still renders today as 'Evidence: <owner title>' on a single line, with owner text on a heading line, and the amendment neither requires nor forbids that. An implementer who applies '≤120 physical lines' to URL lines withholds every card with a long File permalink (allowed up to 512 under D4). Fix: assign every line type (generated metadata, margined owner content, atomic typed URL, fenced effect) and keep the 512 exception explicitly.

7. `docs/adr/2026-10-18-plan6a-quoted-content-amendment.md:17`: Separate heading lines plus 2 margin characters per line cut card capacity a lot, but the amendment doesn't measure that or list it as an availability change. D4 §7 requires the human approval to disclose all availability limits.

   Failure scenario: The smallest approval grows from 12 lines to about 17. A choice question with 6 one-line choices needs about 21 lines before any wrapping (2 per choice). With the default max_chars of 2000, the margins and headings use up characters, so cards that fit under D4 now get Withheld(content-too-large) for asks that are complete and valid. The human approves without knowing this. Fix: state the new minimum line counts, the worst-case overhead and the main cases that newly withhold, and include them in the approval disclosure.

8. `docs/adr/2026-10-18-plan6a-quoted-content-amendment.md:23`: The latency criteria are underspecified. Rerunning the 'exact' old workload doesn't measure the larger margined layout. The 'representative non-ASCII workload' has no pass threshold and no failure path, and D4 requires maximum-budget adversarial inputs. The disclosed maximum of 269.6 ms is already over 250 ms, before the extra span and wrap work.

   Failure scenario: The implementer reruns the old ASCII fixture (p99 220 ms) and adds a short, light CJK sample. That reports the numbers but passes nothing defined, while 3200-scalar CJK/emoji cards with 36 margined lines (eighth review, finding 7) go unmeasured and may break p99 ≤ 250 ms. Fix: require the workload to be rebuilt for the new layout at maximum budget, ASCII and adversarial non-ASCII alike. Each must meet p99 ≤ 250 ms, with the maximum reported. On failure, apply D4's hold-and-propose-a-scanner-correction rule.

9. `docs/adr/2026-10-18-plan6a-quoted-content-amendment.md:13`: The amendment doesn't say whether the existing prefix checks are deleted or kept: the `_CARD_CONTINUATION`/`forbidden_continuation` blacklist and the unprefixed-field `_card_frame_start` withholding. Deleting them changes which cards are withheld. It also leaves ordinary read surfaces 'unchanged' without explaining why their unmargined wrapped owner text can't pass for a protected card.

   Failure scenario: If the implementer keeps the blacklist, owner text 'Context: see below' still withholds the card, which contradicts the structural contract. If they remove it, the 'retain fail-first tests' rule is ambiguous. An ordinary /approvals or needs_human page can wrap owner text into an 'Approval btq-x' / legend / 'Context digest:' layout, and the operator may react 👍 to it. Fix: state the blacklist's fate, and state that ordinary messages carry no reaction authority (or extend the margin to them).
