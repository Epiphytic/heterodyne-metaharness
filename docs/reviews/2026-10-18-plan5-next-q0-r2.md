**Verdict: REVISE.** The R1 repair does fix findings 1, 3, 4, 5, 6, 8 and 9 as claimed. Finding 7 (keeping an advanced readback `Uncertain`, no replay) is a sound choice. For finding 2, the "only an actual settled result from the pinned reducer frees capacity" approach follows D4. Four problems remain in the offline source itself:

- **No settle path for undispatched rows:** an approved execution row that was never prepared, for example because it expired before prepare, has no way to be settled and holds capacity forever.
- **Report immutability guard removed:** the core check that kept positive success evidence immutable is gone and nothing in core replaces it.
- **Terminal rows still writable:** rows already marked terminal (capacity released) can still be written through the dispatch operations.
- **Over-strict text validation:** it now blocks recording real decisions when the reaction is a ZWJ emoji or the denial reason has more than one line.

**Future activation requirements, not defects in this PoC:** a live atomic/CAS backend, authentication, an authenticated receipt that proves which write won, and how real operators recover rows held after expiry, exhausted launches or absent reports.

10 findings, most severe first:

1. `btq_actions/core.py:413`: The new settle port goes through _dispatch, which refuses when row.dispatch is None, so an approved execution row that was never prepared (deadline passed before prepare, or never dispatched) cannot be settled even with positive, authenticated, exactly scoped recovery. R1 finding 2 is not repaired for that case.

   Failure scenario: Execution row is committed with an approve event; the 60s deadline passes before prepare, so the pinned prepare reducer refuses. settle(...) raises Refused('invocation-mismatch') because dispatch is None. The row stays terminal=False forever and counts against the per-bead cap of 2 and global_cap. Two such rows block allocation for that bead permanently, and no recovery observation can release them.

2. `btq_actions/core.py:472`: The R1 change removed core's `any(r.effect == 'succeeded')` guard and nothing replaced it, so core no longer keeps positive success evidence immutable, despite the doc saying it is. Any later report the reducer accepts is appended next to an unsettled success.

   Failure scenario: Report(inv, claim, 'succeeded', 'f'*64, cleanup_proven=False) is committed and not settled. A later Report(inv, claim, 'succeeded', 'a'*64, True), or an 'unknown'/'absent' report, is not an exact duplicate, so core passes it to contracts.report and appends it. If the reducer accepts it, the row records conflicting success evidence or a downgraded effect and may be settled on the second digest. No test covers differing evidence; the only test reuses 'f'*64.

3. `btq_actions/core.py:358`: _dispatch does not check row.terminal, so transition, preparation_failed, settle and restart can still write to a row whose capacity has already been released. _write carries terminal=True forward, and the only protection left is the reducer's internal state.

   Failure scenario: A row is settled (terminal=True; capacity freed and possibly reallocated). A second settle(...) or restart(...) with the same invocation reaches the contract port and, if the reducer accepts it (for example idempotent settle or a reducer version drift), _write commits a new dispatch or a new invocation/launch on a terminal row. That can arm a launch which no longer counts against capacity. Only report() checks row.terminal.

4. `btq_actions/core.py:551`: validate_text now rejects Unicode category Cf, which includes U+200D ZERO WIDTH JOINER, so any ZWJ emoji reaction makes _event refuse and blocks recording the whole authenticated decision. The reaction is only metadata.

   Failure scenario: The operator approves with reaction '❤️‍🔥' (U+2764 U+FE0F U+200D U+1F525) or '🏳️‍🌈'. _event -> validate_text(reaction, 32) raises Refused('invalid-text'), so decide() never commits. The first authenticated decision is lost and the row stays 'filed', holding capacity.

5. `btq_actions/core.py:547`: Deny reasons now go through validate_text, which rejects all Cc characters including \n and \t, so a normal multi-line operator denial cannot be recorded.

The denial is never committed, the row stays 'filed' and non-terminal, and keeps holding per-bead and global capacity. The fix for R1 finding 10 only needed to reject C1/bidi/separator characters, not every whitespace control.
