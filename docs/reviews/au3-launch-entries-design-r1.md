# AU-3 launch entries design review r1 (cycle 1 of 3)

Reviewer: gpt-6.1-sol (Codex, configured effort). Author: claude-opus-5-5. Mode: cross-model. Reviewed commit: 9a8d889. Verdict: REVISE.

1. **[BLOCKING] `docs/superpowers/specs/2026-10-08-au3-launch-entries-design.md:61` — Credential identity disagrees with AU-2.** AU-3 hashes canonical JSON; AU-2 hashes the NUL-separated adapter and login-file paths. The same login therefore gets different `ck1-` keys, breaking continuity when AU-2 lands. AU-3 also expands `~` through passwd, while AU-2 uses the supplied environment’s `HOME`. **Fix:** reuse AU-2’s `credential_key(adapter, login_files)` and account-resolution rules; apply the stricter file-existence check specifically where adoption requires it.

2. **[BLOCKING] `docs/superpowers/specs/2026-10-08-au3-launch-entries-design.md:252` — Replay can launch the same operation twice.** After a crash at `receipt`, `outcome`, or `outcome!`, the original operation remains open. Reconciliation sets its entry to `launched`, but step 2 explicitly pins another generation whenever the pinned entry has an outcome. If the original session has already ended, replay dispatches again instead of completing the original operation. Reconciliation also omits restoration of the receipt’s native ID. **Fix:** distinguish completion of the operation’s own dispatch from a genuinely new launch operation. Replay a started receipt through the outcome/native-ID writes and DONE tail without another dispatch; replay a refusal through its appropriate failure tail.

3. **[BLOCKING] `docs/superpowers/specs/2026-10-08-au3-launch-entries-design.md:287` — Operator release fabricates a launch outcome.** This interim behaviour is **not acceptable under r14**. D2 and PICKUP.md require a dispatched entry’s outcome to come exclusively from its receipt. Stopping a session and recording an operator event do not establish that generation started. **Fix:** remove the non-receipt `launched` write. Keep the entry unresolved and block further gating until an explicitly approved recovery procedure resolves the uncertainty; any exception needs an authority amendment.

4. **[BLOCKING] `docs/superpowers/specs/2026-10-08-au3-launch-entries-design.md:223` — A held adoption has no supported recovery exit.** The immutable `held` verdict causes every release to re-escalate, even after the operator repairs the original problem. Unclaiming does not remove that row, so reclaiming the same bead still cannot launch. This interim behaviour is **not acceptable as specified under r14 §4.3**, which identifies journaled release as the exit from a held park. Blocking a guessed-account resume is required; permanently blocking verified operator recovery is not. **Fix:** specify a journaled recovery transition that retains the original adoption evidence and allows release only after account/history verification. Do not make unclaiming the recovery mechanism.

5. **[BLOCKING] `docs/superpowers/specs/2026-10-08-au3-launch-entries-design.md:219` — Startup escalation conflicts with preserved open operations.** An open operation explicitly makes adoption `held` at line 191. Startup then calls `parker.escalate`, which opens another operation, but the existing journal permits only one open operation per bead. This produces `OpConflict` before recovery can finish. Crash replay of an already-open adoption escalation has the same problem. **Fix:** atomically hand off an existing operation to escalation, using the existing `escalate_from` pattern, and replay an already-created escalation rather than opening another. Commit `settled` with that handoff.

6. **[BLOCKING] `docs/superpowers/specs/2026-10-08-au3-launch-entries-design.md:183` — Missing metadata is mistaken for proof that no session launched.** The existing code explicitly supports a previously running bead whose session record is missing (`LAUNCH_UNRECORDED`). AU-3 gives that bead no adoption row. Operator release can then recreate its record, after which the guard sees no launch history and treats it as a first launch on the current login. **Fix:** exempt only beads positively established never to have launched. Missing records with possible prior launch history must receive a recoverable adoption hold.

7. **[BLOCKING] `docs/superpowers/specs/2026-10-08-au3-launch-entries-design.md:251` — Launch-entry reconstruction contradicts r14.** The design categorically refuses to import entries from bead metadata after journal loss or restoration. ADR §3.3 explicitly requires launch entries to be rebuilt from the bead, and D2 requires generation sequences to rebuild from `wsd_launches` alone. A pure reconstruction test at line 321 does not implement that recovery path. **Fix:** define reconstruction that preserves entries and generation sequences while keeping receipts journal-only. Reconstructed dispatched entries without outcomes and receipts must still hold; metadata must never manufacture a receipt.

8. **[NON-BLOCKING] `docs/superpowers/specs/2026-10-08-au3-launch-entries-design.md:255` — AccountChanged escalation is an acceptable temporary safety stop within AU-3’s staged scope.** It preserves credential continuity and requires operator intervention instead of switching accounts or retrying on a timer. It is not the final D5 behaviour: r14 requires an `account_changed` deferral, rechecked at startup, reload, or release. **Fix:** retain the explicit AU-4 replacement requirement and ensure the completed plan implements those recheck and deferral transitions.

REVISE
