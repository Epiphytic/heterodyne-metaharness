2. [BLOCKING] **Automatic bumps cannot match B6’s recognizer.** [B6:20](docs/superpowers/specs/2026-10-07-admind-asks-bump-design.md:20) recognizes only `asknote:<ask>:bump:<mid>:<i>`, while [B14:27](docs/superpowers/specs/2026-10-07-admind-asks-bump-design.md:27) emits `asknote:<ask>:autobump:<seq>:<i>` and claims it matches. Plain replies would therefore retain ordinary notice routing to the agent. **Fix:** explicitly recognize both exact, sent-only key forms, with separate validation for the 64-hex command ID and decimal sequence. Keep both outside `_CARD_KEY`.

3. [BLOCKING] **“Full repeat” cannot always be measured using the original `card_parts`.** [B11–B12:24](docs/superpowers/specs/2026-10-07-admind-asks-bump-design.md:24) repeats full details but checks completeness using the original card’s count. A legacy shortened approval card, or a shortened question/merge card, can have fewer original chunks than its repeat; `full_text` explicitly renders the whole ask ([asks.py:229](src/heterodyne/admind/asks.py:229)). Checking only the original count can falsely classify a prefix as a complete repeat. **Fix:** persist the actual chunk count for each repeat and require every expected index from that single batch. Preserve the independent legacy, operator-specific `!details` gate. For current approval asks, reusing `stored_details` unchanged does preserve R21; do not re-split those checked chunks.

4. [BLOCKING] **B14 needs durable, atomic activity transitions.** [B14:27](docs/superpowers/specs/2026-10-07-admind-asks-bump-design.md:27) does not define whether bumps and repeats reset activity when queued or sent, nor couple automatic enqueueing with the clock update. A crash between those writes can queue another reminder after restart; waiting for delivery can accumulate reminders while sending is blocked. The current send marker records no timestamp ([store.py:432](src/heterodyne/admind/store.py:432)). **Fix:** define UTC timestamps and update rules explicitly. Atomically reserve/enqueue an automatic bump and persist its activity watermark; define pending/failed delivery behavior. Apply inbound resets only after authorization and successful replay claim, using a monotonic maximum. Deferred or skipped checks must not advance activity.

5. [BLOCKING] **The migration discards recent operator activity.** Initializing every existing row from `created_at` ([B14:27](docs/superpowers/specs/2026-10-07-admind-asks-bump-design.md:27)) immediately bumps an old approval ask even if the operator added a note an hour ago. Those notes already have durable timestamps ([store.py:601](src/heterodyne/admind/store.py:601)). **Fix:** backfill from available activity history, including notes and decision attempts; specify a conservative fallback for unavailable delivery history. Make migration atomic and one-time, so subsequent restarts preserve the clock.

[NON-BLOCKING] **B13 introduces an exception to the literal original-message requirement.** [B13:26](docs/superpowers/specs/2026-10-07-admind-asks-bump-design.md:26) always avoids bump chains, but its repeat fallback is a different message from B3’s original `ask:<id>:0`. Its “first delivered copy” rationale also conflicts with preferring an original that arrives later. **Fix:** explicitly amend B3 with the replacement-card exception and define late-original behavior. If the original-message requirement remains strict, skip when the original is unavailable.

7. [NON-BLOCKING] **Clarify scheduler locking and deferral without changing R29’s lock order.** [B14:27](docs/superpowers/specs/2026-10-07-admind-asks-bump-design.md:27) specifies `work_lock`, which serializes decisions and refreshes, but socket posts independently hold `ask_post_lock` ([daemon.py:645](src/heterodyne/admind/daemon.py:645)). **Fix:** require final eligibility/gate checks and enqueueing without an intervening await, in one transaction; preserve `work_lock → ask_post_lock` whenever both are needed. Use the existing outbound gate, including observation and operator-seen checks, and give R29’s fresh ask its own clock. Replace “at most every 10 minutes” with an unambiguous check interval.
