**Verdict: REVISE.** The design has the right overall shape: an unresolved HOLD instead of an invented failure, protection before the adapter is released, separate recovery approvals, and idempotent post mapping keyed by operation. But four things are not viable against source `167b1b9` as written:

- **Ambient Store mutation:** the Store already changes evidence on every request. That undercuts the design's premise of HOLD and protection.
- **Laundered failures:** the Store records synthesized failures that the settle table would accept as positive evidence.
- **Withdraw fence:** withdraw has no fence on the Store side.
- **Recovery approval binding:** the recovery approval's content is not bound to anything T10 itself produced.

I checked the input manifest hashes for the design and three sources, and they match. The design and ADR files are byte-identical. This was a static, read-only review: no edits, tests, probes, queue, database or network.

10 findings, most severe first:

1. `docs/designs/2026-10-18-t10-operational-recovery.md:49`: The design starts protecting artifacts at prepare-quarantine. But both Store backends route every request (outcome, state, list, publish, verify, remove) through store_core.handle(), which first runs _recover() and _sweep() under the exclusive Store lock. So the evidence of an unresolved HOLD row keeps being changed or deleted before any preparation exists, and 'nonmutating inspection' cannot be built on the existing request path.

   Failure scenario: An approved row is in HOLD because the helper keeps failing. Any unrelated `wsctl harness list`, or the advance tick's _recover_store()/outcome(), goes through handle(). _sweep then deletes the row's complete staging and staged manifest once older than staging_hours. Or _recover_one finds the .record.json missing and calls _abandon, which writes .failed and removes the trees. By the time the operator runs inspect or prepare-quarantine, the 'valid staged manifest' settle path and the tree are gone, the snapshot digest changes on every tick, and a recoverable row becomes unrecoverable. Fix: protection must start the moment a row enters approved/HOLD. Make it a Store-side hold record that _recover, _sweep, _abandon and _remove_install honor. Give inspect its own handler that skips the handle() prologue, and amend E21 to say so.

2. `docs/designs/2026-10-18-t10-operational-recovery.md:40`: The settle table maps 'Store-owned durable failure' to Journal `failed`. But the existing Store creates exactly those records from missing or malformed evidence: _recover_one writes .failed RECOVERY_FAILED for an unparsable intent and calls _abandon on any Refused, such as a missing record file. Separately, _outcome turns a transient _state OSError ('broken') into `failed:INSTALL_BROKEN`. Section 1 says neither kind of evidence proves failure.

   Failure scenario: An EIO during check_fast makes _state return 'broken'. outcome() returns 'failed:INSTALL_BROKEN', and settle records a terminal Journal `failed`, releasing the adapter-wide hold even though a valid receipt exists and the install later verifies as published. Likewise, a lost .record.json leads to _abandon, a .failed record, and Journal failed: a failure invented from missing evidence. Fix: give Store results a typed provenance (pre-intent positive refusal via _fail, versus recovery-synthesized abandonment, versus a transiently unreadable receipt state). Only the first may settle to `failed`; the others stay HOLD.

3. `docs/designs/2026-10-18-t10-operational-recovery.md:71`: Withdraw fences publication only in the Journal, and the Journal has no durable 'publish-issuing' phase. So 'publication already issued' cannot be determined for an approved row. A helper publish whose client timed out with HELPER_FAILED keeps running in the helper and can finish after the withdrawal.

   Failure scenario: advance calls store.publish on HelperStore. The socket times out (StoreRefused HELPER_FAILED) while the helper is still waiting for the Store lock. Withdraw then sees Journal `approved` and Store outcome 'staged', decides nothing was issued, and records a terminal no-publication withdrawal, so the row stops being OPEN. The helper then completes _publish. The install is now 'published', and _pin and use will select it although its operation was withdrawn. Fix: write a Journal `publish-issuing` state (CAS) before every store.publish call. Add a Store-side cancel/fence record, written under the Store lock and honored by _publish and _recover. Allow withdraw only after a Store fence receipt, or when the row is in a state with no issuance.

4. `docs/designs/2026-10-18-t10-operational-recovery.md:51`: T10 does not compose the recovery approval and does not bind it to a recorded digest. The controller writes the bead, and the caller supplies `--approval <bead-id>`. approvals.verdict predicate 7 needs Expected.context_digest, which T10 has no independent source for, and only the `effect` string is checked. That leaves the human-visible scope and bead identity unverified, and a denial is not binding.

   Failure scenario: The controller writes a bead whose effect line has the right recovery UUID and preparation digest, but whose description and artifact list understate what gets released. Or it asks again on a new bead after a denial. T10 takes the bead's own posted digest as the expected value, so predicate 7 holds trivially, predicate 10 passes, and the quarantine is applied under consent the human never actually gave. Fix: at preparation, have T10 itself build the canonical recovery ask with approvals.compose and record its ask_digest (and, once created, the single bead ID) in the Journal by CAS. quarantine/withdraw must use Expected(recorded bead, recorded digest, exact effect) and require the bead's text to match byte-for-byte. A denial terminates that recovery UUID.

5. `docs/designs/2026-10-18-t10-operational-recovery.md:83`: The lock model does not match the source. There is no per-operation 'T10 operation lock', only one global HarnessOps RLock. advance() holds it across _decide's network and native reads (approve-bead readout, bd show, ask_digest git reads of 20 s each) and across store.publish helper calls. The design requires a 5 s lock bound and no network work under locks, and does not say how the existing paths will be restructured.

   Failure scenario: As specified, withdraw, settle and quarantine take 'the same lock used by advance'. A slow readout or git read in _decide holds it far longer than 5 s, so recovery commands return busy indefinitely, or the implementer drops the bound. If _decide's reads move outside the lock, nothing in the design makes its `approved` CAS conditional on the fence revision. remove/prune's _guarded order (every workstream guard lock, then the RLock, then the Store) is also missing from the stated order. Fix: define a concrete per-staging lock or revision scheme. Move _decide's reads before a CAS from posted to approved conditioned on revision and fence. State the complete order: guard locks, operation lock, Store lock, Journal transaction.

6. `docs/designs/2026-10-18-t10-operational-recovery.md:69`: The operation-key mapping is one key to one ask, but admind keeps a lineage of asks per bead. R29 refresh creates a new ask_id for the same bead, and commit_approval supersedes any open or answered ask for that bead from any poster, including a legacy AskPost. The withdraw tombstone and the 'delayed post cannot create a card' guarantee do not cover refresh or supersession.

   Failure scenario: The bead's digest changes, so run_attempt calls refresh() and posts a fresh card (new ask_id, refreshed_from=old). Withdraw on the mapped key finds the old ask 'stale' and, as designed, 'returns the actual status', but the refreshed card stays live and approvable. Or refresh runs after the tombstone and posts a card for a withdrawn operation. Fix: bind the key to the bead's whole lineage. refresh and commit_approval must check that bead's key and tombstone and carry them forward. Withdraw cancels every open or answered ask in the lineage. Legacy AskPost for a bead bound to a key is refused.

7. `docs/designs/2026-10-18-t10-operational-recovery.md:65`: Rows whose create or post outcome is unknown have no bounded exit. Adoption needs a positive match, 'truly unresolved creation' is left to native recovery that this amendment does not provide, withdraw requires an existing bead and a known ask mapping, and the design never says whether staging_hours expiry still applies to the new issuing/unknown states.

   Failure scenario: bd create times out after it committed, and the correlation lookup returns no match or is truncated. The row stays issuing/unknown: it cannot be withdrawn (no bead), adopted or recreated. The OPEN state holds its install name in in_use, and the operator has no supported command to end it, which recreates R7 #1 in a new place. Fix: say explicitly that a local fence with no publication (expiry or withdraw without a bead) is always allowed for these rows, because publication still needs a Journal approved CAS. Record any bead found later as an orphan approval, not as a reactivation.

8. `docs/designs/2026-10-18-t10-operational-recovery.md:55`: The claims that 'an ordinary old client/helper may not operate around it' and 'old helpers refuse' have no mechanism. The existing store_core.handle(), _recover, _sweep and _remove_install ignore unknown record directories, so an old helper or old LocalStore will mutate quarantine-protected artifacts without noticing.

   Failure scenario: After a downgrade, or with a stale helper process still running after the upgrade, an old-binary handle() runs _sweep and _recover on every request and _remove_install on remove. None of them read the new protection index, so protected stagings and trees are deleted or abandoned. Fix: give the on-disk format an incompatible epoch that the 167b1b9 code itself fails on (for example, move the directories it requires, or add a lock or layout file whose presence breaks the old _open_store). Add an acceptance test that runs the pinned old store_core against a quarantined Store and shows it refusing.

9. `docs/designs/2026-10-18-t10-operational-recovery.md:28`: Inspection 'rechecks both versions' and settle 'compares the snapshot', but the Store has no generation or revision counter. And settle's row 2 needs an 'intact original E13 approval' (a native/network re-read) without saying whether that read happens under the lock or how it is bound by CAS.

   Failure scenario: Without a Store generation bumped under the exclusive lock by every mutation, including the handle() prologue, the recheck must either re-enumerate up to 4096 entries (double cost, still racing the helper prologue) or compare something weaker and accept a mixed snapshot. Doing the E13 re-read under the lock breaks the no-network rule; doing it outside without a revision CAS lets settle publish on approval evidence that has since gone stale. Fix: add a durable Store generation counter to the Store protocol. Do the E13 re-read before taking locks and bind it to the operation revision checked by the CAS.

10. `docs/adr/2026-10-18-t10-operational-recovery.md:1`: The unapproved design is kept as two byte-identical copies, one in docs/designs and one in docs/adr. The manifest asserts they are identical, so every incorporation must edit both, and an ADR file existing under docs/adr can be mistaken for an enacted ADR reference.

    Failure scenario: Cost of the duplication: the planned one-time author incorporation edits one copy and not the other, so the immutable push carries two different 'designs' and the byte_identical_to claim becomes false. A tool or reader that treats docs/adr/* as accepted ADRs (btq's approval_valid checks for an ADR ref) sees an 'UNREVIEWED' proposal as an ADR. Fix: keep one canonical file, and add the ADR only after human approval, or make it a stub that points to the immutable design commit.
